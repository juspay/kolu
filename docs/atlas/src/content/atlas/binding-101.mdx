This is the companion to [the hosting side, taught](surface-hosting-101.html). That note taught the framework's **server** half — how a surface crosses a machine, ending at `buildHostRegistry` ("hold a session per host, dispatch by name"). This note teaches what **W4 added to the framework**: the **client** half of the same story. The subject here is `@kolu/surface*`; kolu itself appears only at the end, as the first consumer.

**The one-line map:** the framework already owned "a server holds N live connections" (the registry). W4 made it own the mirror image — **"a client holds N live connections, exactly one active, and the active one can swap at runtime"** — plus everything that swap must not break.<Footnote>"Exactly one active" is today's special case, not a ceiling (srid asked). The general volatility — a changing SET of live connections with a changing active SUBSET (the hybrid-canvas future) — is deliberately not a receptacle yet: its first real consumer is demand-gated. But the W4 shapes leave the door open by construction: the misroute guard is multiplicity-safe (each connection owns its own socket and clients — calls can't cross), `createKeyedRoot` composes N-wise, and the two single-active composites encode it as *policy*, not physics — the manager's retire-on-switch relaxes to retire-on-remove, and `connectionScoped` gains a set-shaped sibling (one scope per member). When hybrid canvas earns itself, multi-active is a relaxation of these primitives, not a rewrite.</Footnote> Six additions, each below with the problem that forced it.

## The volatility being tamed (why this belongs in the framework at all)

A client that can live-switch connections faces one hard volatility: **connection lifetime racing user intent**. Subscriptions were opened against connection A; the user picks B; A's socket is closing while B's is warming; calls are in flight on both; and the UI must never show A's data under B's name. None of that is app-specific — any multi-connection client (kolu's host switch today, a fleet view tomorrow) faces exactly it. That's the framework test from the [hosting note](surface-hosting-101.html) passing in the other direction: this is electricity, not app code.

## The six additions, ground up

**1 · `createKeyedRoot<K, T>` — the atom (surface-app/solid).** *Problem:* "when this key changes identity, tear down everything the old key built and rebuild for the new one" — with the first value available *synchronously* (a render must never see `undefined`). It sounds trivial; it had been hand-rolled **twice** with two different bugs waiting (one copy tested, one not). *Shape:* `createKeyedRoot(key, factory)` — dispose-and-recreate a reactive root on key-identity change. Everything else in this note stands on it. **Kolu usage:** never called directly — kolu reaches it *through* additions 2 and 4 (both are built on it), which is the point: one tested implementation of the guarantee, zero copies in app code.

**2 · `connectionScoped` — subscriptions that survive a swap (surface-app/solid).** *Problem:* a subscription opened against the active connection must tear down and re-open when the active connection changes — **and a torn-down subscription must be *silent***. The bug that forced the invariant: the readout subscriptions were wrapped in a detached reactive root whose disposer was *discarded*, so a swap disposed the owner but **never the subscription** — it leaked live, caught the old socket's dying error, and fired three red "server restarted" toasts on every switch.<Footnote>The honest debugging story, kept because it teaches: the first instinct was to *filter* the error at the subscribe site — a band-aid. The question "why isn't the abort signal already catching this?" exposed the truth: the sub was never disposed at all. Two framework fixes fell out: the detached root's disposer is now tied to the caller's owner, and the abort signal now travels all the way into the stream source so a pending read cancels immediately (fixing an asymmetry — the reactive sibling already passed its signal). The invariant, named: <em>a disposed subscription cannot report anything</em>.</Footnote> *Shape:* `connectionScoped(active, factory)` — keyed on the connection's identity, synchronously populated, owner-safe. When to reach for it: any `.use()`-style standing subscription in an app whose connection can swap. **Kolu usage** — `bindingScoped` is literally the manager's `connectionScoped` re-exported, and every standing readout rides it:

```ts
// packages/client/src/binding/bindings.ts — the framework primitive IS kolu's helper:
export const bindingScoped = manager.connectionScoped;

// packages/client/src/kaval/KavalUpdateBadge.tsx — a real consumer: this kaval-status
// sub re-opens against the new host's padi on every switch, old one torn down + silent:
const kavalStatus = useBindingScopedSub((b) =>
  b.clients.padi.cells.daemonStatus.use(...));
```

And the second name in that snippet, glossed: **`useBindingScopedSub` is kolu's shared-singleton form of `bindingScoped`** — `createSharedRoot(() => bindingScoped(pick))`, composed from the framework primitive plus kolu's pre-existing `createSharedRoot`. The problem it solves: `bindingScoped` runs under *some* reactive owner, and for an app-wide standing readout (daemon status, memory, inventory) the owner must be neither a component (unmounting would kill the sub out from under every other consumer) nor duplicated (N components opening N identical subscriptions). The shared root gives the sub **one app-lifetime owner shared by every consumer** — you read it as `useX()()`: the outer call resolves the shared root, the inner reads the current host's live sub. Framework mechanism, kolu ownership policy — which is why it lives in `binding/`, not in `surface-app`.

**3 · `createActiveConnectionManager<K, C>` — the client-side twin of the registry (surface-app/solid).** *Problem:* someone must own the keyed cache of live connections, the one-active rule, and the switch itself — and the switch has two failure modes that look exotic until they bite. **The yank:** warming a new connection can take *seconds* (an ssh provision); a naive `await warm(); setActive(k)` means an abandoned pick commits *late* and yanks the user away from their newer choice. The manager owns a **pick epoch** — bumped as the *first* statement (before even the same-key early return, so re-picking the current key *cancels* an in-flight pick), re-checked after every await: last intent wins, always. **The misroute:** a call in flight on the old connection must not resolve against it while the UI shows the new one — switching **retires** the old connection (socket closed, `send` stubbed to throw a *typed, honest* "retired by this client" error — never a fake "server restarted"). *Shape:* the manager takes policy callbacks — how to build a connection, how to warm it, what to do when the server rejects a key — and owns all the mechanism. **Kolu usage** — the entire host switch is this one construction plus policy (`packages/client/src/binding/bindings.ts`):

```ts
manager = createActiveConnectionManager<string, Binding>({
  initialKey: LOCAL_HOST,
  makeConnection: makeBinding,          // kolu's connectSurfaces bundle for ?host=<h>
  socketOf: (b) => b.ws,                // what to retire on switch
  isFallbackKey: (h) => h === LOCAL_HOST,
  fallbackKey: LOCAL_HOST,              // where a rejected host falls back to
  serverRejectedCloseCode: 1008,        // "host gone" → fallback, stop re-dialing
  warm: async (h, active) => {          // deliberate add-then-connect, via the
    await active.link.hosts.add({ host: h });  // CURRENT binding's link
  },
  /* …toasts on warm-failure/rejection — policy, not mechanism */
});
// switching a tab = manager.switchTo("zest") — epoch, retirement, re-key all inherited.
```

It is `buildHostRegistry`'s mirror image; the framework now holds both halves of "a changing set of live connections."

**4 · The provider goes accessor-shaped (surface-app).** *Problem:* `SurfaceAppProvider` took its control-plane client as a static value — a page-lifetime assumption baked into the framework's own front door. *Shape:* `controlPlane: Accessor<ControlPlane<T>>`; the provider re-derives its build-info subscription per control-plane *identity* (on `createKeyedRoot`, same guarantee, one tested home). Static callers just write `() => client`; swapping callers hand it the active connection's accessor. **Kolu usage** (`packages/client/src/index.tsx`) — one JSX prop is the whole integration:

```tsx
<SurfaceAppProvider controlPlane={() => activeBinding().clients.surfaceApp} …>
// a host switch re-derives build identity for the new host — no reload, no stale banner.
```

**5 · Honest teardown as a typed fact (surface-app).** *Problem:* a retired socket used to throw an error whose message claimed "server restarted — reload required" — a *lie* for an intentional switch, and downstream code toasted it. Two different states shared one representation. *Shape:* retirement now throws a **distinct typed error** ("socket retired by this client"); genuine stale-restart keeps its own. Distinct states, distinct types — the same rule as the identity sum in the hosting note. **Kolu usage:** nothing to call — kolu only tells the manager *what* to retire (`socketOf: (b) => b.ws` above) and inherits the honesty: a late call on a switched-away binding rejects with the retired-transport fact, the reload overlay fires only on a *genuine* server restart, and the old three-red-toasts lie is unspellable.

**6 · Entry-scoped cells on `buildHostRegistry` (surface-nix-host).** *Problem:* a registry entry often wants to serve its *own* diagnostic cells (identity, inventory) derived from its own session — and a hand-rolled side-map of disposers next to the registry disposed them on explicit removal but **not** on add-rollback or destroy-all: two latent leaks. *Shape:* `HostEntry` gains optional `cells?: { dispose() }`, and the registry disposes entry cells beside `session.destroy()` at **every** teardown site. **Kolu usage** (`packages/server/src/hostPool.ts`) — each pool entry serves its host's own diagnostics and hands their lifecycle to the registry:

```ts
buildEntry: (host) => {
  const perHostKolu = buildPerHostKoluCells(host, session); // identity·convergence·inventory,
  return {                                                  // read from THIS host's session
    session,
    handler,
    cells: { dispose: perHostKolu.dispose }, // registry disposes at EVERY teardown site —
  };                                          // remove, add-rollback, destroyAll alike
},
```

The leak class is structurally gone — the lifecycle lives with the thing that owns the other teardowns.

## Secondary: what's left in kolu (the first consumer)

After the six additions, kolu's own code shrinks to **policy**:

- `client/src/binding/` — *which* host (the `activeHost` signal + `sessionStorage`, per-tab by design), the Labs picker, recents, the toasts, the padi-flavored warm step (`hosts.add` through the current link), and `useBindingScopedSub` (the shared-singleton composition of the framework's `connectionScoped` with kolu's `createSharedRoot` — ownership policy, so it stays app-side). All the mechanism it used to hand-roll — cache, epoch, retirement, re-keying — is framework calls now (~150 lines deleted).
- `server/src/hostPool.ts` — `buildHostRegistry` holding one `DaemonSession<PadiSurfaceClient>` per machine (local arm or ssh arm per host), each entry contributing its per-host cells via addition 6; **no `controls`**, so `pool.reconnect` doesn't even typecheck.
- The dialogs read `identity()`/`convergence()` off the active binding — per-host by construction.

That division is the point: the next multi-connection app (a fleet view is literally "N live mirrored clients whose set changes") writes *only* the equivalent policy layer and inherits every bug-fix above for free.

## The through-line, if you read both notes

The [hosting note](surface-hosting-101.html) ended on: *when your thing won't fit a framework slot, check whether the behavior or only the annotation refuses — widen the slot if it's the annotation.* This note is the complementary rule: *when an app grows machinery that tames a hard volatility, name the receptacle it wants and graduate it* — the review's job is to make the candidate visible even at a population of one. The server half grew `buildHostRegistry` (drishti proved it); the client half grew `createActiveConnectionManager` (kolu proved it); the framework now owns both halves, and both apps write policy.
