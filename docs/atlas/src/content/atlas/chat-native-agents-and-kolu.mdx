**One conversation ↔ one kolu terminal.** User text → terminal input; agent
**messages** (not tools/edits) → conversation. The chat surface can be the
**kolu UI** first, then **Xyne Spaces via pesu** — same pipe, different face.

pesu is the XS bridge only; config is env/systemd next to pesu, not the web app.

## Components

Three processes on the chat side of the wall; four on the machine side. The
browser PWA is **not** on the critical path — same class of client as
`padi-tui` / `kolu mcp`.

| Component | Process | Job in this design |
| --- | --- | --- |
| **Xyne Spaces** | XS cloud | Threads, identity, @mention/DM delivery, message store |
| **XS apps platform** | part of XS | Signed **webhook** out; **app API** in (`postMessage`, `updateMessage`, `user/info`) |
| **pesu** | new daemon beside kolu (`packages/pesu`) | HTTP webhook receiver + bind store + padi client + XS API client |
| **padi** | workspace daemon | `padiSurface`: `lifecycle.*`, loaders, **new chat transcript stream** |
| **kaval** | PTY daemon under padi | Owns the live PTY; serializes writes |
| **agent CLI** | child in the PTY | claude / codex / opencode / grok — writes its own session files |
| **transcript loaders** | in-process in padi today | Vendor file → `transcript-core` IR (`user` · `assistant` · `tool_*` · …) |
| **kolu PWA** | browser | Tile = PTY; CH1 = Conversation in Inspector; deep link |

```
Xyne Spaces ──HTTPS──► pesu ──unix socket──► padi ──unix socket──► kaval ──PTY──► agent
     ▲                   │                      │
     │                   │                      └── loaders ← session files on disk
     └──── HTTPS API ────┘                      └── streams.transcriptChat → chat frames
```

pesu dials padi with the same kit as other non-browser faces
(`@kolu/padi/dial` → digest-keyed socket, control-core handshake, contract
skew fail-fast). It does **not** go through kolu-server.

## Surface primitives (why CT1 is a stream)

`padiSurface` is declared with the five `@kolu/surface` member kinds. The live
conversation path has to pick one deliberately — a one-shot is not a stream.

| Primitive | Shape | Fit for chat log? |
| --- | --- | --- |
| **`streams`** | input → async iterator; **snapshot-then-deltas** (or full replace each frame); reconnect re-subscribes via `STREAM_RETRY` | **Yes — CT1.** Per-terminal `{ id }`, first frame = chat-filtered snapshot, later = new/growing messages |
| **`procedures`** | request → one response | One-shot only. Today's `transcript.exportHtml`. Fine for export/dump; live only if a consumer polls+diffs — not the product path |
| **`events`** | discrete fires | No backlog on subscribe — wrong for conversation history |
| **`cells`** | standing single value | Not per-terminal append-heavy log |
| **`collections`** | keyed set + deltas | `terminals` is already the entity set; the message list is not a second keyspace |

**Client consume:**

- Kolu UI (CH1): `client.streams.transcriptChat.use(() => ({ id: focusedTerminal() }))` — enrolled in surface health by default.
- pesu (PE1): same stream over the dialed client (async iterator + stream-retry context). Unenrolled only if a single terminal's re-sub must not flicker a global health fact (same carve-out class as `terminalAttach`).

**Re-serve forwarding:** **`delta`** (fail-through) — same class as `activity` / `terminalAttach`. A mid-chain disconnect must terminate the downstream stream so a snapshot is only ever the first frame of a *fresh* stream, never spliced into a half-open one.

**Rejected alternatives (recorded):**

- Procedure-first CT1 + poll — works as a stopgap, lies about the product (we want live).
- Cell of “last assistant text” — loses history and multi-bubble turns.
- Event of “assistant said X” — reconnect drops everything already spoken.

## Bind state (pesu-local)

pesu holds the only new durable fact:

```
threadId  →  { terminalId, authorUserId, hostKey? }
```

- **Create on miss** — first webhook for an unbound thread runs
  `lifecycle.create` (+ agent launch), then stores the row.
- **Author gate** — later webhooks must match `authorUserId` (v1: one
  allowlisted operator). Mismatch → visible decline via `postMessage`, never
  silence, never `sendInput`.
- Not in kolu's conf store; not in XS. Survives pesu restart if persisted
  next to pesu (file/env scope TBD; start with on-disk JSON beside the daemon).

## Interaction: first message

End-to-end create + first prompt.

| Step | From → to | What moves |
| --- | --- | --- |
| 1 | User → XS | DM or `@bot` text in a channel |
| 2 | XS → pesu | `POST` webhook: `APP_MENTIONED` or `DIRECT_MESSAGE`. Payload: `conversationId`, `userId`, `cleanContent`, `messageId`. Header: `X-Xyne-Signature` (HMAC of raw body) |
| 3 | pesu | Verify HMAC (constant-time) → **200 immediately** → work async (XS does not retry) |
| 4 | pesu → XS | optional `user/info` to resolve display name; cache |
| 5 | pesu → padi | `lifecycle.create({ cwd? })` → `{ id: terminalId }` |
| 6 | padi → kaval | spawn PTY (shell) |
| 7 | pesu → padi | `lifecycle.sendInput({ id, data: "<agent argv>\\r" })` — same initial-command path as `padi-tui create -- claude …` |
| 8 | pesu → padi | `lifecycle.sendInput({ id, data: "<user text>\\r" })` — first agent prompt |
| 9 | pesu | persist bind `conversationId → { terminalId, authorUserId }` |
| 10 | pesu → XS | `postMessage` into `conversationId`: ack + deep link to open that terminal in kolu |

Agent is unaware of chat. It only sees PTY input.

## Interaction: later user messages

| Step | From → to | What moves |
| --- | --- | --- |
| 1 | XS → pesu | same webhook shape |
| 2 | pesu | lookup bind by `conversationId`; reject if author ≠ stored |
| 3 | pesu → padi | `lifecycle.sendInput({ id: terminalId, data: "<text>\\r" })` |
| 4 | kaval | write bytes into that PTY (last-writer-wins at kaval) |

No second terminal. No coordinator hop. Thread is the mailbox for one PTY.

## Interaction: agent → conversation (transcript stream)

Return half — **CT1 is the wire for this.** Today: loaders + `transcript.exportHtml`
(procedure). Missing: a live surface stream of chat-filtered events.

| Step | Component | What |
| --- | --- | --- |
| A | agent CLI | appends to vendor session store (Claude JSONL, Codex/OpenCode SQLite, …) |
| B | padi | loaders → IR; filter to chat (`user` / `assistant` — same cut as HTML chat-log mode) |
| C | **`streams.transcriptChat`** | input `{ id }`; first yield = full chat snapshot; later = deltas (new messages or growing assistant text) |
| D | CH1 / PE1 | UI paints bubbles; pesu `postMessage` / `updateMessage` into the XS thread |

Reconnect: client re-subscribes → fresh snapshot replaces stale state (surface
stream invariant). No poll loop as the design.

## What each API is (and is not)

### Xyne Spaces → pesu (webhook)

| Event | When |
| --- | --- |
| `APP_MENTIONED` | explicit @bot in a channel |
| `DIRECT_MESSAGE` | every message in the bot DM |

Plain channel messages without @ are **not** delivered to installed apps.
pesu answers 200 first; failures after that are pesu's problem (post a visible
error into the thread).

### pesu → Xyne Spaces (app API, bearer JWT)

| Call | Use |
| --- | --- |
| `POST …/chat/postMessage` | new bot turn (or first ack) |
| `POST …/chat/updateMessage` | grow one message while an assistant turn streams |
| `POST …/chat/agentProgress` | optional typing indicator during a turn |
| `GET …/user/info` | resolve sender id → name |

### pesu / kolu → padi (`padiSurface`)

| Member | Kind | Use |
| --- | --- | --- |
| `lifecycle.create` | procedure | new terminal (optional `cwd`) |
| `lifecycle.sendInput` | procedure | agent launch line + every user message |
| **`transcriptChat`** (name TBD) | **stream** | chat-filtered frames for one terminal — CT1 |
| `transcript.exportHtml` | procedure | unchanged export path; not the live face |

pesu does **not** call kaval directly. padi owns the terminal id space and
awareness; kaval is an implementation detail behind `lifecycle.*`.

### Out of scope for this wire

- Fleet board / who-needs-me in chat  
- Coordinator multi-worker campaigns  
- Routing chat traffic through kolu-server for pesu  
- Bot secrets in the web UI  

## pesu internal shape

```
packages/pesu/
  bin.ts          # listen + dial padi + load binds
  webhook.ts      # HMAC verify, parse, 200, enqueue
  xyneApi.ts      # postMessage · updateMessage · user/info
  binds.ts        # threadId → terminalId (+ author)
  turns.ts        # create-on-miss · author gate · sendInput
  mirror.ts       # subscribe transcriptChat → postMessage
  config.ts       # XS base URL, secrets via env, agent argv, cwd, allowlist
```

Same layering idea as `padi-tui`: thin composition over existing padi surface
members; no second terminal protocol.

## Build order — not pesu first

Full pesu needs XS credentials, webhooks, and a public URL. The **interesting
half of the product** does not: a conversation face on one terminal over the
**transcript stream** + `sendInput`. That is useful in kolu alone — and it is
what `/bridge` does by hand via MCP (`sendInput`, wait for agent state, read
output), but as a real UI instead of a skill loop.

| Do first | Why |
| --- | --- |
| **CT1 + CH1** | Ship the live message pipe as a kolu feature; no XS |
| **PE0** | Chat can create/drive a terminal from XS (half duplex still useful) |
| **PE1** | Same stream, second consumer (post into XS) |

Not in this tree: multi-agent campaign board / bridge dashboard as product UI
— that is a different note ([campaign surface](campaign-surface.html)). Here
we only productize the **1:1 conversation** that pesu will also use.

### CT1 — `streams.transcriptChat`

<Phase id="CT1" name="padi surface stream: chat-filtered transcript frames" status="next" />

**Today:** `procedures.transcript.exportHtml` — one-shot HTML. Loaders already
produce a vendor-neutral IR.

**Ship:** a new **`streams`** member on `padiSurface` (name TBD; call it
`transcriptChat` here):

```
input:  { id: terminalId }
output: chat-filtered frames
        // prefer explicit snapshot | delta (attach-style),
        // or full message list each frame (activity-style)
```

- Filter = HTML **chat log** mode: `user` + `assistant` only (no tools, edits,
  reasoning dumps).
- **Snapshot-then-deltas** so reconnect replaces state; never deltas-only.
- Forwarding policy: **`delta`** (fail-through).
- Implement by watching the same session files sensors already touch; re-run
  (or incremental) loaders; emit when chat-visible text changes.

`exportHtml` stays as the export procedure. A dump procedure is optional and
is **not** CT1.

**Done when:** a Solid consumer and a raw dial client can both subscribe to
one terminal's chat frames live, and a reconnect delivers a coherent snapshot.

### CH1 — conversation in the right panel (Inspector)

<Phase id="CH1" name="live chat log in the Inspector next to Compose" status="todo" needs={["CT1"]} />

#### What kolu is today (do not invent chrome)

Real shell, as shipped:

- **Canvas tile** = the PTY (title bar + xterm). Agent TUI, tools, raw output
  live **here** — always.
- **Right panel** tabs = **Inspector | Code** only
  (`RightPanelTabKind`, `data-testid="right-panel-tab-*"`).
- **Inspector** already has **Compose** (`ComposeSection`): mono draft box,
  **Send →**, copy *“Inserts into the terminal — press Enter there to submit”*.
  Then Directory / Git / Agent / Attach sections (`Section` + uppercase labels).

CH1 does **not** put Terminal|Chat on the tile. The tile stays a terminal.

#### What you get (prototype)

One new **Conversation** section **above Compose** in the same Inspector —
live chat-filtered transcript for *this* terminal. Compose stays the write
path; the tile still shows the agent working with tools.

| You do (today’s chrome) | What happens after CH1 |
| --- | --- |
| Open right panel → **Inspector** | Same tab bar as now |
| Scroll **Conversation** | Human / AI messages from CT1 — no tool_call noise |
| **Compose** + **Send →** (⌘↵) | Same control as today: `sendInput` into the tile’s PTY |
| Watch the **tile** | Agent TUI / tools still there when you want depth |

#### Open product call (Compose)

Compose today **inserts, does not submit** (see `composeSend` / docs). Chat
users often expect Send = full turn. Decide in CH1:

- keep insert (honest with current Compose), or  
- optional “submit” (trailing Enter) for conversation mode only — must not
  break the paste-race rule Compose exists for.

#### Not this

| Already in kolu | CH1 |
| --- | --- |
| Compose alone | write without a live read of the conversation |
| Export HTML chat log | offline snapshot, not live in the panel |
| Fake “Chat tab on the tile” | **not** kolu — rejected |

#### Under the chrome

Conversation body ← `streams.transcriptChat` (CT1). Compose → existing
`lifecycle.sendInput`. Placement = `MetadataInspector` section, not new
tile modes.

**Done when:** with Inspector open you can follow the conversation without
export or reading tool spam in the panel, while the tile remains the real
PTY; reconnect does not double-paint messages.

## Done criterion (full tree)

DM the bot → terminal under padi/kaval → first prompt is yours → assistant

live in kolu's chat face over **one** padi stream → deep link opens that
terminal.
