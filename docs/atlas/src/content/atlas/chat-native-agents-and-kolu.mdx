**One conversation ↔ one kolu terminal.** User text → terminal input; agent
**messages** (not tools/edits) → conversation. The chat surface can be the
**kolu UI** first, then **Xyne Spaces via pesu** — same pipe, different face.

pesu is the XS bridge only; config is env/systemd next to pesu, not the web app.

## Components

Three processes on the chat side of the wall; four on the machine side. The
browser PWA is **not** on the critical path — same class of client as
`padi-tui` / `kolu mcp`.

| Component | Process | Job in this design |
| --- | --- | --- |
| **Xyne Spaces** | XS cloud | Threads, identity, @mention/DM delivery, message store |
| **XS apps platform** | part of XS | Signed **webhook** out; **app API** in (`postMessage`, `updateMessage`, `user/info`) |
| **pesu** | new daemon beside kolu (`packages/pesu`) | HTTP webhook receiver + bind store + padi client + XS API client |
| **padi** | workspace daemon | `padiSurface`: `lifecycle.*`, loaders, **new chat transcript stream** |
| **kaval** | PTY daemon under padi | Owns the live PTY; serializes writes |
| **agent CLI** | child in the PTY | claude / codex / opencode / grok — writes its own session files |
| **transcript loaders** | in-process in padi today | Vendor file → `transcript-core` IR (`user` · `assistant` · `tool_*` · …) |
| **kolu PWA** | browser | Tile = PTY; CH1 = Conversation in Inspector; deep link |

```
Xyne Spaces ──HTTPS──► pesu ──unix socket──► padi ──unix socket──► kaval ──PTY──► agent
     ▲                   │                      │
     │                   │                      └── loaders ← session files on disk
     └──── HTTPS API ────┘                      └── streams.transcriptChat → chat frames
```

pesu dials padi with the same kit as other non-browser faces
(`@kolu/padi/dial` → digest-keyed socket, control-core handshake, contract
skew fail-fast). It does **not** go through kolu-server.

## Surface primitives (why CT1 is a stream)

`padiSurface` is declared with the five `@kolu/surface` member kinds. The live
conversation path has to pick one deliberately — a one-shot is not a stream.

| Primitive | Shape | Fit for chat log? |
| --- | --- | --- |
| **`streams`** | input → async iterator; reconnect re-subscribes via `STREAM_RETRY` | **Yes — CT1.** Per-terminal `{ id }`, **forward-only** chat deltas (optional cheap live/cursor hello — **not** history snapshot) |
| **`procedures`** | request → one response | One-shot only. Today's `transcript.exportHtml`. Fine for export/dump; live only if a consumer polls+diffs — not the product path |
| **`events`** | discrete fires | No backlog on subscribe — wrong for conversation history |
| **`cells`** | standing single value | Not per-terminal append-heavy log |
| **`collections`** | keyed set + deltas | `terminals` is already the entity set; the message list is not a second keyspace |

**Client consume:**

- Kolu UI (CT1+CH1, one PR): `client.streams.transcriptChat.use(() => ({ id: focusedTerminal() }))` — enrolled by default; **append deltas only** (empty after hard reload).
- pesu (PE1): same stream; track a post **cursor**, not full session RAM.

**Re-serve forwarding:** **`delta`** (fail-through) — same class as `activity` / `terminalAttach`.

**Rejected alternatives (recorded):**

- Procedure-first + poll — not live.
- Full message list every stream frame — re-bloats every yield.
- **History snapshot on subscribe/hard reload** — slow on long LLM sessions; use export for the past.
- Cell of “last assistant text” — loses multi-bubble turns.
- Event of “assistant said X” — no backlog on subscribe.
- Unbounded Solid store of all chat events ever received in a multi-day open tab.

## Bind state (pesu-local)

pesu holds the only new durable fact:

```
threadId  →  { terminalId, authorUserId, hostKey? }
```

- **Create on miss** — first webhook for an unbound thread runs
  `lifecycle.create` (+ agent launch), then stores the row.
- **Author gate** — later webhooks must match `authorUserId` (v1: one
  allowlisted operator). Mismatch → visible decline via `postMessage`, never
  silence, never `sendInput`.
- Not in kolu's conf store; not in XS. Survives pesu restart if persisted
  next to pesu (file/env scope TBD; start with on-disk JSON beside the daemon).

## Interaction: first message

End-to-end create + first prompt.

| Step | From → to | What moves |
| --- | --- | --- |
| 1 | User → XS | DM or `@bot` text in a channel |
| 2 | XS → pesu | `POST` webhook: `APP_MENTIONED` or `DIRECT_MESSAGE`. Payload: `conversationId`, `userId`, `cleanContent`, `messageId`. Header: `X-Xyne-Signature` (HMAC of raw body) |
| 3 | pesu | Verify HMAC (constant-time) → **200 immediately** → work async (XS does not retry) |
| 4 | pesu → XS | optional `user/info` to resolve display name; cache |
| 5 | pesu → padi | `lifecycle.create({ cwd? })` → `{ id: terminalId }` |
| 6 | padi → kaval | spawn PTY (shell) |
| 7 | pesu → padi | `lifecycle.sendInput({ id, data: "<agent argv>\\r" })` — same initial-command path as `padi-tui create -- claude …` |
| 8 | pesu → padi | `lifecycle.sendInput({ id, data: "<user text>\\r" })` — first agent prompt |
| 9 | pesu | persist bind `conversationId → { terminalId, authorUserId }` |
| 10 | pesu → XS | `postMessage` into `conversationId`: ack + deep link to open that terminal in kolu |

Agent is unaware of chat. It only sees PTY input.

## Interaction: later user messages

| Step | From → to | What moves |
| --- | --- | --- |
| 1 | XS → pesu | same webhook shape |
| 2 | pesu | lookup bind by `conversationId`; reject if author ≠ stored |
| 3 | pesu → padi | `lifecycle.sendInput({ id: terminalId, data: "<text>\\r" })` |
| 4 | kaval | write bytes into that PTY (last-writer-wins at kaval) |

No second terminal. No coordinator hop. Thread is the mailbox for one PTY.

## Interaction: agent → conversation (transcript stream)

Return half — **CT1 is the wire for this.** Today: loaders + `transcript.exportHtml`
(procedure). Missing: a live surface stream of chat-filtered events.

| Step | Component | What |
| --- | --- | --- |
| A | agent CLI | appends to vendor session store (Claude JSONL, Codex/OpenCode SQLite, …) |
| B | padi | loaders → IR; filter to chat (`user` / `assistant` — same cut as HTML chat-log mode) |
| C | **`streams.transcriptChat`** | input `{ id, after? }`; **forward-only** chat deltas from current offset / cursor |
| D | CT1+CH1 / PE1 | Inspector appends live; pesu posts with a cursor |

Hard reload / re-subscribe: **no history snapshot** — continue from last
offset (or empty until next message). Full past → export.

## What each API is (and is not)

### Xyne Spaces → pesu (webhook)

| Event | When |
| --- | --- |
| `APP_MENTIONED` | explicit @bot in a channel |
| `DIRECT_MESSAGE` | every message in the bot DM |

Plain channel messages without @ are **not** delivered to installed apps.
pesu answers 200 first; failures after that are pesu's problem (post a visible
error into the thread).

### pesu → Xyne Spaces (app API, bearer JWT)

| Call | Use |
| --- | --- |
| `POST …/chat/postMessage` | new bot turn (or first ack) |
| `POST …/chat/updateMessage` | grow one message while an assistant turn streams |
| `POST …/chat/agentProgress` | optional typing indicator during a turn |
| `GET …/user/info` | resolve sender id → name |

### pesu / kolu → padi (`padiSurface`)

| Member | Kind | Use |
| --- | --- | --- |
| `lifecycle.create` | procedure | new terminal (optional `cwd`) |
| `lifecycle.sendInput` | procedure | agent launch line + every user message |
| **`transcriptChat`** (name TBD) | **stream** | chat-filtered frames for one terminal — CT1 |
| `transcript.exportHtml` | procedure | unchanged export path; not the live face |

pesu does **not** call kaval directly. padi owns the terminal id space and
awareness; kaval is an implementation detail behind `lifecycle.*`.

### Out of scope for this wire

- Fleet board / who-needs-me in chat  
- Coordinator multi-worker campaigns  
- Routing chat traffic through kolu-server for pesu  
- Bot secrets in the web UI  

## pesu internal shape

```
packages/pesu/
  bin.ts          # listen + dial padi + load binds
  webhook.ts      # HMAC verify, parse, 200, enqueue
  xyneApi.ts      # postMessage · updateMessage · user/info
  binds.ts        # threadId → terminalId (+ author)
  turns.ts        # create-on-miss · author gate · sendInput
  mirror.ts       # subscribe transcriptChat → postMessage
  config.ts       # XS base URL, secrets via env, agent argv, cwd, allowlist
```

Same layering idea as `padi-tui`: thin composition over existing padi surface
members; no second terminal protocol.

## Build order — not pesu first

Full pesu needs XS credentials, webhooks, and a public URL. The **interesting
half of the product** does not: live conversation in the Inspector over a
**transcript stream** + `sendInput`. That is useful in kolu alone.

| Do first | Why |
| --- | --- |
| **CT1+CH1** (one PR) | Live **read-only chat log** in Inspector (same filter as export); **forward-only** stream |
| **PE0** | Chat can create/drive a terminal from XS (half duplex still useful) |
| **PE1** | Same stream, second consumer (post into XS) |

Not in this tree: multi-agent campaign board / bridge dashboard as product UI
— that is a different note ([campaign surface](campaign-surface.html)). Here
we only productize the **1:1 conversation** that pesu will also use.

### CT1+CH1 — one PR: live read-only chat log

<Phase id="CT1+CH1" name="streams.transcriptChat + read-only Conversation in Inspector" status="next" />

**One PR.** Product first: the **same thing as Export → Chat log**, but live in
the Inspector — human + AI messages only, **read-only**. Not a second agent
UI, not a write path redesign.

Compose already exists above/below it and stays as-is (insert, not submit).
No “chat Send = submit” decision in this PR.

#### What the user gets

You already have an agent in a tile. Open the right panel → **Inspector**.
Above Compose, a **Conversation** section shows the session as a chat log —
exactly the cut export’s chat mode uses. As the agent works, the log follows
the live edge (forward-only). Tools and edits stay on the **tile** PTY and out
of this list.

| --- | --- |
| See the conversation without export or tool spam | Changing Compose submit semantics |

| Same mental model as chat-log export | Multi-worker / bridge board |

Write-from-chat (submit-on-send, etc.) can come later once the read path is
honest. Compose remains available for insert as today.

#### Wire (CT1) — live forward only, no history snapshot

**Today:** loaders → IR; `transcript.exportHtml` with `mode: "chat"` is the
offline document of the same filter (full session, O(S) — on demand only).

**Ship:** `streams.transcriptChat` on `padiSurface` as a **live feed of new
chat events**, not a history API:

```
input:  { id: terminalId, after?: Cursor }   // optional resume cursor
output: chat-filtered events (deltas)         // no full-session payload
```

- Filter = **chat log** IR: `user` + `assistant` only (same definition as
  export chat mode — one source of truth).
- **No heavy snapshot** of the last *N* messages (and never the whole session)
  on subscribe or hard reload. That path re-reads/parses long JSONL/SQLite and
  is exactly what we refuse for multi-hour agents.
- **Continue from last message:** the stream only emits **new** chat-visible
  events after the current file/DB offset (or after `after` if supplied). A
  hard reload **does not** rehydrate history into the panel.
- Open Conversation after reload → **empty** until the next human/AI message.
  Full history stays **Export → Chat log**.
- Forwarding: **`delta`** (fail-through). Mid-chain drop terminates the
  stream; client re-subscribes and resumes from **last seen cursor** (or from
  "now" if none) — still no history dump.
- Surface reconnect discipline: first frame may be a **cheap hello**
  (`{ kind: "live", cursor }`) or empty ack — **not** a bounded transcript
  window rebuild. Do not cargo-cult attach-style "first frame = full
  scrollback."

`exportHtml` remains the path for offline full history. The live panel is a
**ticker**, not a browser for the archive.

#### Hard reload (browser tab)

A hard reload kills **only the browser face**. Daemons and agents keep running
— same stack story as the rest of kolu.

| Layer | On hard reload |
| --- | --- |
| **kaval PTYs** | Still alive — agents keep working |
| **padi** | Registry, awareness, session files on disk unchanged |
| **kolu-server** | Still up; browser opens a **new** websocket |
| **Client RAM** | Gone — Solid stores, open streams, Conversation buffer |
| **Compose draft** | Survives — per-terminal `localStorage` (today) |
| **Canvas / session** | Restored from padi/server session when the client reconnects |
| **Conversation (CT1+CH1)** | Starts **empty**; re-subscribe is **forward-only** — no history snapshot |
| **Full past** | Still on disk → **Export → Chat log** (or the live PTY tile) |

Boot after reload: re-dial → re-subscribe surfaces → re-attach PTYs (PTY
snapshot is fine — that path already exists). Conversation does **not** use
the PTY-attach pattern of “first frame = full scrollback.” It only appends
**new** chat events from the current offset. Empty until the next human/AI
message is correct, not a bug.

What does **not** happen: agents killed, transcripts wiped, full-session
re-parse into the panel, or needing pesu for recovery.

#### Memory: only what arrived this UI session

| Rule | Detail |
| --- | --- |
| **Append-only while open** | Client keeps messages received **since this subscribe** (optionally a small ring if the open tab runs for hours) |
| **Hard reload** | Client RAM gone → Conversation starts **empty**; stream resumes **forward only** — no snapshot catch-up |
| **Virtualized list** | Only near-viewport rows mount DOM for whatever is in the buffer |
| **Stick to bottom** | Follow live edge when at bottom |
| **Export stays separate** | Want the past → HTML chat log export, not the live panel |

#### Backend cost (why CT1 must not re-export)

Grounded in what padi already does — implementers must not invent a "poll
exportHtml" stream **or** a "snapshot last N chat messages on subscribe."

| Path today | Work per fire | Role |
| --- | --- | --- |
| **Export loaders** (`loadClaudeCodeTranscript`, Codex rollout, Grok JSONL) | `readFileSync` **whole** file → parse **all** lines → full IR | **O(S)** in session file bytes *S* — end-of-session / on-demand only |
| **OpenCode loader** | SQL over the session DB | **O(M)** in messages — still full session, not live |
| **Session watcher** (dock agent state) | `subscribeFileAppends` + **256 KB tail** (`TAIL_BYTES`) + **150 ms debounce** | **O(1)** amortized in *S* for *state* — not chat text |

Claude's watcher comment is load-bearing: without debounce, token streaming
fires the handler dozens–hundreds of times per second, each allocating a large
tail buffer. Export is deliberately not that path.

**Naïve stream (forbidden):** on every debounced append **or on every
subscribe/reload**, call the full export loader (or rebuild last *N* chat
messages by scanning *S*).

| | Complexity |
| --- | --- |
| Per update while the agent streams (full re-export) | **O(S)** CPU + peak memory |
| Over a session of size *S* with *U* updates | **O(U · S)** → ~**O(S²)** when *U* tracks *S* |
| Snapshot history on hard reload | **O(S)** or **O(scan)** — rejected; long LLM sessions make this the pain |

**Sound stream (required):** same *shape* as the session watcher, not the
export loader — **forward-only**.

| Step | Cost |
| --- | --- |
| Detect append | **O(1)** — existing append subscribe / poll floor |
| Debounce | ~150 ms (same idea as watcher) |
| Read **new bytes only** from last file offset (or new SQLite rows by id) | **O(Δ)** |
| Parse new lines / map to chat filter | **O(events in Δ)** — chat rows are sparse vs tools |
| Emit delta(s) | **O(chat bytes out)** |
| Subscribe / hard reload | **O(1)** — open at current end (or resume `after` cursor); **no** history materialization |

Steady state (one agent streaming, one subscriber): **O(Δ) per debounced tick**.
Lifetime of processed file: **O(S)** once as the session grows (each byte
forward once). Reload does **not** re-walk *S*.

| Extra factor | Rule |
| --- | --- |
| **Subscribers *N*** | One shared per-terminal producer + fan-out (**O(Δ)** once, cheap emit × *N*). Never *N* full reloads. |
| **Terminals *T*** | Chat reducer is **subscribe-driven** — only open Inspector / pesu mirrors pay. |
| **Wire** | Deltas only (plus optional tiny live/cursor hello). Never full list / never "last *N* messages" dump. |

**Bottom line for implementers:** streaming is fine if CT1 is built like the
**session watcher** (append + debounce + incremental, **continue from last
offset**). It is **not** fine if it is **`exportHtml` on a timer** or
**snapshot history on reconnect**. Hard reload = empty panel + forward feed;
archive = export.

#### Done when (this one PR)

- Focused terminal's **new** chat messages are **readable live** in Inspector
  (human + AI only).
- Same filter semantics as export chat log (one definition).
- **Hard reload does not snapshot history** — panel restarts empty (or
  cursor-resume only); full past stays export.
- Backend: **incremental O(Δ)** per tick; subscribe/reload **O(1)** w.r.t. *S*.
- Tile stays the PTY; Compose behavior unchanged.

#### Prior art — PR #1810 (do not merge; port the leaf)

An earlier draft PR — [#1810](https://github.com/juspay/kolu/pull/1810)
(`pesu-b0`) — implemented the **old** B0: one XS thread bound to an **existing
coordinator** (resolve terminal **by title**), FIFO write floor, attributed
paste drive loop, growing reply via loaders + `updateMessage`. That product
shape is **superseded** by this note (thread ↔ **one new terminal**,
create-on-miss; CT1+CH1 first). **Do not merge #1810 onto master.** Open a
**new** PE0 PR and **port** what still applies.

| Port into PE0 (XS leaf) | Why it still fits |
| --- | --- |
| `webhook.ts` + HMAC tests | Same XS events (`APP_MENTIONED` / `DIRECT_MESSAGE`); constant-time verify; 200-then-async |
| `xyneApi.ts` + fake XS tests | `postMessage` / `updateMessage` / `user/info` (and later PE1/PE2) |
| `config.ts` fail-fast env | Crashes if secrets / base URL / allowlist absent — no defaults |
| `log.ts` (pino + Hono access log) | Always-on visibility; secrets never logged |
| Author allowlist + visible decline | Same single-operator v1 gate (never silence) |
| `nix run .#pesu` packaging | Deploy shell for the daemon |

| Leave behind (wrong model) | Why |
| --- | --- |
| `coordinator.ts` — title lookup + drive loop | PE0 does **not** bind a pre-existing coordinator; it **creates** a terminal |
| “One thread → the campaign orchestrator” | One thread → one agent terminal; no multi-worker door |
| FIFO inbox as the product | Optional later if concurrent webhooks hurt; not the core bind |
| Growing-reply as B0’s main outbound | Outbound is **PE1** (`transcriptChat` → post); PE0 is inbound + ack |
| Atlas B0 text / roadmap on that branch | This note is the plan of record |

**Implement PE0 as:** webhook → author gate → bind miss ⇒ `lifecycle.create` +
agent launch + store `conversationId → { terminalId, authorUserId }` →
`sendInput` user text → ack `postMessage` (+ deep link). Dial padi like
`padi-tui` (`@kolu/padi/dial`), not kolu-server. Cherry-pick or copy the
salvage rows above; rewrite binds/turns for create-on-miss.
