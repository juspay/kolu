**pesu stands alone; kolu stands beside it.** DM the bot in Xyne Spaces and a
single daemon does the whole loop: verified webhook in, an
[ACP](https://agentclientprotocol.com) `session/prompt` to a headless agent it spawns as its own child over stdio,
the reply posted back to the thread. No proxy process, no socket, no tile in
the runtime path — the shape [buzz](https://github.com/block/buzz) runs in
production.<Footnote>Grounded 2026-07-25 by reading the buzz source, not its
docs: `buzz-acp` is simultaneously chat consumer, ACP client, process
supervisor, and session pool; it owns each adapter's stdin/stdout directly
(`crates/buzz-acp/src/acp.rs`) and re-serves ACP on nothing — its observer
module advertises publishing telemetry "without exposing a local HTTP port"
(`crates/buzz-acp/src/observer.rs`).</Footnote>

One choice is central and distinguishing: **pesu is git-first.** Every
conversation lives under a git repo — always — and the repo is the bot's
memory: a knowledge base the conversation draws on as context, and grows
only through commits you authorize from the thread. Coding is the natural
extension of that, not the founding case, because software projects are
already git repos.

What kolu contributes is deliberately *outside* that loop: **the takeover.**
The agent's work is real files in a real git worktree, and its conversation
is an ordinary session in the CLI's own store — so when chat stops being
enough, you open a kolu terminal in that worktree, run
`claude --resume <session-id>`, and you are inside the bot's own
conversation: interactive, full history, all its file state around you. pesu
does not depend on kolu; kolu completes it.

## The shape — one daemon, Buzz-grounded

| Component | Process | Job |
| --- | --- | --- |
| **Xyne Spaces** | XS cloud | Threads, identity, @mention/DM webhooks, flow cards |
| **pesu** | standalone daemon (`packages/pesu`) | Chat-frontend plugin (XS first) + author gate + binds; embedded ACP client + adapter supervision; per-thread worktrees |
| **ACP adapter** | child of pesu | The headless agent behind standard ACP — [`claude-agent-acp`](https://www.npmjs.com/package/@agentclientprotocol/claude-agent-acp), [`codex-acp`](https://www.npmjs.com/package/@agentclientprotocol/codex-acp); any stdio ACP agent works |
| **kolu** | separate product, same box | The takeover surface — not in the runtime path at all |

**Xyne Spaces is the first chat frontend, not the design.** The chat side of
pesu is one thin seam — deliver an inbound message; post, update, and
progress a reply — and XS is its first plugin. A Discord-shaped second
frontend is architecturally possible from the get-go, because everything
past that seam (worktrees, the ACP client, supervision, the takeover ack)
never sees XS. One frontend ships in v1; the seam is the commitment, not a
second integration.

ACP is still the only protocol on the wire — NDJSON JSON-RPC over the child's
stdio, exactly as the spec ships it — and driving the agent through it
deletes the whole observation problem the PTY path had: no bracketed-paste
races, no screen-settle detection, no turn-end heuristics. `session/prompt`
returns when the turn ends, and everything in between is a typed
frame.<Footnote>Buzz's production scar tissue stays our checklist: some
agents keep streaming after `session/cancel`, so cancel gets a grace window
then a respawn; an in-flight permission request must be answered `cancelled`
before cancelling the turn or the agent deadlocks; the adapter is spawned as
a process-group leader and killed as a group so its tool children are reaped.
Buzz's numbers for the same choices: five-second cancel grace, respawn
backoff 1s→30s with jitter, a 3-crashes-in-60s circuit breaker
(`crates/buzz-acp/src/lib.rs`, `pool.rs`).</Footnote>

Session visibility is a log, and is priced like one: pesu appends every ACP
frame to a per-session log file beside its bind state. The thread is the
product view; the log file is the gore view for debugging. There is no
viewer process, because a viewer is not worth a process.<Footnote>An earlier
revision of this note ran the adapter behind an `acp-proxy` in a kolu tile —
"chat threads as terminals" — with the tile as the observability story. It
shipped as <PrLink pr={1985} />, then was closed unmerged: with a headless
adapter the tile can never be more than a read-only rendering of the same
`session/update` stream pesu already consumes — a log viewer — and a log
file is the same thing at a fraction of the machinery. (Buzz reached the
same verdict from the other direction: rather than any local viewer it
encrypts frames onto its own relay and renders them in its chat app — the
chat surface is the viewer, which for us is the XS thread itself.) The
supervision core and the real-process test harness built in #1985 port into
pesu as part of PS1; the socket shape may yet return as the remote-host arm
when remote boxes arrive — a distant-future item, not designed here.</Footnote>

Where this deliberately differs from buzz, recorded so the choices are
conscious: buzz pools adapter processes and multiplexes sessions across them
with *preferred, not absolute* affinity — a busy pool can silently start a
fresh session for a channel, forking its history
(`crates/buzz-acp/src/pool.rs`) — and its replies are not the turn's output
at all: the model is instructed to post by running a `buzz messages send`
CLI. pesu keeps one adapter process per thread and posts the turn's own
result; both simplifications fall out of not pooling.

## Git-first — the repo is the memory

**Every pesu conversation lives under a git repo. There is no repo-less
mode.** A thread that names no repo binds the configured default; the repo
is not a feature pesu offers but the ground it stands on, and it is the
identity choice that distinguishes pesu from other chat-agent systems: the
repo is the bot's **memory** — precisely, a **knowledge base, never a
transcript**. Conversations themselves are not committed; they *draw on*
the repo as context, and what a thread concludes can *grow* it — markdown
notes for a discussion, code for a task — only when the user authorizes the
change, right from the thread. Knowledge accumulates as history you can
diff, grep, review, and clone, and the next conversation over the same repo
starts from everything already committed.<Footnote>Contrast the systems around it: Claude Tag's agent state
lives in a cloud sandbox you don't own; buzz's durable trace is events on
its relay. pesu's durable state is a git repo on your machine — the same
artifact your team already knows how to share, review, and back
up.</Footnote>

This is pesu's answer to the **agent memory problem**: not a vendor's opaque
memory feature, but plain files under version control — greppable,
reviewable, model-agnostic, owned. And knowledge **stacks**: a conversation
may refer to several repos — `work off srid/my-notebook + team-docs` — the
first named is the workspace, where commits land; the rest are checked out
read-only beside it as context layers.

<PsNotebookMock />

A discussion thread is the plainest case: `@kolu work off srid/my-notebook —
explain to @john why foo beats qux, based on context X`. The agent argues
from the repo's notes; when someone says "record that", it commits the
conclusion back as markdown — humans talk, humans approve, the repo
remembers. **Coding is the natural extension, not a separate mode**: software projects are already git repos, so "fix the flaky
e2e suite" is just another repo-bound thread whose commits happen to be
code. Repo selection is deliberately dumb: the first message may name one
or more aliases from pesu's configured allowlist (exact token match, no
parsing cleverness); no match means the configured default repo.

## The takeover — what kolu distinctly adds

The handoff medium is the filesystem plus the session store — no protocol,
no export step, no transcript plumbing:

- **Every thread binds to a git worktree.** The agent's tools act on real
  files; its work is diffable, testable, committable the moment it lands.
- **The conversation is an ordinary CLI session.** `claude-agent-acp` is
  built on the same engine as the
  [`claude` CLI](https://claude.com/claude-code), writes a standard JSONL
  transcript into `~/.claude/projects/`, and implements ACP `session/load`
  by passing the ACP session id straight into the engine's `resume` — the
  ACP session id *is* the CLI session id.<Footnote>Facts from the shipped
  adapter and this dev box, 2026-07-25: `claude-agent-acp` depends on
  [`@anthropic-ai/claude-agent-sdk`](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk)
  (it even resolves the bundled `claude` binary at startup), and its `session/load`/`resumeSession` pass
  `params.sessionId` as the SDK's `resume` option (`dist/acp-agent.js`). The
  #1985 smoke sessions sit in `~/.claude/projects/…-packages-acp/*.jsonl` as
  ordinary Claude Code transcripts. `codex-acp` structurally matches: it
  advertises `loadSession: true` and maps the ACP session id onto Codex's
  native `threadId` — the id `codex resume` takes — read from its shipped
  bundle but not yet exercised end-to-end, so PS1 proves it once before the
  ack claims it for codex threads.</Footnote>
- **So the takeover is two commands, not a feature:** open a terminal in the
  worktree; `claude --resume <session-id>`. pesu's ack posts both, verbatim.

## Decisions

| Decision | Choice |
| --- | --- |
| Library | TypeScript, [`@agentclientprotocol/sdk`](https://www.npmjs.com/package/@agentclientprotocol/sdk) on its current `agent()`/`client()` model — the deprecated connection classes from the #1985 branch never reach master (supersedes #1989) |
| Package boundary | **None in v1 — KISS.** The ACP client and supervision are pesu modules, ported with their tests from the closed #1985 branch; extract a package only when a second consumer actually exists |
| Adapter | pesu config — **any stdio ACP agent**; day one `claude-agent-acp` and `codex-acp`, pinned as npm deps (no global installs) |
| Workspace | **every thread binds a repo — no repo-less mode.** A per-thread git worktree, cut from a repo on pesu's env-configured allowlist (`alias → path`); the first message may name allowlisted aliases verbatim; no match → default repo |
| Knowledge stack | a conversation may name **several** repos — the first is the workspace, where commits land; the rest are checked out read-only beside it as context layers |
| Memory | **the repo is the memory — a knowledge base, never a transcript.** Conversations are not committed; they draw on the repo as context, and grow it only through user-authorized commits (markdown or code) proposed from the thread. pesu itself persists nothing but the bind file |
| Bind state | `threadId → { cwd, acpSessionId, authorUserId, agent }`, JSON file beside pesu |
| Session visibility | every ACP frame appended to a per-session log file beside the bind state; no viewer process |
| Takeover ack | the ack carries the worktree path, the session id, and the exact `claude --resume` line |
| Permissions | **Auto-approved, documented.** pesu always answers `session/request_permission` with the `allow_once` option, and the bot's docs state so plainly; interactive approve-from-thread is a *Later* item, gated on verifying XS flow cards can deliver an app's button callbacks at all |
| Reply shape | Post once, then `updateMessage` ≤1/s as the growing reply; split at XS's 40,000-char cap<Footnote>The XS app API has no delta primitive: `updateMessage` is a full-body replace, and `agentProgress` is ephemeral — a Redis-backed working/done pill with a one-line `toolLabel`, never persisted. The ≤1/s cadence is manners, not a platform limit.</Footnote> |

### PS1 — the XS round trip + the takeover ack

<Phase id="PS1" name="webhook → worktree → prompt → reply · ack carries the resume line" status="next" />

The user-facing feature is the whole loop: DM the bot, watch the reply land,
own the takeover line. Under it rides the one internal port: the supervision
core from the closed <PrLink pr={1985} /> branch — process-group spawn and
kill, paced respawn, graced cancel, bounded handshake — plus its
fake-adapter fixtures and real-process vitest suite, moved into pesu as
modules and rebuilt on the SDK's `agent()`/`client()` handler model, so the
deprecated connection classes and their `biome.jsonc` suppression never
reach master. The four lifetime bugs review caught on that branch are pinned
by those tests; that insurance is the most valuable artifact it produced.
`acp-proxy`, `acp-chat`, the unix socket, and the PTY rendering are not
ported.

pesu: signed webhook (`APP_MENTIONED` / `DIRECT_MESSAGE`) → allowlist gate →
bind the thread → cut the worktree → spawn the adapter →
`session/prompt` → post the reply. The XS leaf — `webhook.ts` + HMAC tests,
`xyneApi.ts` + fake-XS tests, fail-fast env config, logging, allowlist,
`nix run .#pesu` — ports from <PrLink pr={1810} />.

The ack is where the takeover lands: worktree path, session id, and the
literal `claude --resume <id>` line. For codex threads the ack includes a
resume line only after the `threadId` mapping is verified against the real
`codex` CLI once (see the takeover footnote) — an unverified resume line is
worse than none.

The thread's ceremony-free home is a **DM** (every message is delivered); in
a channel each message must @mention the app — the apps platform has no
follow-the-thread.<Footnote>Follow-the-thread exists only in XS's separate
bot-catalog system, not for installed apps. Two recorded options if the
per-message @mention grates: an XS-side feature request, or a pesu-side
poller over one dedicated channel's `channelHistory` — not built until
wanted.</Footnote> pesu answers the webhook 200 immediately and works async
— delivery is fire-and-forget, so a slow handler loses events. Deployment
shape: systemd user service on `127.0.0.1`, fronted by **Tailscale Funnel**
for the stable public webhook URL; secrets reach it **only as environment
variables** — never the repo, logs, or an agent transcript.

<Ps1Mock />

**Test flows (this PR):**

1. DM the bot a question — the ack arrives with the worktree path and resume
   line; the reply lands in the thread.
2. Send a follow-up in the same DM — **no new session**; the same
   conversation answers with the earlier context.
3. Run the ack's `claude --resume` line in a terminal in that worktree — the
   bot's conversation opens interactively with full history (captured once
   as PR evidence).
4. Have someone not on the allowlist DM the bot — one-line decline; nothing
   spawned.
5. `curl` the webhook with a bad `X-Xyne-Signature` — rejected, nothing
   posted, nothing created (pinned by a test).
6. In a channel, `@kolu <ask>` works; a plain message in the same thread
   without the @mention does nothing (the documented apps-platform gap).
7. Ask for something gated — the run proceeds without pausing
   (auto-approved `allow_once`), exactly as the bot's docs say it will.
8. Start a thread over a notes repo, stacking a second repo — the reply
   argues from both; on your go-ahead in the thread, the conclusion lands
   as a markdown commit in the workspace (the git-first loop, end to end).

**Done when:** DM → worktree exists → reply lands; a second message
continues the same session; the ack's resume line provably opens the same
conversation; a forged signature is rejected; a non-operator gets a visible
decline, never silence; the ported supervision suite is green inside pesu
(crash → respawn → next prompt works; hang → cancel → grace → respawn;
parameterized by adapter argv with the deliberately different second vendor
retained) with zero deprecated SDK imports and zero lint suppressions for
them.

### PS2 — turn polish

<Phase id="PS2" name="growing reply · tool labels · resume across restart" status="todo" needs={["PS1"]} />

The growing reply (`updateMessage` ≤1/s, cap-aware split); `tool_call`
frames → `agentProgress` labels while the turn runs; `session/load` on pesu
restart, so the daemon holds no conversation state beyond its bind
file.<Footnote>Both pinned adapters advertise `loadSession`; resume replays
the session's history as the same `session/update` stream, so pesu's cursor
logic needs no special path. For an adapter that doesn't advertise it, pesu
starts a fresh session and says so in the thread — visibly, never
silently.</Footnote>

**Test flows (this PR):**

1. A long task — **one** message grows in place instead of a stream of
   separate messages.
2. The progress pill changes labels as the agent moves between tools; it
   clears when the turn ends.
3. `systemctl --user restart pesu` mid-conversation, then send the next DM —
   the conversation continues with prior context; no earlier reply is
   double-posted.
4. Provoke a reply longer than 40,000 chars — it splits into consecutive
   messages instead of failing.

**Done when:** restart pesu mid-conversation; the next DM continues the same
conversation with prior context, without double-posting earlier replies.

**Later, on demand (small bounded additions, not phases):**
**approve from the thread** — a `session/request_permission` becoming a
button card in the thread is designed only after verifying the XS apps
platform can deliver an app's button callbacks at all (unconfirmed today;
until then documented auto-approve is the contract, and a cancel must
resolve any pending request as `cancelled` first — the buzz deadlock
lesson); a **second chat frontend** (Discord-shaped) behind the same seam;
per-thread agent selection UX (the wire already takes any adapter);
**[goose](https://goose-docs.ai/) as an optional agent** — one config entry,
no code.<Footnote>Recorded 2026-07-25 from the adapter and goose sources:
goose's native ACP is strongest on session persistence and cancellable
permission requests — advantages that become observable only once
resume-across-restart (PS2) and approve-from-thread land — and wins
decisively on provider breadth (15+ API/cloud/local model providers), at
the cost of one more runtime between the thread and the model when a
claude/codex subscription is already the target.</Footnote>

## Background

**Why chat at all.** Anthropic shipped [Claude Tag](https://www.anthropic.com/news/introducing-claude-tag)
— one shared Claude per channel, pursuing tasks "over hours or days" — and
[Karpathy called the shape](https://x.com/karpathy/status/2069547676849557725)
"the 3rd major redesign of LLM UIUX": the agent as a persistent coworker
that lives where the team already works.<Footnote>The proof-point Anthropic
leads with is blunt: *"65% of our product team's code is created by our
internal version."* The human's job shifts from driving keystrokes to
managing agents.</Footnote> Buzz is the same thesis as a product — chat
where agents are coworkers in channels — and XS-plus-pesu is that exact
shape on infrastructure you own.

**What the moat actually is.** The properties that distinguish this from
Claude Tag — the shell and files real, the host yours, the model swappable
(the adapter is config) — are properties of *self-hosting pesu*, and they
hold with no kolu anywhere in sight.<Footnote>Marc Andreessen, [on what
agent research converged on](https://www.youtube.com/watch?v=knx2wrILP1M):
*"an agent is … a language model, and above that a bash shell … and then a
file system, and the state is stored in files"* — and *"your agent is now
actually independent of the model … you can swap out a different LLM
underneath."* That is this architecture, line for line.</Footnote> kolu's
distinct contribution is the takeover: because the agent's state is files in
a worktree and a session in the CLI's own store, the product where you
already live in terminals is one `cd` and one `--resume` from continuing the
bot's work by hand. Chat owns the breadth; kolu owns the moment delegation
stops being enough.

### The XS apps platform, as grounded

The contract PS1 builds against — read from the xyne-spaces source
(2026-07-13), not its docs, because XS has **three separate integration
systems** that are easy to conflate: the *bot catalog* (backend-native
bots), *incoming webhooks* (URL-embedded-secret message drops), and the
**apps platform** — installed apps with a webhook URL, a bearer token, and a
signing secret. pesu is an installed app; only the third system applies.

| Event | Fires when |
| --- | --- |
| `APP_MENTIONED` | the app is explicitly @mentioned in a channel — carries `conversationId` (thread), `channelId`, `messageId`, sender `userId`, body as HTML + plain text, attachments |
| `DIRECT_MESSAGE` | *every* message in a 1:1 DM with the app (same shape, no `senderName`) |
| `USER_MENTIONED` | a human is @mentioned where the app is present — observer signal |

**Auth, both directions, one secret.** Deliveries carry `X-Xyne-Signature` —
HMAC-SHA256 of the raw body with the app's signing secret; no timestamp or
replay scheme, so verification is a constant-time compare and replay is an
accepted, recorded risk. The bearer token is a JWT signed HS256 *with that
same secret*, no expiry — it lives until regenerated.

**The app API** (`/api/apps`, bearer): `chat/postMessage` (text, markdown,
or structured content; `conversationId` targets a thread) ·
`chat/updateMessage` · `chat/agentProgress` · `chat/channelHistory` /
`chat/conversationReplies` (catch-up after downtime) · `channel/openDm` ·
`user/info`.<Footnote>No webhook payload carries a sender email (the DM
payload omits even the display name) — pesu resolves people through
`user/info` and caches them. Event delivery is fire-and-forget with no
retries: a delivery missed while pesu is down is lost; the read APIs
recover.</Footnote>

## Out of scope

- **Remote boxes — in scope for the product, distant future for this
  plan.** Everything here is one machine: pesu, the adapters, the worktrees,
  and kolu side by side. When multi-host arrives, the remote arm may well
  turn out to be a proxy-shaped process re-serving ACP from the far host —
  noted so the option isn't forgotten, deferred so it isn't designed
  prematurely.
- **kolu changes** — none at all: no new session kind, no dock/awareness
  work, no viewer. The takeover uses plain terminals kolu already has.
- **PTY-agent observation** — session watchers and every interactive tile a
  human drives stay exactly as they are.
- **Bot secrets in a web UI** — pesu config is env/systemd beside the
  daemon.

## Done criterion (full tree)

DM the bot → a headless session answers from a per-thread worktree → the
reply grows in place → restart pesu and the thread resumes → and at any
point, open a terminal in that worktree, run the ack's `claude --resume`
line, and continue the bot's own conversation by hand.
