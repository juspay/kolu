## The shift: the agent moved into the chat

Karpathy isn't describing a chatbot you ask questions. He's describing a coworker:
a persistent agent that lives where the team already works, holds the org's tools
and context, and runs tasks on its own while you do something else. You @-tag it,
walk away, and it pings you when it needs you. Anthropic shipped this shape as Claude
Tag — one shared Claude per channel, tasks it pursues "over hours or days," an audit
log of every task and who asked for it. The proof-point is blunt: *"65% of our product
team's code is created by our internal version."* The work moves into chat, and the
human's job shifts from driving keystrokes to managing agents.

In that world the terminal specializes. Chat keeps gaining
richer rendering — diffs, highlighting, even little editors — but it stays async text
over request and response. It is not a live process you can step into. The terminal is
where you drop to a shell, answer an interactive prompt, watch raw output, drive a
debugger. Chat owns the breadth; the terminal owns the depth — and kolu is what makes
the depth real.

## kolu in one picture

At its core kolu does two things: it **runs real terminals on computers you
control, and watches what's happening inside them.** That core is three parts:

- **kaval** owns each live terminal — start an agent, type into it, resize it, kill it.
  It is also the single point that *serializes* writes: when input arrives, last one wins.
- **padi** is the per-host workspace daemon above it: its agent sensors watch every
  terminal without touching it, folding the raw noise into a simple board — which agent
  is working, which is asking you something, which just finished — and it owns the
  durable session: what each terminal ran, the agent's resume identity, restore across
  restarts and even an unclean daemon death.
- **`@kolu/surface`** is the typed wire that carries both over any connection — a local
  socket, or ssh to another machine. Remote hosts are a shipped, first-class part of the
  app: add a host and its terminals sit behind a host switcher, on desktop and mobile.

<Svg svg={stack} caption="Not a rigid stack. XS is its own app and integrates kolu through one seam; kolu runs headlessly on whatever machine you point it at — your laptop, a server, or a remote sandbox. Chat, presence, and login stay in XS." />

Two things sit either side of kolu, and the relationship with each is different:

- **XS is independent.** It already runs without kolu. Integrating kolu is simply what
  lets a chat thread reach into a real terminal — XS gains the depth, kolu gains a front
  door. Everything social stays in XS.
- **The machine is wherever kolu runs.** kolu runs **headlessly on any box** — your laptop,
  a server, or a remote sandboxed host. Remote sandboxes (an Incus cluster, another team's
  project) are something it **naturally supports**: a remote host is just another place to
  dial the same surface.

So the picture is not a tower of dependencies. XS *integrates* kolu; kolu *runs on*
whatever machine you choose. The arrow is integration one way and execution the other.

## The moat: model-agnostic, open, yours

kolu and a chat app divide cleanly. kolu owns the live process, the files, and the
durable session. XS owns identity, login, presence, and who-may-write. A foundation that
reaches up and grows chat stops being a neutral base *any* chat app can integrate and
becomes one more single-vendor app. Holding that line isn't caution — it's the moat.

<Callout kind="accent" title="The moat — our competitive advantage">
**kolu runs claude, codex, or opencode under any chat app, on infrastructure you control.**
That is the bet on open standards and open source, and it is exactly what a single-vendor
stack can't match. Claude Tag is one vendor's model, with the shell and files hidden inside
a cloud sandbox you don't own. kolu keeps the model **swappable**, the shell and files
**real**, and the host **yours** — so the chat app on top is a choice, never a lock-in.
</Callout>

<Callout kind="accent" title="What an agent actually is (Andreessen)">
Marc Andreessen, [on what decades of agent research quietly converged on](https://www.youtube.com/watch?v=knx2wrILP1M):
*"an agent is … a language model, and above that a bash shell … and then a file
system, and the state is stored in files,"* plus cron — and *"every part of that
other than the model is something we already completely know."* The kicker:
*"your agent is now actually independent of the model … you can swap out a different
LLM underneath."*

That is kolu's architecture, line for line: the **shell** is the interface to every
tool (kolu *watches* it, doesn't wrap it), the **files** are the durable state, and
the **model is the swappable chip** (claude · codex · opencode). A chat app that
hard-codes one vendor's model and hides the shell and files inside a cloud sandbox
gives up exactly the durable substance kolu keeps.
</Callout>

## The seam: observe out raw, act through the coordinator

XS integrates kolu through one seam with two deliberately asymmetric halves: **observe
flows out raw; act flows in through one door — the coordinator.** kolu authenticates
nothing: the connection *is* the trust — an owner-only socket locally, an ssh link to a
remote host — so identity, login, and presence stay in XS.

The **coordinator** is an orchestrator agent running in an ordinary kolu terminal — the
same shape kolu's own development runs on: one agent that provisions worker terminals,
dispatches briefs, answers the workers' questions, and verifies their claims at the tree.
Its behavioral contract is the `/orchestrator` skill: rulings run through the review
lenses with named grounding, teardown kills only recorded PIDs, the human merges every
PR. The chat bot is a **mirror of that coordinator**: it binds one thread to that one
terminal, renders the coordinator's reports into the thread, and relays the thread's
messages back in — attributed per XS identity — using the same drive loop the coordinator
itself uses on workers.

<Svg svg={bridge} caption="The seam. OBSERVE (green) flows out raw and read-only — the board straight off padi. ACT (blue) flows in through one door: the coordinator, an orchestrator agent in an ordinary kolu terminal, which drives the workers with the fleet loop. Chat never writes to a worker terminal." />

| Surface | Half | Reuses |
| --- | --- | --- |
| the board | out · read-only | padi's agent sensors — which agent is working / asking you / just finished (`padi-tui wait`'s buckets), rendered into the thread on demand with no coordinator hop |
| attention | out · read-only | per-terminal urgency through the notify seam — the bot pings the thread instead of the desktop<Footnote>Unprompted posts ride the installed app's own API: POST /api/apps/chat/postMessage with a conversationId targets a thread, authenticated by the app's bearer token — the same call pesu answers messages with, so pinging needs no extra machinery.</Footnote> |
| deep links | out | a kolu URL to the exact terminal — depth on demand: step in, answer the interactive prompt, debug, in kolu itself |
| the coordinator bridge | in + out | one terminal's screen and input — send a message, wait for the turn to end, read the reply: the identical agent-drives-agent loop kolu already ships |

Chat gets **no raw act verbs on workers** — that absence is the design, not a gap:

- **The write floor dissolves.** "At most one writer per terminal" machinery exists only
  if chat can touch live terminals. With one door, the floor is the coordinator's inbox:
  thread messages queue into a conversation and are handled in turn, attributed.
  Serialization by conversation, not by locks.
- **Guarantees live at the knowing endpoint.** The coordinator is the one place that
  knows campaign state — what is in flight, which merge goes first, what a change must
  not break — so "who does what next" is decided there, never in a thread reacting to a
  screen.
- **Discipline is inherited, not re-implemented.** Everything the orchestrator contract
  enforces — claims verified at the tree, grounded rulings, no pattern kills, the human
  merging — applies to chat traffic automatically, because chat traffic *is* coordinator
  traffic.

### The same door assists the humans' own discussion

Because a message to the thread and a message to the coordinator are the same thing,
the coordinator is also a **participant in the conversation between humans** — the
teammate shape, not just command-and-control. Several people argue a design in the
thread; the coordinator contributes exactly what its contract makes it good at: the
claim checked against the actual tree before anyone builds on it, the ruling with its
grounding named so the humans can audit the reasoning rather than defer to it, and the
running record of what was decided and why. AI-assisted discussion among humans falls
out of the coordinator pattern for free — no second bot, no separate "assistant" mode,
one attributed inbox.

## The XS apps platform, as grounded

The contract pesu builds against — read from the xyne-spaces source (2026-07-13), not
its docs, because XS has **three separate integration systems** that are easy to
conflate: the *bot catalog* (backend-native bots, its own mention/thread semantics),
*incoming webhooks* (URL-embedded-secret message drops), and the **apps platform** —
installed apps with a webhook URL, a JWT token, and a signing secret. pesu is an
installed app; only this third system applies.

**What an installed app is.** Its own per-workspace user (name and avatar from the app
record), addressable by @mention, DM-able. Created from the dashboard; the webhook URL,
bearer token, and signing secret are per-install credentials.

**Events — XS → the app's webhook URL.** One POST per event,
`{eventType, payload, timestamp}`, fired on exactly three chat triggers:

| Event | Fires when | Payload notes |
| --- | --- | --- |
| `APP_MENTIONED` | the app is explicitly @mentioned in a channel | `conversationId` (thread), `channelId`, `messageId`, sender `userId` + `senderName`, body as `content` (HTML) + `cleanContent` (text), attachments |
| `DIRECT_MESSAGE` | *every* message in a 1:1 DM with the app | same shape but **no `senderName`** |
| `USER_MENTIONED` | a human is @mentioned in a channel the app is in | observer signal; adds `mentionedUserIds` |

Plain, unmentioned channel messages are **never delivered** — there is no
follow-the-thread for apps (that behavior lives in the bot catalog only). No payload
carries a sender email; `GET /api/apps/user/info` resolves it.

**Authentication, both directions, one secret.** Deliveries carry `X-Xyne-Signature` —
HMAC-SHA256 (hex) of the raw JSON body with the app's signing secret; there is no
timestamp or replay scheme, so verification is a constant-time HMAC compare and replay
is an accepted, recorded risk. The bearer token is a JWT signed HS256 *with that same
secret*, payload `{appId, userId}`, no expiry — it lives until regenerated.

**The app API — the app → XS, `Authorization: Bearer`.** All under `/api/apps`:

- `POST chat/postMessage` — text, markdown, or structured content; target by
  `channelId`/`channelName`, or by `conversationId` to reply **into a thread**; posts
  as the app's user.
- `POST chat/updateMessage` — edit a posted message in place (the growing-reply UX).
- `POST chat/agentProgress` — an ephemeral typing/progress indicator.
- `GET chat/channelHistory` · `GET chat/conversationReplies` — read back (catch-up
  after downtime).
- `POST channel/openDm` — open a DM with a user; `GET user/info` — id → name/email.

**Operational facts.** Message content caps at 40,000 characters. Event delivery is
fire-and-forget: no retries, failures logged server-side only — an app that was down
missed those events (the read APIs recover). No effective rate limit is configured on
the app API routes; cadence discipline (e.g. ≤1 `updateMessage`/s) is the app's own
manners.

## The first proof: pesu, in the kolu tree

pesu integrates through XS's **apps platform** — the shape the installed "kolu" app
already has: XS pushes **signed events** to a webhook URL pesu serves, and pesu talks
back through XS's **app API** with a bearer token. pesu itself is a small daemon in the
kolu source tree (`packages/pesu` — an app-tier sibling of kolu-server: it imports
kolu's packages, nothing imports it), running beside kolu on the machine you own. Both
directions below are grounded in the XS source.

- **In — events, signed.** XS POSTs `{eventType, payload, timestamp}` to pesu's URL on
  exactly three chat triggers: `APP_MENTIONED` (an explicit @kolu in a channel),
  `DIRECT_MESSAGE` (every message in a 1:1 DM with the app), and `USER_MENTIONED`
  (observer). The payload carries the thread id (`conversationId`), the channel, the
  sender's user id, and the message body as both HTML and plain text. Every delivery is
  authenticated by `X-Xyne-Signature` — HMAC-SHA256 of the raw body with the app's
  signing secret — which pesu verifies with a constant-time compare before touching the
  payload.<Footnote>Three facts to design around, from the XS source: the payload never
  includes the sender's email (and the DM payload omits even the display name) — pesu
  resolves people through `GET /api/apps/user/info` and caches them; delivery is
  fire-and-forget with no retries, so pesu answers 200 immediately and works async, and
  a delivery missed while pesu is down is lost (the read APIs — `channelHistory`,
  `conversationReplies` — allow catch-up); and there is no replay protection on the
  signature, an accepted risk recorded here.</Footnote>
- **Out — the app API, one bearer token.** `POST /api/apps/chat/postMessage` posts to a
  channel or — with `conversationId` — into a thread; `updateMessage` edits a message
  in place; `agentProgress` shows a live typing indicator; `channelHistory` /
  `conversationReplies` read back. This one API is *both halves of the mirror*: the
  reply to a message and the unprompted post are the same call — **B2 ships no wire B0
  doesn't already have**; it is a policy switch (relay the coordinator's
  between-message turns), not new machinery.

**The one honest UX gap, stated:** the apps platform delivers a channel message only on
an explicit @mention — the follow-the-thread behavior (replying in a bot's thread
without re-mentioning) exists only in XS's separate bot-catalog system, not for
installed apps. So B0's conversational home is the **DM**, where every message flows
both ways with no ceremony, and in channels each instruction @mentions kolu. Two
recorded options if thread-follow comes to matter: an XS-side feature request (the
right fix), or a pesu-side poller over `conversationReplies` for its bound threads (a
workaround with a polling cost — not built until wanted).

**Does the coordinator get chat verbs of its own?** No — the coordinator stays
chat-unaware, which keeps the mirror agent-CLI-agnostic and the bridge passive.
Structured output doesn't need coordinator agency either: `postMessage` takes plain
text, markdown, and structured payloads, so rendering is pesu's concern. An MCP face
(pesu's verbs as a `@kolu/surface`, re-exposed via `@kolu/surface-mcp`) stays a
recorded option whose sole revival condition is a coordinator demonstrably needing to
*initiate* a chat action the transcript mirror cannot express.

Each phase is **one PR, end to end** — it ships nothing that isn't consumed within it
(the padi plan's law, held here). Every PR below is a complete, usable product on its
own.

### B0 — the round trip

<Phase id="B0" name="the bridge daemon — a chat-driven coordinator over the installed app" status="next" />

**What you see:** DM the kolu app and you are talking to the coordinator — every
message you send lands in its terminal prefixed with your name; its answer appears as
one message that grows while it works, with a typing indicator during the turn. In a
channel, **"@kolu ‹ask›"** does the same into the message's thread. Several people can
take part; each message is attributed and handled in arrival order.

**The turn, end to end:** verify `X-Xyne-Signature` (constant-time) → 200 immediately →
enqueue on the FIFO inbox (the write floor — one turn in flight, ever) → resolve the
coordinator terminal **by title** via the kaval client (ids re-key across kaval
restarts; titles survive) → resolve the sender via `user/info` (cached) → attributed
two-step write-in, snapshot-verified → `agentProgress` on → as the reply grows in the
coordinator's transcript, read it through the **shipped loaders**
(`kolu-claude-code` / `kolu-codex` / `kolu-grok` / `kolu-opencode`, dispatched on the
agent kind padi publishes — the same dispatch `padi/transcript.ts` does, so B0 is
model-agnostic on day one) → `postMessage` once, then `updateMessage` at a civil cadence
so the thread shows one growing message → the turn-end bucket flips → final update,
typing off. A fault posts as a visible reply — never silence. Replies split at XS's
40,000-character message cap.

**The code tree** (no transcript module — the loaders already exist):

```
packages/pesu/src/
  bin.ts            # entry: config → webhook server + turn engine
  config.ts         # XS base URL · listen port · coordinator title ·
                    #   env NAMES for the signing secret + bearer token
  webhook.ts        # the receiver: HMAC verify, event parse, immediate 200
  xyneApi.ts        # the bearer client: postMessage · updateMessage ·
                    #   agentProgress · user/info (+ user cache)
  inbox.ts          # the FIFO turn queue — the write floor
  coordinator.ts    # terminal-by-title · attributed write-in · turn-end via
                    #   padi's buckets · reply text via the loaders
  attribution.ts    # "from Sridhar: " prefix formatting
```

**Hard requirements, in the PR:** a **stable public URL** for the webhook (a named
tunnel or funnel — quick-tunnels rotate their hostname per run and silently orphan the
registration); secrets reach pesu **only as environment variables** — never the repo,
the PR, logs, or an agent transcript; a forged-signature request is rejected (pinned by
a test); a coordinator-busy message queues and answers in order.

### B2 — the live mirror

<Phase id="B2" name="unprompted posts over the same app API — the thread becomes the campaign feed" status="todo" needs={["B0"]} />

**What you see:** the thread updates **on its own**. A worker finishes and the
coordinator's report appears; a ruling goes out and you read it as it happens; an agent
needs a human and the thread gets pinged — each post carrying a link that opens the
exact terminal in kolu when you want the depth. Mechanically this is B0's `postMessage`
with a `conversationId` and the transcript relay switched on for between-message turns —
no new wire, which is why it is the roadmap's smallest PR.

The discussion-assist patterns — the coordinator contributing grounded answers to a
debate between humans — are coordinator behavior, the `/orchestrator` skill's
territory, and deliberately not a pesu PR.
