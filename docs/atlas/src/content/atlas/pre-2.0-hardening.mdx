### PR #1911 — the review verdict (2026-07-21)

An adversarial review (11 hunters over the real diff — /perfection-review +
/architecture-first-principles C1–C7 — every finding re-verified by a refuter)
says: **the lock is good; half the PR isn't the lock.**<Footnote>The lock core
survived every attack: fail-closed marker read (empty/corrupt/EACCES all
refuse), symlink-safe root identity down to the deepest existing ancestor,
guard-before-logger so a refused launch can't even create a log dir in
production's root, the `--stdio` front guarded before any spawn.</Footnote>

- **~52% of the 1,483 added lines serve the lock.** The rest is role markers
  **nothing reads** — their only reader, the adopt/kill guard, was rejected out
  of the PR to <Issue n={1912} /> — plus ~370 lines in kaval closing a
  gate-leak window the PR itself opens to order that unread write. Lock 1
  needs **zero kaval changes**.
- **Both ssh e2e lanes are broken by the PR, invisibly** — CI has no
  ssh.<Footnote>`remotePadiSsh.test.ts` dials the remote `padi --stdio` with no
  `--role` and no `--state-root`, which the new guard now refuses before
  serving; `just e2e-ssh-2box` deliberately binds boxB's REAL default-root padi
  as a dev-role binder — now structurally refused.</Footnote>
- **The prose overclaims**: comments and README assert the adopt/kill guard
  exists ("can never adopt or SIGTERM") — it doesn't yet; only *binding* is
  refused.
- **One real treasure buried inside**: padi leaks its boot gate when startup
  throws — a genuine pre-existing bug whose fix deserves its own small PR.

**Open decision (srid):** close #1911 and rebuild lock-only — padi + server +
nix, ~half the size, review-recommended — or trim it in place on the existing
branch. Either way the ssh lanes and the overclaiming docs are fixed in the
same change, and the write-only role stamps ship with their reader in
<Issue n={1912} />.
