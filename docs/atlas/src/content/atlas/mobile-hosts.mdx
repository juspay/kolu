The multi-host engine is done and it does **not** care what layout it's in: the
keyed padi host map, W9 retained switching (a switch repaints instantly from a
kept surface), W10 persisted fleet (hosts survive a restart), and W5 per-host
attention all live below the UI. But the *only* face that engine has is
desktop. `ChromeBar` and its `HostSelectorStrip` are gated behind
`isDesktop()`, and the touch layout — the pull-down sheet in
<Cite file="packages/client/src/MobileChromeSheet.tsx" /> — renders **no host
chrome whatsoever**. So on a phone you cannot see which host you're on, switch
hosts, or add one. The capability exists; the surface doesn't.

This note proposes that surface: a **host row inside the mobile pull-down
sheet**. Everything below is mocked at phone width (≈390 px) so the design is
something to *look at*, not read. The one hard constraint threads every mockup —
the mobile chips are not a restyle.

<Callout kind="accent" title="Constraint — pixel-language identical to desktop">
A mobile host chip is the **same visual grammar** as the desktop tab, not a
lookalike. The connection **dot tone** comes from `hostChipTone.dotClass`
(green only for `connected`, amber warming, red failed), the **identity hue**
from `hostHue`, and the amber **attention pill** from `ATTENTION_PILL_CLASS`
(the `@kolu/solid-statepip` token shipped in <PrLink pr={1774} />, the Dock's
unread badge's own source). A green dot, an amber `2`, a violet chip must mean
the *same thing* on a phone as on a laptop. Divergence isn't a style choice —
it's a bug, because both surfaces read one token.
</Callout>

palette / settings / inspector cluster. Each host is a chip carrying the

identity-hue border when active, and the amber attention pill when that host
has agents awaiting you. A tap switches; the `+` adds.

### Tap a chip — the canvas re-hues, instantly

A tap is one call: `setActiveHost(host)`, the identical write the desktop strip
makes. Because of W9, the target host's surface is already retained, so the
canvas repaints from it with **no reload and no reconnect** — the per-host hue
wash on the canvas floor cross-fades to the new host, so switching *feels* like
moving rooms, not reloading a page.<Footnote>The switch is a synchronous signal
write — `setActiveHost(props.host)`, and `useEntry(activeHost)` re-keys the
per-host canvas. W9 (retained switching) means the surface for the target host
is kept warm, so the repaint is immediate rather than a fresh attach. The
mobile row calls the exact same function the desktop `HostSelectorStrip` does;
there is no mobile-specific switch path.</Footnote>

### Many hosts — the row scrolls sideways

When hosts outgrow the phone's width the row becomes **horizontally
scrollable** rather than wrapping or collapsing to a menu. A right-edge fade
signals more chips off-screen; the active chip is what you scroll back to. This
is the deliberately-simple mobile answer — desktop's `⋯ +N` overflow fold and
`sm..md` dropdown collapse are width-measurement machinery a thumb-scroll makes
unnecessary.<Footnote>Open design question, called out below: whether mobile
should instead borrow the desktop overflow model (`computeVisibleHosts` +
`HostOverflowMenu`). The prototype and these mockups assume the scroll-row; it's
the lighter build and reads naturally as a touch gesture, but it trades away the
"active chip always visible without scrolling" guarantee the desktop fold
keeps.</Footnote>

so at phone width it overflows the viewport and clips.** So this is presented as
two mockups — the honest current behaviour, and a proposed mobile-native
variant — for a design call.

## How it wires in

The whole point is that this is a **thin leaf**, not new machinery. `App.tsx`
already forks on `isDesktop()`; the desktop branch mounts `ChromeBar →
HostSelectorStrip`, and the touch branch mounts the pull-down sheet. This
proposal adds one component — `MobileHostRow` — to that sheet, and it reads the
**exact same seams** the desktop strip reads: `padiMap.entries` for the host
list, each entry's `cells.urgency` for the awaiting count, `hostChipTone`
(`dotClass` / `hostHue`) for tone and identity, `ATTENTION_PILL_CLASS` for the
pill, and `setActiveHost` for the switch.

<Svg svg={wiring} wide caption="isDesktop() forks App.tsx into two host surfaces. HostSelectorStrip (desktop) and the proposed MobileHostRow (mobile) are both thin leaves onto one layout-agnostic engine — the same reads (padiMap.entries, entry.cells.urgency), the same tokens (hostChipTone, ATTENTION_PILL_CLASS), the same write (setActiveHost). No new store, stream, or keybinding: the engine already streams host membership and urgency, and W9/W10 already own retained-switch and persistence." />

<Callout kind="note" title="No new electricity — this is not a receptacle">
By the electricity test, `MobileHostRow` hides no *hard* volatility of its own:
transport, reconnect, persistence, and retained-switch all live below it in the
host map and the `@kolu/surface-map` layer. It is a **presentation leaf** that
projects already-streamed state, the mobile twin of `HostSelectorStrip`. So it
belongs in the client's `host/` module beside its desktop sibling — **not** a new
`@kolu/*` package. The one shared thing worth watching is the vocabulary:
`hostChipTone` and `ATTENTION_PILL_CLASS` are the single source both leaves must
keep consuming, so the pixel-language constraint holds by construction rather
than by discipline.
</Callout>

## Implementation — one client-only PR

This is a single, client-only change threading existing seams — no server, no
protocol, no package. It reuses one already-exported affordance
(`AddHostAffordance`) and adds one component plus one mount line.

| Piece | What it is | Grounding |
| --- | --- | --- |
| `MobileHostRow.tsx` | New leaf: the chip row + add affordance, ~130 lines | reads `padiMap.entries`, `entry.cells.urgency`, calls `setActiveHost` |
| `MobileChromeSheet.tsx` | One import + one mount line, host row above the control cluster | <Cite file="packages/client/src/MobileChromeSheet.tsx" /> |

### Decisions to settle before building

Two forks change the build and are srid's call — they're deliberately left open
here because the whole note is a mockup to react to:

- **Add-host surface** — reuse the current anchored `AddHostAffordance` popover
  (cheapest; visibly cramped at phone width), or build the proposed in-sheet
  full-width variant (a little more work; the honest mobile answer). *Recommend
  the in-sheet variant.*
- **Overflow model** — the horizontally-scrolling row shown here (lighter,
  reads as a touch gesture), or port desktop's `⋯ +N` fold / dropdown collapse
  (keeps the active chip always visible without scrolling). *Recommend the
  scroll-row.*

One smaller choice is baked in as a default, not a question: the row lives at
the **top of the sheet**, above the palette/settings cluster, because host
identity is the most global thing in the sheet. Once srid reacts to these
mockups, a `/be` run implements the chosen variants from the parked head-start.
