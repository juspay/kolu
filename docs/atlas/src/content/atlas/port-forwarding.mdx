Agents constantly start dev servers, and the URL scrolls away into the
scrollback. This feature answers the one question kolu can't answer today —
**where is the thing the agent just ran?** — with exactly one concept:
listening TCP ports, attributed to their terminal, one click from your
browser.<Footnote>The inspiration, [kero.sh](https://kero.sh/), also shows a
process list with CPU% and memory. We drop processes from the plan entirely
(KISS): CPU% is the most expensive part to build for the least payoff, and a
name+pid list is decoration. The process-subtree walk survives only *inside*
the scanner, as the mechanism that attributes a port to a terminal.</Footnote>
It ships as a shared library — **`@kolu/port-forward`** — consumed by two
independent apps in the drishti mold: kolu's Inspector, and **vazhi** (Tamil:
*way, passage*), a standalone TUI in the spirit of opencode.

The plan is built for kolu's real deployment shape: the server runs on a
headless Linux box (*pureintent*) while the browser runs elsewhere (*zest*, a
macbook on the tailnet). Everything below follows from one fact: **"localhost"
in a link means the viewer's machine**, so the only universally reachable
place is the kolu server host — the name already in your address bar. Every
port is made to answer *there*, and the client builds URLs from
`window.location.hostname`, never a literal "localhost".

## How a click becomes a page — the three cases

| where the server listens | how it becomes reachable | what the chip opens |
| --- | --- | --- |
| kolu host, `127.0.0.1:5173` | TCP relay: listen on `0.0.0.0:61000`, pipe to loopback | `http://pureintent:61000` |
| remote host, `127.0.0.1:5173` | `ssh -L *:61000:127.0.0.1:5173` on the already-open master | `http://pureintent:61000` |
| kolu host, `0.0.0.0:5173` | already reachable — nothing to do | `http://pureintent:5173` |

In plain words: a dev server on pureintent's loopback is invisible to your
macbook (loopback never leaves a machine), so the library opens a door on
pureintent's network side and copies bytes across. A dev server on a *remote*
host is one hop further: the same door on pureintent, with the ssh connection
kolu already holds to that host carrying the last leg. And a server that
bound `0.0.0.0` on pureintent needs no door at all — the scanner records the
bind address, so kolu tells these cases apart
automatically.<Footnote>Sub-case of case 2: the remote host is the viewer's
own machine (zest as a kolu remote host, viewed from zest). Traffic loops
zest → pureintent → ssh → zest — roundabout but correct, and not worth a
special case in v1.</Footnote>

## One library, two apps — and no third daemon

kaval and padi remain **the only daemons**. The reusable capability is a
library package, `packages/port-forward/` (`@kolu/port-forward`): the forward
map (`(host, remotePort) → local listener`, N hosts × N ports), `ssh -O
forward` / `ssh -O cancel` against ControlMaster sockets, the loopback TCP
relay, free-port picking, and teardown. Its ssh side needs no connection
management of its own: `controlMaster.ts` computes the `ControlPath`
deterministically from the destination and `ControlMaster=auto` makes whoever
connects first the master — so any process using the same `controlOptPairs`
helper shares masters with kolu automatically. The ControlPath convention
*is* the integration, with zero coordination code.<Footnote>Forwards die with
their master connection, so a dropped host can never leak tunnels; the
library's cancel path handles the deliberate case.</Footnote>

Two consumers, no runtime link between them — the drishti pattern proper
(shared libraries, independent apps):

- **kolu** embeds the library in the server process it already runs. Forward state is a cell on kolu's **existing** surface — no new socket, no IPC, no supervision. Kolu's forwards live and die with kolu's server, which is correct: reachability was tied to that process anyway.
- **vazhi** is a standalone TUI (opencode-style — no CLI verbs, no serve mode) over the same library: a live table of its own forwards, add/cancel keybinds. Run it anywhere — including inside a kolu terminal, where kaval's persistence keeps it alive across browser reloads for free. Kolu never consults it; it exists to prove the library stands alone and to manage forwards when kolu isn't around. It gets its own `flake.nix` for later externalization into its own repo.<Footnote>Consequence of independence, stated: kolu and a running vazhi each own their *own* forwards and don't see each other's lists — they share ssh masters (via the ControlPath convention) but not state. Accepted for v1; a merged view would require the shared-daemon design this plan deliberately rejects.</Footnote>

<Callout>
**Security posture, stated:** a forward listener is unauthenticated raw TCP
on the kolu server's serving interface — anyone on the tailnet can connect,
the same exposure as running the dev server on `0.0.0.0` yourself. That is
the accepted v1 trust model (the tailnet is the trust boundary, as it already
is for kolu's own UI); per-forward auth would be a later, separate feature.
</Callout>

## Port links in the Inspector

<Mockup />

A **Ports** section joins the existing blocks in
`packages/client/src/right-panel/MetadataInspector.tsx` (pure rendering — the
data arrives on the terminal's metadata like everything else). The flows:

- **Open.** Click a chip → `window.open` on `http://${location.hostname}:…`, matching the Code tab's external-open idiom (`CodeTab.tsx:1114`). Case-3 ports open **directly**; cases 1–2 call the embedded library's `create`, get the listener port, open it, and the chip gains a `⇄ :61000` badge. Forwarding is **lazy — first click only**, never eager for every detected port.<Footnote>An agent session can hold six listening ports; auto-tunneling all of them VS-Code-style keeps idle listeners alive for ports nobody opens. Lazy costs one `ssh -O forward` round-trip (~ms on the multiplexed socket) on first click.</Footnote>
- **Manage.** A **Forwarded Ports** group lists every active kolu forward — `host:remotePort → :localPort`, origin `auto` (chip click) or `manual`, cancel `⨯` per row. Kolu auto-cancels an `auto` forward when the scanner sees its remote port die; `manual` forwards persist until cancelled or their host disconnects.
- **Manual forward.** The `＋ Forward a port…` row and a <Kbd keys="⌘+K" /> command accept `host:port` — for a port the scanner missed or one outside any terminal's subtree.
- **Discoverability.** One tip in `settings/tips.ts`: "Click a port in the Inspector to open the server an agent just started."

## Detection: ports, attributed to the terminal

Process facts belong to the PTY owner, so the scanner is a new module in kaval
— `packages/kaval/src/processScan.ts`, beside the existing foreground sampler
(`ptyHost.ts:620`). One host-wide pass every 5 seconds<Footnote>Cadence and
the unref'd, non-overlapping poll shape copy
`packages/padi/src/memorySampler.ts` and its `derived.cell(source({ read,
install: everyMsOr(…) }))` wiring in `servePadi.ts:247`.</Footnote> builds the
pid→ppid table once, partitions it into per-shell subtrees, and joins
listening TCP sockets against each subtree:

- **linux** — pid table from `/proc/*/stat`; LISTEN rows (with their **bind address**) from `/proc/net/tcp` + `tcp6`, joined to pids via `/proc/<pid>/fd` socket-inode readlinks — the same technique `surface-daemon-supervisor/src/socketHolder.ts:100` uses for unix sockets.
- **darwin** — `ps -axo pid,ppid,comm` for the table; `lsof -iTCP -sTCP:LISTEN -P -n -F pcn` for ports, under a hard `timeout` and SIGKILLed if wedged, as `socketHolder.ts:157` does. Both platforms gate CI; the darwin path is day-one work.

Each terminal's sample — `PortInfo { port, name, wildcard }` in
`packages/terminal-vocab/src/schema.ts`, beside `ForegroundSchema:145` — is
**deduped by structural equality** before publishing on the `ptyHostSurface`
contract, so an unchanged scan emits nothing: the churn guard that keeps a
5-second ticker from thrashing SolidJS. From there every layer exists: the
padi sensor set folds it into `TerminalSnapshot`, the surface serves it
(snapshot-then-deltas invariant, `.claude/rules/streaming.md`), and the
reconcile-backed store in `useTerminalMetadata.ts:180` delivers leaf-grained
ticks to the section.

<Callout>
**Architecture verdicts, conditioned on this build:** the *scanner* is a leaf
module inside kaval — a bounded one-shot scan with kaval as its only consumer
— and graduates only if it grows independent consumers or its own streaming
volatility. `@kolu/port-forward` is the opposite case: ssh connection/forward
lifecycle is a hard volatility with two genuinely independent apps on top
(kolu and vazhi), which is exactly why it is a *library* package — the
upstreamed "common stuff" of the drishti pattern — and why neither app is a
daemon the other must talk to.
</Callout>

## Build plan — the PRT track

| id | ships | needs | proof |
| --- | --- | --- | --- |
| PRT0 | `@kolu/port-forward` library + vazhi TUI (own flake.nix) | — | standalone forward on a real remote box, no kolu running |
| PRT1 | kaval scanner · Ports section · direct open | — | e2e: spawned listener's chip appears + opens |
| PRT2 | kolu embeds the library: lazy forward · Forwarded Ports UI · manual · auto-cancel | PRT0 + PRT1 | real remote box: chip → tunneled HTTP 200 via shared master |
| PRT3 | embedded in-kolu preview pane | PRT2 | deferred — not planned yet |

PRT0 and PRT1 are independent and can proceed in parallel; only PRT2 needs
both.

### PRT0 — the library, proven by vazhi (one PR)

`packages/port-forward/` plus the vazhi TUI with its own `flake.nix` (`nix
run .#vazhi`). **Done when**, with **no kolu running**: in a terminal, vazhi
adds a forward to a real remote box (pu harness) and shows the row live;
`curl http://<vazhi-host>:<port>` **from a different machine** returns the
remote server's body (proving the non-loopback bind); cancelling the row
severs it; quitting vazhi tears its forwards down. Two structural criteria on
top: vazhi imports **only `@kolu/port-forward`** (no kolu internals) — the
proof that makes PRT2's embed mechanical — and, with kolu's mirror connected
to the same host, vazhi's forward creates **no second ssh master** (assert
one master via `ssh -O check` + process count) — the criterion the
ControlPath-convention design exists to satisfy.

### PRT1 — detection + Ports section (one PR)

Scanner, `ports` schema field, sensor fold, the Inspector section, direct-open
chips, the tip. **Done when** an e2e scenario runs
`node -e 'require("http").createServer((_,r)=>r.end("ok")).listen(8123,"0.0.0.0")'`
in a real kolu terminal and asserts the `8123` chip appears within two scan
ticks and clicking it opens the page at `location.hostname:8123` — pinning the
real path (kaval scan → `ptyHostSurface` → padi snapshot → surface → reconcile
store), which no client-side mock can satisfy. Parser unit tests run on
fixture `/proc` trees *and* fixture `lsof -F pcn` output; the darwin gate
(`aarch64-darwin`) must be green, not skipped. Loopback-bound chips render
with a "needs a forward" affordance that activates in PRT2.

### PRT2 — kolu embeds the library (one PR)

The kolu server embeds `@kolu/port-forward`; forward state becomes a cell on
kolu's existing surface; chip click → lazy create; tunnel badges; Forwarded
Ports group; manual forward + ⌘K command; auto-cancel policy. **Done when**,
verified with the `remote-host-testing` harness against a real remote box
*and* a viewer on a different machine than the kolu server: clicking a remote
terminal's chip creates the forward **through the embedded library over the
shared ControlMaster socket** (a second ssh connection does not satisfy this;
a running vazhi is neither required nor consulted), the opened
`http://<kolu-host>:<localPort>` returns the remote server's body, cancelling
the row severs it, and stopping the remote server auto-cancels the `auto`
forward within two scan ticks. Evidence video of the click-to-page flow.

### PRT3 — embedded preview (deferred)

Open the forwarded page inside kolu — a browser pane in the Code tab, in the
spirit of the Codex desktop app — instead of a new tab. Explicitly out of
scope until PRT2 ships<Footnote>A cross-origin iframe surface for arbitrary
dev servers is a genuinely bigger build, and any server sending
`X-Frame-Options: DENY` / `frame-ancestors` refuses framing — the new-tab
path must remain the fallback regardless.</Footnote>; no design here yet —
when it matures this section is rewritten, not layered.
