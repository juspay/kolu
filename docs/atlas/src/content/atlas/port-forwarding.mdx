Agents constantly start dev servers, and the URL scrolls away into the
scrollback. This feature answers the one question kolu can't answer today —
**where is the thing the agent just ran?** — with exactly one concept:
listening TCP ports, attributed to their terminal, one click from your
browser.<Footnote>The inspiration, [kero.sh](https://kero.sh/), also shows a
process list with CPU% and memory. We drop processes from the plan entirely
(KISS): CPU% is the most expensive part to build for the least payoff, and a
name+pid list is decoration. The process-subtree walk survives only *inside*
the scanner, as the mechanism that attributes a port to a terminal.</Footnote>
It ships as a shared library — **`@kolu/port-forward`** — consumed by two
independent apps in the drishti mold: kolu's Inspector, and **vazhi** (Tamil:
*way, passage*), a standalone TUI in the spirit of opencode.

The plan is built for kolu's real deployment shape: the server runs on a
headless Linux box (*pureintent*) while the browser runs elsewhere (*zest*, a
macbook on the tailnet). Everything below follows from one fact: **"localhost"
in a link means the viewer's machine**, so the only universally reachable
place is the kolu server host — the name already in your address bar. Every
port is made to answer *there*, and the client builds URLs from
`window.location.hostname`, never a literal "localhost".

## How a click becomes a page — the three cases

| where the server listens | how it becomes reachable | what the chip opens |
| --- | --- | --- |
| kolu host, `127.0.0.1:5173` | TCP relay: listen on `0.0.0.0:61000`, pipe to loopback | `http://pureintent:61000` |
| remote host, `127.0.0.1:5173` | `ssh -L *:61000:127.0.0.1:5173` on a connection of its own | `http://pureintent:61000` |
| kolu host, `0.0.0.0:5173` | already reachable — nothing to do | `http://pureintent:5173` |

In plain words: a dev server on pureintent's loopback is invisible to your
macbook (loopback never leaves a machine), so the library opens a door on
pureintent's network side and copies bytes across. A dev server on a *remote*
host is one hop further: the same door on pureintent, with the ssh connection
kolu already holds to that host carrying the last leg. And a server that
bound `0.0.0.0` on pureintent needs no door at all — the scanner records the
bind address, so kolu tells these cases apart
automatically.<Footnote>Sub-case of case 2: the remote host is the viewer's
own machine (zest as a kolu remote host, viewed from zest). Traffic loops
zest → pureintent → ssh → zest — roundabout but correct, and not worth a
special case in v1.</Footnote>

## One library, two apps — and no third daemon

kaval and padi remain **the only daemons**. The reusable capability is a
library package, `packages/port-forward/` (`@kolu/port-forward`): the forward
map (`(host, remotePort) → local listener`, N hosts × N ports), one dedicated
`ssh -L` process per remote forward, the loopback TCP relay, port picking, and
teardown. For a remote target **the local port is the remote port whenever that
number is free here** — `pu-dev:4123` answers on `0.0.0.0:4123`, a port you can
predict and bookmark — and only when the number is taken does the kernel pick a free one
instead; a forward is never refused merely because its number is busy, and
there is no knob either way.<Footnote>Read the rule as remote-only: a
`local` (loopback-relay) target never gets the preference and cannot, because
both of its ends are on this machine — a listener on `0.0.0.0:<port>` relaying
to `127.0.0.1:<port>` is pointed at ITSELF, and one connection to it opened
~29,000 file descriptors in 1.5s before the build caught it. The kernel always
picks for a relay.</Footnote>

**A forward lives exactly as long as the process that opened it.** That is the
one property the mechanism is chosen for, and it is why each forward gets its
**own** ssh connection (`ControlPath=none`, so it can neither ride nor create a
shared master) rather than a listener on a master shared with kolu. Sharing was
the original design and it was wrong: OpenSSH gives a master's forwards a
lifetime of their own — a listener added with `-O forward` outlives its
requester until the master's `ControlPersist` idle timer reaps it, killing a mux
client does *not* take its forward down, and there is no `-O list`, so a
restarted process can neither see nor adopt what it left behind. An empty list
beside live ports is the worst possible pair, and it is what the shared design
actually produced.<Footnote>Both facts measured on a live sshd before the
rewrite: forwards survived their creator by the full ControlPersist window, and
a SIGKILLed mux client left its listener serving. Sharing a master and
kernel-tied lifetime are mutually exclusive in OpenSSH; lifetime wins.</Footnote>
The connection is held open by a remote command (`cat`) reading a pipe the
library never writes to, so the kernel closing that pipe — on quit, on crash, on
`kill -9` — ends the session and with it the listener, with no timer in the
loop.<Footnote>`-N` (no remote command) does NOT have this property: measured,
an `ssh -N -L` child SURVIVES its parent's SIGKILL and keeps serving the port.
The hold-open command is what makes the lifetime kernel-tied, and a library test
pins it — open a forward in a child process, SIGKILL it, require the port to
refuse.</Footnote> The costs, stated: one ssh handshake per forward instead of a
channel on a warm master, and a SIGKILL leaves the ssh children visible for as
long as it takes their connections to notice — they die with those connections,
they do not linger on a timer.

The per-forward connection also needs its own authentication, and that costs
nothing new: kolu's mirror already requires **non-interactive** ssh
(`BatchMode=yes` and the rest of `SSH_OPT_PAIRS`), so any host kolu can mirror
is a host a dedicated forward connection can reach with the same keys and the
same `~/.ssh/config`. `host` here is just an ssh destination — `user@box`, an
alias, whatever kolu's remote hosts already say — with no kolu-specific host
model inside the library. And the **`ForwardManager` API is the PRT2
contract**: `create` (idempotent by target) · `cancel` · `list` · `dispose` ·
`onLost` is exactly what kolu's Inspector will wire against, so the mechanism
could be replaced under it — as it just was — without either app noticing.
Mechanism in the library, policy in the consumers.<Footnote>**Two shape questions
PRT2 was to settle, and both settled as NO CHANGE — recorded because "we looked
and the second consumer wanted the same thing" is a different fact from "nobody
got round to it".** (1) `list()` stays pull-only. The prediction was that a second
consumer would want a subscription; kolu instead does exactly what vazhi does —
re-read the map after every act — and it does so because the surface CELL it feeds
is itself a re-read on a change edge. Two independent consumers converging on
pull is evidence the pull shape is right, not that the subscription is overdue.
(2) `create` still rejects with the mechanism's own message. The prediction was
that the Inspector would branch on a `kind` (retry, pick another port, mark the
host down); it branches on none of them, because the map ALREADY handles the only
recoverable case — a taken local port falls back to a free one inside
`openPreferringPort`, so it never reaches a consumer as an error. What is left is
genuinely terminal (no ssh, host unreachable, tunnel never came up) and its one
honest treatment is to show the user what happened. A tag with no reader would be
speculative structure.<br /><br />**One thing DID change**, and it went the other
way — into the library rather than into a consumer: a target that comes back gets
the local port it had before. That is what makes a link survive a dev-server
restart, and it belongs to the MAP because it is bookkeeping the map already
holds. Left to consumers, kolu and vazhi would each have kept the same table
beside the same map and got its eviction rules subtly different.</Footnote>

Two consumers, no runtime link between them — the drishti pattern proper
(shared libraries, independent apps):

- **kolu** embeds the library in the server process it already runs. Forward state is a cell on kolu's **existing** surface — no new socket, no IPC, no supervision. Kolu's forwards live and die with kolu's server, which is correct: reachability was tied to that process anyway.
- **vazhi** is a standalone TUI (opencode-style — no CLI verbs, no serve mode) over the same library: a live table of its own forwards, add/cancel keybinds. Run it anywhere — including inside a kolu terminal, where kaval's persistence keeps it alive across browser reloads for free. Kolu never consults it; it exists to prove the library stands alone and to manage forwards when kolu isn't around. It gets its own `flake.nix` for later externalization into its own repo.<Footnote>Consequence of independence, stated: kolu and a running vazhi each own their *own* forwards and don't see each other's lists — they share nothing at all — not state, and (since each forward owns its own ssh connection) not connections either. Accepted for v1; a merged view would require the shared-daemon design this plan deliberately rejects.</Footnote>

<Callout>
**Security posture, stated:** a forward listener is unauthenticated raw TCP
on the kolu server's serving interface — anyone on the tailnet can connect,
the same exposure as running the dev server on `0.0.0.0` yourself. That is
the accepted v1 trust model (the tailnet is the trust boundary, as it already
is for kolu's own UI); per-forward auth would be a later, separate feature.
</Callout>

## How the tunnel works, from zero

No new machinery, no daemon, nothing installed on either machine: a forward is
one ordinary `ssh` process — the same tool that logs you in — told to hold a
door open. Here is the actual command kolu runs, taken apart:

<Svg
  svg={sshAnatomy}
  caption="The command, dissected — and the numbered path a page request takes through it."
/>

A dev server bound to **loopback** answers only its own machine — `127.0.0.1`
and `::1` both just mean "this computer".<Footnote>Two spellings because there
are two loopbacks, IPv4's and IPv6's — and a server listening on one is NOT
reachable on the other, which is why the command dials the exact loopback the
scanner saw the server bind. Dialling the wrong one was a real shipped bug in
this very track.</Footnote> The tunnel lends that private server a public door:
`ssh` listens on the kolu host, and everything that knocks is carried — inside
the same encrypted connection ssh always uses — to the far machine, where
`sshd` knocks on the server's own loopback on your behalf. Your browser never
learns any of this happened; it just loads a URL on the kolu
host.<Footnote>The unlabelled flags in the real invocation are the mechanism
section's story in option form: `BatchMode` (keys only, never prompt),
`ExitOnForwardFailure` (if the door can't open, fail loudly instead of
half-connecting), `ControlPath=none` (never share a connection — the lifetime
argument above).</Footnote>

<Svg
  svg={sshLifetime}
  caption="Birth, life, death: the door is the process's own open socket, so it cannot outlive it."
/>

That is the entire protocol: one `READY` line at birth, a `cat` that waits
forever, and a kernel that closes the listener the instant the process ends —
which is why there is no cleanup code to forget and no way to leak a port. The
mechanism section above carries the expert-level detail (why each forward gets
its own connection, what `-N` would break, the measured evidence).

## Port links in the Inspector

<Mockup />

A **Ports** section joins the existing blocks in
`packages/client/src/right-panel/MetadataInspector.tsx` (pure rendering — the
data arrives on the terminal's metadata like everything else). The flows:

- **Open.** Click a chip → `window.open` on `http://${location.hostname}:…`, matching the Code tab's external-open idiom (`CodeTab.tsx:1114`). Case-3 ports open **directly**; cases 1–2 call the embedded library's `create`, get the listener port, open it, and the chip gains a `⇄ :61000` badge. Forwarding is **lazy — first click only**, never eager for every detected port.<Footnote>An agent session can hold six listening ports; auto-tunneling all of them VS-Code-style keeps idle listeners alive for ports nobody opens. Lazy costs one ssh handshake on first click — the price of a forward that dies with the process that opened it, and the reason to pay it once per opened port rather than once per detected one.</Footnote>
- **Manage, in ONE section — and one colour per meaning.** The Inspector shows a single **Ports** list, and a forwarded port is ONE row: the number, the program, a teal `⇄ :localPort` pill whose tooltip is the address you can paste, copy `⧉` and cancel `⨯` revealed on hover *or* keyboard focus, and `↗ open`. Three row endings that look different on purpose — forwarded, *quietly* offerable ("↗ forward & open", muted until you reach for it), and plainly open. It used to be two stacked groups with a forwarded port in both, and a bare `⇄` that answered no question: forwarded **where**? What the second group was RIGHT about is kept — a forward is a fact about the HOST, so a ⌘K forward or one whose listener has died trails the same section under "also forwarded on this host". The **host tab's dropdown** keeps its own list (no hostname repeated inside that host's own panel, a count on the header), and the host tab's **connection dot wears a teal ring** while doors are open there.<Footnote>The binding rule the pass settled: **green is connection health, teal is open doors, and neither may borrow the other's colour** — a third meaning would get a third colour, never a second green. The first cut drew the ring in the accent and it read as a focus highlight: a quieter way of saying "connected" rather than a fact of its own. The ring still composes AROUND the pip and never touches the pip's own colour, which is painted from the health fact and nothing else. Display vocabulary moved too: a `manual` forward reads **"pinned"** — the user knows they made it; what they need to predict is that it stays — while `auto` survived only by earning a tooltip, since it was jargon with no explanation anywhere on the surface. The wire field names do not change.</Footnote>
- **Manual forward.** The `＋ Forward a port…` row and a <Kbd keys="⌘+K" /> command accept `host:port` — for a port the scanner missed or one outside any terminal's subtree.
- **The unit is the TILE, not the pane.** A tile is one thing to the user and several PTYs to the daemon, so the scanner attributes a port to whichever *pane's* subtree holds it — correct and unavoidable. But **a dev server almost always runs in a split**, so a section that read only the main pane showed nothing in the common case (observed on a live deployment during PRT1, not in review). Every ports surface therefore reads main + splits, the same unit the Attach section already documents, merging rather than grouping: which pane a listener sits in is a detail of how the user split their tile. PRT2's **Forwarded Ports** group and auto-cancel inherit this — a forward belongs to the tile that opened it, not to a pane that may be closed while the server keeps running.
- **Discoverability.** One tip in `settings/tips.ts`: "Click a port in the Inspector to open the server an agent just started."

## Detection: ports, attributed to the terminal

The scanner is its own package — **`@kolu/port-scan`**
(`packages/port-scan/`, with the darwin C helper in its `native/`) — driven by a
**padi sensor**, and not a kaval module. Two separate calls, and both matter.

*Why a package*: the OS is the volatility. How a kernel names the processes
holding listening sockets has already changed three times on darwin in this
repo alone, and linux answers by a different mechanism in a different byte
order. That is the [electricity](electricity) bar — a real axis of change
behind a stable receptacle — so the reader lives outside padi with the arrow
pointing out, and its only input is a list of root pids. Test ③ (a *second*
consumer proving it) is honestly still pending: the OSF standalone tool and
PRT2's vazhi are named but unbuilt, the same tier `@kolu/serve-dir` shipped at.

*Why padi drives it*: the repo's own taxonomy draws the line. Facts that require the
PTY itself live in kaval (foreground needs `tcgetpgrp` on the PTY fd, cwd is
parsed from OSC sequences), while facts derived by OS inspection from a
snapshot key live in padi (git status is derived from `cwd`; kaval knows
nothing about git by design). The port scan needs zero PTY access — its only
input is each shell's root pid, which padi already reads off kaval's list
surface — so it sits beside the git sensor, keeps subprocess-spawning out of
the memory-sensitive kaval, and **changes no kaval wire contract** (contract
skew on remote hosts has its own bug note; not growing `ptyHostSurface` is a
feature). One host-wide pass every 5 seconds<Footnote>Cadence and the
unref'd, non-overlapping poll shape copy
`packages/padi/src/memorySampler.ts` and its `derived.cell(source({ read,
install: everyMsOr(…) }))` wiring in `servePadi.ts:247` — a padi idiom,
which is one more reason the scanner lives there.</Footnote> builds the
pid→ppid table once, partitions it into per-shell subtrees, and joins
listening TCP sockets against each subtree:

- **linux** — pid table from `/proc/*/stat`; LISTEN rows (with their **bind address**) from `/proc/net/tcp` + `tcp6`, joined to pids via `/proc/<pid>/fd` socket-inode readlinks (the same technique `socketHolder.ts` uses — RE-DERIVED, not shared: one leaf both plug into, with the fd-failure policy injected, is a standing extraction), walking **only the union of terminal subtrees**. Expect and tolerate per-pid `EACCES`/`ENOENT` outside the subtrees — but `EACCES` on a *requested* subtree surfaces as a scan error, never an empty port list. Do not spawn `ss` (measured ~7× slower, and it hides other-users' pid attribution anyway).
- **darwin** — a **libproc helper kolu builds** (`packages/port-scan/native/portScanDarwin.c`, compiled by the nix derivation beside it, its path baked onto padi as `KOLU_PORT_SCAN_HELPER` with no `PATH` fallback and no system fallback). ONE invocation prints BOTH tables in a versioned TSV — `V\t1`, then `P\tpid\tppid\tname` and `L\tpid\tport\thex-bind-address` (tab-separated) — and refuses a version it does not know, because a half-understood shape would parse to zero listeners and read as “nothing here is serving”. It emits **raw address bytes, not a wildcard boolean**, so `isAnyAddress` stays the single judge for both platforms; that hex is in NETWORK order where `/proc`’s is host-order-per-32-bit-word, which is why there are two decoders and exactly one judge. Non-root sees own-uid pids only — sufficient by construction, since a terminal’s subtree is padi’s own uid.<Footnote>**This replaced `ps` + `lsof`, which had replaced `netstat` — and the netstat record has now been written up wrongly TWICE, in opposite directions, so it is stated as observations rather than as a verdict.** **Window A** (the original): macOS 27.0 `netstat -anv` returns an empty internet table while reporting success — zero bytes, exit 0, clean stderr; `-anv -f inet` returns 117 bytes of header and no rows. **Window B**: on the same box the same `/usr/sbin/netstat -anv -p tcp` returns 29 LISTEN rows and `-anv` returns 241 KB — which was written up as "the original does not reproduce", and the original was retracted. **That retraction was wrong**, and it made exactly the error it accused the original of: generalising one sampling window into an absolute. **Window C** (the adversarial fact-check) settled it — back to empty, deterministic over six back-to-back runs: `-anv -p tcp` 0 bytes / exit 0 / clean stderr, `-anv` 169 KB with **zero** tcp or udp rows (621 unix-domain rows — the internet tables are simply absent), and `-anv -f inet` **117 bytes, matching window A to the byte**. A pty does not change it; `lsof` and the helper each saw the same 22 listeners at that moment; and the box had **not rebooted** between B and C (up 1 d 12 h, one boot). So macOS 27's netstat **intermittently loses its internet tables while reporting success** — stable within a window, flipped between windows, **cause unknown** (three windows is not a mechanism, and `command -v netstat` resolved to `/usr/sbin/netstat` in every one). That is disqualifying by itself: "answers no ports, successfully" is the worst failure mode for a feature whose whole job is that question, and intermittent is worse than always. A second, independently verified reason stands too: netstat's `Local Address` column is fixed-width and **truncates** (`fe80::c051:5eff:.49508` — address cut, port glued on after a `.`), and the bind address is exactly what reachability is judged from.</Footnote>


### The decided end state: one shared Rust helper, behind a proof gate

The C helper is **deliberately not the destination.** The destination is a small
(~50-line) Rust binary wrapping **`sysinfo`** (pid / ppid / name) and
**`listeners`** (pid plus the complete bind address — and on macOS it calls the same
`proc_listpids` / `proc_pidinfo` / `proc_pidfdinfo` family directly rather than
shelling out to `lsof`), owning the SAME versioned TSV above so the wire shape stays
kolu's and neither crate's debug/Serde form leaks to a consumer. It is meant to become the
**kolu + drishti boundary** in a subsequent PR, and that shared boundary — not
speed — is what would justify it over two per-platform readers. It is not there yet;
see the gate result below.

It ships when it passes a concrete gate, not before:

1. Exact own-user listener parity — pid, port, address family, raw bind address —
   against `ss` on linux and this C helper plus `lsof` on macOS.
2. Explicit fixtures for `127.0.0.1`, `0.0.0.0`, `::1`, `::`, **and a dual-stack /
   IPv4-mapped listener.** This is the specific known risk: `listeners`' macOS
   address conversion does not visibly carry the `insi_vflag & INI_IPV4` branch the C
   helper uses, and that branch is what makes a dual-stack `::` socket classify as
   reachable rather than as needing a forward.
3. A Node process reports as `node`, never a runtime thread name such as
   `MainThread` — executable basename must beat the short comm.
4. Ten-run median **≤20 ms on both platforms** at baseline, and max ≤40 ms with +100
   listeners. This admits a low-tens Rust implementation and rejects a convenience
   wrapper with `procs`-like cost.
5. Version line first; a malformed process name cannot change the field count; short
   stdout writes and top-level enumeration failures exit non-zero.
6. A pinned dependency bump cannot merge without the parity tests on both platforms.

### The gate RAN, and it FAILED on address parity — so the C helper ships

The ~50-line `sysinfo`+`listeners` wrapper was built and measured, not assessed on
paper. It is **not** in this PR, because it did not clear the gate.

**What failed: `listeners` drops the IPv4-mapping marker on darwin.** Bind
`::ffff:127.0.0.1` and ask every instrument about the same live socket — including the
KERNEL, so this is not one tool's word against another's. Identical results from three
independent binders (node, python3, and a raw C `bind()`) on zest, macOS 27.0:

| instrument | `::ffff:127.0.0.1` | `::ffff:0.0.0.0` |
|---|---|---|
| **kernel `getsockname`** — the arbiter | `00000000000000000000`**`ffff`**`7f000001` → v4-**mapped** | 32 zeros |
| **kernel `proc_pidfdinfo`** | `vflag=0x01` (INI_IPV4 set, INI_IPV6 **clear**) · v4 slot `7f000001` · v6 slot `0000…0000``7f000001` | v4 slot `00000000` |
| **C helper** (ships) | `7f000001` ✓ | `00000000` ✓ |
| `lsof` | `127.0.0.1` ✓ | `*` ✓ |
| `sysinfo`+`listeners` | `00000000000000000000`**`0000`**`7f000001` ✗ — i.e. `::127.0.0.1` | 32 zeros |

Those `ffff` bytes are the mapping marker. Without them the reported address is
`::127.0.0.1` — the deprecated IPv4-**compatible** address, which is a *different
address* from the IPv4-**mapped** one that was bound. The C helper's explicit
`insi_vflag & INI_IPV4` branch is what the crate is missing, exactly as the research
predicted was the risk.

**Severity, stated precisely:** no wildcard verdict flips *today*. A mapped wildcard
comes out as all-zeros, which `isAnyAddress` accepts via its all-zeros arm; a mapped
loopback comes out non-zero and unmarked, which it rejects. So both classify correctly
by accident. But two things are true and disqualifying: the address a consumer reads
is **wrong** (PRT2 forwards to addresses, it does not merely classify them), and
`isAnyAddress`'s v4-mapped arm — the arm that exists solely for this case — is then
**never exercised on darwin**, so a future change to it would be untested on the one
platform that needs it. Gate item 1 asks for exact raw-bind-address parity; this is
not that.

**What PASSED**, so the follow-up need not re-derive it:

- Linux parity and all five address fixtures: green, including the v4-mapped pair
  (linux reads `/proc/net/tcp6`, which carries the mapped form literally).
- The crate's integration tests **run inside the nix sandbox on both platforms** —
  verified, not assumed: loopback binds are permitted by linux's private netns and by
  darwin's `sandbox-exec`, and the darwin failure above was an assertion failure, not
  a bind error. So `doCheck = true` is viable wiring for the follow-up.
- Latency was never the problem: the wrapper was in the same low-tens range as the C
  helper.

**Three corrections to the research sketch**, found by compiling it:

1. `listeners::get_all()` returns **UDP and non-listening sockets too** (`Protocol` is
   TCP|UDP; `SocketState` carries the whole TCP state machine). The
   `TCP && Listen` filter is load-bearing — without it a UDP port, or an ESTABLISHED
   connection's local port, is published as a listener.
2. `get_all()` returns `Box<dyn Error>`, not `Box<dyn Error + Send + Sync>`; the
   sketch's `main` signature does not compile.
3. `sysinfo` 0.39 requires Rust **1.95** while the pinned nixpkgs ships **1.93**, so
   it pins to 0.37.

### Round 2: the crate bug is FIXED in a fork, and the gate now fails on LATENCY only

The address bug was fixed and the gate re-run with the sound discriminator. Parity now
passes everywhere; the blocker moved.

**The fix.** `listeners` is forked to
[juspay/listeners](https://github.com/juspay/listeners), branch
`fix/darwin-v4-mapped-addresses`, rev `227440e922f8140f22b5a6966f28b387e3ce6e8a`
(pinned by rev, not branch, so a force-push cannot change what we build). It replaces the
`soi_family` branch with an `insi_vflag` one. The flag ORDER is evidence-driven, and
two measurements ruled out the simpler patches: a dual-stack `::` sets **both** flags, so
preferring v4 would report the wildcard as `0.0.0.0` and lose its IPv6 reach; and `::1`'s
v4 slot holds `00000001`, which preferring v4 would surface as `0.0.0.1`. Hence
`INI_IPV6` first, `INI_IPV4` second, family last. A mapped bind now reports
`::ffff:127.0.0.1`, matching what the crate's own Linux path already returns.

Two regression tests ride with it, negative-checked rather than assumed: the v4-mapped one
FAILS on the unfixed code and passes after; the dual-stack one passes either way by design,
because its job is to pin the flag order, which the first test cannot. Full crate suite on
macOS: 15/16, and the one failure (`test_consistency`) fails **identically with and without
the fix** — pre-existing, and diagnosed while we were there: `lsof` showed several ports on
that host held by more than one process, so `get_process_by_port(port) == a_specific_listener`
is not well-defined. Reported upstream as
[GyulyVGC/listeners#56](https://github.com/GyulyVGC/listeners/issues/56) (bug report only —
the decision to offer a PR is deliberately deferred).

**Parity: PASS, on both platforms.** Five fixtures × two binders (node, python3) × both
platforms, oracles `lsof` + the C helper on darwin and `ss` on linux. Compared by the
CORRECTED discriminator — canonical equivalence, not byte equality: v4-mapped → v4, and any
all-zeros address → ANY (the same equivalence `isAnyAddress` itself applies, and a
dual-stack wildcard is legitimately reportable in either width). 10/10 rows equal on each
platform. The case that failed round 1 now reads
`…ffff7f000001` → `v4:7f000001`, equal to the C helper's `7f000001`.

**Latency: FAIL, on both platforms.** Gate is a 10-run median ≤20 ms:

| | median | gate | verdict |
|---|---|---|---|
| Rust wrapper, darwin (zest) | **23.2 ms** | ≤20 ms | ✗ over by ~3 ms |
| Rust wrapper, linux (550 procs) | **~100 ms** | ≤20 ms | ✗ over by 5× |
| C helper, darwin, same box + method | 10.6 ms | — | the incumbent |
| padi's own `/proc` reader, linux | 14-18 ms | — | the incumbent |

The +100-listener leg was not measured: the baseline already fails, so it could not change
the verdict.

**The cost is structural, not tuning.** The wrapper enumerates processes twice — once via
`sysinfo`, again inside `listeners` — where the C helper makes one libproc pass. That is
exactly the risk the original research flagged. Worse on linux, and more fundamentally:
`listeners` maps socket inodes by walking **every** process's fds, whereas padi's reader
walks only the union of the terminal subtrees it was asked about. No amount of wrapper
tuning changes that; it is the crate's shape.

**So the C helper still ships, and the decision that remains is a threshold one, not a
correctness one.** Darwin misses by ~3 ms for a readout whose cadence is duty-cycle bounded
anyway (`nudgeFloorMs` would simply stretch its own floor). Linux is the real obstacle to
the shared-boundary idea, and it is the platform that needs no helper at all. A plausible
end state is therefore narrower than "one binary for both": the shared boundary buys most of
its value on darwin, and linux keeping its subtree-scoped `/proc` reader may be the right
answer rather than a compromise. That is a call to make deliberately with these numbers in
hand, not something to settle inside this PR.

### Overturned: single-pass Rust matches C, so the shared binary is reopened

Surveying one more candidate — [portview](https://github.com/Mapika/portview) (MIT,
v1.6.0) — produced a number that invalidates the conclusion drawn above, so it is
recorded here rather than left in a report.

**portview measured ~9.9 ms median on darwin and ~25.5 ms on linux**, against our C
helper's 10.6 ms on the same box by the same method. It is Rust, and it is a single pass
over its own libproc / `/proc` code.

So the `sysinfo`+`listeners` wrapper's 23.2 ms darwin / ~100 ms linux was never
Rust's cost — it was the **double enumeration**, exactly as suspected: `sysinfo` walks
the process list, then `listeners` walks it again (and on linux walks every process's
fds to map inodes). One pass in Rust is as fast as one pass in C.

**That reopens the shared kolu ⇄ drishti binary on performance grounds.** The blocker was
never the language, and it was not really the crates either — it was composing two
whole-host enumerations. A single-pass Rust binary written against the same libproc /
`/proc` calls the C helper already uses should land in the same ~10 ms band, and it
would carry the cross-platform boundary the C helper cannot.

That design is now written down in its own note — [osfacts](./os-facts-tool.html) (proposed) —
which also folds in `memorySampler`, `socketHolder`, the supervisor's start-time reads and
drishti, since they are all the same question asked five ways.

**What that binary must add over portview**, which is precisely what portview lacks:

1. **A process table**, not just listener rows. portview emits one row per listening
   socket with a single `ppid` edge, so a `shell → npm → node` server cannot be
   walked back to its terminal: `npm` holds no listener and therefore never appears.
   That is the same disqualifier that ruled out `portls`, and it is the whole question
   this feature asks.
2. **`--roots` scoping**, so cost tracks the ask rather than the host. portview's
   single-port query is a host-wide scan followed by a filter — measured at 26.0 ms full
   vs 25.1 ms scoped, i.e. no saving at all.

Two smaller findings from the same survey, both already acted on:

- portview does **not** shell out (own libproc/`/proc`/IpHelper code), so it inherits
  neither the macOS netstat blindness nor the `listeners` v4-mapped bug — it reads
  `insi_vflag`. But it tests `INI_IPV4` **before** `INI_IPV6`, so a dual-stack
  `::` bind reports as `0.0.0.0` (predicted from its source, then measured on zest).
- **Our own C helper had that identical defect**, and it is fixed in this PR — v6 is now
  tested first, with the dual-stack case bound and read back in the helper's own install
  check. We do not get to hold an upstream project to a bar our own reader misses.

### What the follow-up must clear, and the two things the fact-check corrected

The finding above survived an adversarial re-run whose explicit goal was to destroy it
(fresh instruments, three binders — node, python3, a raw C `bind()` — and the kernel
itself as arbiter). It also corrected two things, both of which the follow-up needs.

**The gate's discriminator was wrong, and it would have failed the C helper too.** The
original harness asserted BYTE-EQUALITY with `…ffff7f000001`. But the C helper emits
`7f000001` for that same socket — a *truthful, equivalent* encoding of the same address
in a different width, so it fails that assertion as well. The assertion conflated "same
address" with "same encoding" and was not a sound discriminator. **The gate must compare
address EQUIVALENCE, canonicalising v4-mapped ↔ v4** (`::ffff:a.b.c.d` ≡ `a.b.c.d`),
under which the C helper passes and the crate still fails. Byte-equality is the wrong
test for a fact the OS is entitled to represent two ways.

**The crate's root cause is pinned, so the follow-up can file upstream from facts, not
from a symptom.** `listeners` 0.6.0 branches on **`soi_family`** — AF_INET6 means read
the 16-byte `insi_laddr.ina_6` slot — where it must branch on **`insi_vflag`**. For a
v4-mapped bind macOS reports `soi_family = AF_INET6` but `insi_vflag = INI_IPV4` (v6
flag CLEAR), and it stores the address in the 4-byte `i46a_addr4` slot while the v6
slot holds 12 zero pad bytes + the v4 address. Read as IPv6 that is `::127.0.0.1`, the
deprecated IPv4-**compatible** form — a different address from the IPv4-**mapped** one
that was bound, which is what `getsockname` returns. Corroboration that this is the
branch and not something else: the crate handles a plain `0.0.0.0` (AF_INET) socket
correctly at 4 bytes, and its own `Debug` output names the wrong address outright
(`[::7f00:1]:19701`).

So the fix is one `insi_vflag & INI_IPV4` check in the crate's macOS conversion — the
same branch `portScanDarwin.c` already carries. Either land it upstream or apply it as a
darwin post-process in the wrapper, then re-run the gate with the equivalence
discriminator. If only latency ever fails, profile `sysinfo`'s second process pass —
do not turn a one-shot sampler into a resident daemon merely to hide startup cost
without revisiting the operational model.

**The measurements the decision rests on** — zest (macOS 27.0, ~826–866 processes),
10-run medians, spawn-to-exit; linux from a ~550-process workstation:

| mechanism | macOS median | linux median |
|---|---|---|
| **this C helper** | **8.45 ms** · 9.41 ms with +100 listeners | n/a — linux reads `/proc` directly (14–18 ms) |
| `/bin/ps` alone | 49 ms | — |
| `/usr/sbin/lsof` alone | 94 ms | — |
| `procs --interval 1` | 29.6 ms — **and it discards the bind address** | 89.8 ms |
| `osqueryi` union query | not packaged for darwin | 378 ms |
| `portview` (MIT, own libproc//proc code) | **9.9 ms** — but listener rows only, no process table | 25.5 ms |
| `sysinfo`+`listeners` wrapper | built and measured: low tens, but **FAILS address parity** (below) | built; parity green |

So the old darwin path spent **~143 ms of subprocess** before parsing a byte, for
facts libproc returns in one call — `ps` and `lsof` are themselves libproc clients.
`procs` was rejected on **function, not speed**: it sorts and dedups `u16` ports and
throws the local IP away, so loopback-only and wildcard — the entire distinction this
feature renders — collapse into the same row. `osquery` and `rustnet` were rejected
on platform, size, and (for rustnet) its need for packet-capture privileges.

Re-measured on the shipped derivation: **10.6 ms/run** on a busier zest (866
processes), with live `lsof` parity confirmed on all four bind shapes — including the
dual-stack `::` socket, where the helper's `INI_IPV4` branch yields the 4-byte
`00000000` that `isAnyAddress` reads as reachable, matching lsof's `*:19304`.

**Attribution is the live ppid subtree — and nothing more.** Backgrounded
(`&`) processes, pipelines, and grandchildren all keep the shell as an
ancestor, so the walk sees them; a *true* daemon (setsid/double-fork,
reparented to init) leaves the subtree and is deliberately out of scope — no
session-id heuristics, no host-wide orphan matching. If you daemonized it, it
is no longer "this terminal's server".

**Cadence: a 5-second baseline, nudged by output.** The tick alone means up
to ~5 s between a dev server's "ready" banner and its chip — the one UX cost
the spike numbers don't excuse. So terminal-output bursts and OSC 633
command marks (the same signals the foreground sampler keys on) trigger an
immediate off-schedule scan — single-flight, ≥1 s floor between passes —
while the tick remains the baseline that catches quiet binds and port
*death* (which auto-cancel in PRT2 rides on). Output is only ever a hint
about **when to look**; the socket table stays the sole source of facts — a
printed URL never creates a chip.<Footnote>VS Code's output mode is the
cautionary tale for crossing that line: its terminal-URL regex *creates
forwards* with no liveness check, and its own settings text documents the
consequence — bogus URLs yield stale forwards that survive until reload, and
its process scanner exists only on Linux remotes (macOS/Windows get the
regex, full stop). Most of its knob matrix — autoForwardPortsSource, the
20-forward hybrid fallback, per-port action overrides, focus-gated toasts —
compensates for eager forwarding on uncertain evidence. Kolu's lazy,
scanner-derived design needs none of it.</Footnote>

Measured end-to-end through the shipped scanner (non-root): a complete linux
scan is **~3 ms** (~0.06% of a core at the 5 s cadence); the macOS pair is
**17 ms** on a quiet box and **93 ms** on a busy one (~1.9% of a core). The
5-second cadence has room to spare on both.<Footnote>Parser subtleties, all
fixture-worthy: `/proc/net/tcp` addresses are byte-reversed hex and IPv6 words
are little-endian *per 32-bit word*, not across the address; v4-mapped IPv6
must be normalized (`::ffff:0.0.0.0` is a wildcard, `::ffff:127.0.0.1` is not,
and they differ in four bytes) and dual-stack rows deduplicated on the final
structural `PortInfo`; a fork-inherited socket maps one inode to several pids,
so attribution folds at subtree level before dedup; lsof brackets IPv6 hosts
(`[::1]:5173`), which is what makes "port after the last colon" unambiguous,
and spells the wildcard bind `*`. One more, found live: `/proc/<pid>/stat`'s
`comm` is the THREAD name, and Node renames its main thread — a plain
`node` dev server reports `MainThread`, so the displayed name comes from
`/proc/<pid>/cmdline`'s `argv[0]` instead.</Footnote>

Each terminal's sample — `PortInfo { port, name, wildcard }` in
`packages/terminal-vocab/src/schema.ts`, beside `ForegroundSchema:145` — is
**deduped by structural equality** before it touches the snapshot, so an
unchanged scan emits nothing: the churn guard that keeps a 5-second ticker
from thrashing SolidJS. From there every layer exists: the sensor set folds
it into `TerminalSnapshot`, the surface serves it
(snapshot-then-deltas invariant, `.claude/rules/streaming.md`), and the
reconcile-backed store in `useTerminalMetadata.ts:180` delivers leaf-grained
ticks to the section.

<Callout>
**Architecture verdicts, conditioned on this build:** the *scanner* is a leaf
sensor module inside padi — a bounded one-shot scan with padi as its only
consumer — and graduates only if it grows independent consumers or its own
streaming volatility. `@kolu/port-forward` is the opposite case: ssh connection/forward
lifecycle is a hard volatility with two genuinely independent apps on top
(kolu and vazhi), which is exactly why it is a *library* package — the
upstreamed "common stuff" of the drishti pattern — and why neither app is a
daemon the other must talk to.
</Callout>

`packages/port-forward/` plus the vazhi TUI with its own `flake.nix` (`nix

### PRT1 — detection + Ports section (shipped: <PrLink pr={1982} />)

Scanner, `ports` schema field, sensor fold, the Inspector section, direct-open
chips, the tip. The shipped mechanisms — the linux `/proc` reader and the

kolu and drishti, planned in [osfacts](./os-facts-tool.html); until it passes
that note's gates, what ships here is the measured best on each platform. **Done when** an e2e scenario runs
`node -e 'require("http").createServer((_,r)=>r.end("ok")).listen(8123,"0.0.0.0")'`
in a real kolu terminal and asserts the `8123` chip appears within two scan
ticks and clicking it opens the page at `location.hostname:8123` — pinning the
real path (padi scan → snapshot → surface → reconcile
store), which no client-side mock can satisfy. Parser unit tests run on
fixture `/proc` trees *and* fixture `lsof` field output; the darwin gate
(`aarch64-darwin`) must be green, not skipped. Loopback-bound chips render
with a "needs a forward" affordance; PRT2 made it live.

**Fixtures are not enough, and this phase proved it twice.** A fixture pins the
parser; it cannot pin the assumption that the parser is handed the shape it
expects — and both darwin bugs lived exactly there, green fixtures over a scan
that threw or saw nothing. So the scanner also carries a **live** suite that
spawns real listeners and asks the real scanner about them on whatever platform
it runs (`describeDaemon`-gated, so it rides the `ci::daemon` node that is
required on both platforms).

Scanner discipline, pinned from the Zed/VS Code comparisons: the pass holds
**no OS state between ticks** — parse, join, emit the structural `PortInfo`
snapshot, drop everything else (no retained fds, no process objects, no
thread enumeration); it **repartitions from the current terminal root pids
every tick**, so a terminal opening, closing, or being re-keyed never leaves
a stale subtree; and it is single-flight (the output-nudge and the baseline
tick share one non-overlapping runner).

### PRT2 — kolu embeds the library (shipped: <PrLink pr={1991} />)

What ships, at a glance — detail lives in the footnotes:

- **Every chip opens.** Click → the embedded library opens a door → new tab at `http://${location.hostname}:<port>`. The old shared-master design would have orphaned every forward on each release while the restarted UI showed an empty list.</Footnote>

### The deferred shape question, settled: `wildcard` became `scope`

PRT1's review left one question open for exactly this phase — whether `PortInfo`
should carry `wildcard: boolean` or a three-way
`scope: "any" | "loopback" | "interface"` — on the grounds that PRT2 is where the
second consumer appears and the tag could then be designed against two real
readers instead of one. It appeared, and **the boolean was wrong for a reason no
amount of structural argument had reached: it is not a distinction the
MECHANISMS can act on.**

Both of PRT0's doors connect to **`127.0.0.1` on the far side** — the relay dials
this machine's loopback, the `ssh -L` child dials the remote's. So the boolean's
`false` arm covered two cases with *opposite* correct handling: a loopback bind
(exactly what a door reaches) and a bind to one specific interface such as
`192.168.1.5` (which answers at that address, and which no door can reach at
all). Under `wildcard: boolean` the second case rendered as "needs a forward",
the click would open a listener successfully, and every connection through it
would be refused. A boolean cannot spell the difference, so PRT2 ships the
three-way and `portReach` grows a fourth, honest arm — `no-mechanism` — that
offers nothing because there is nothing to offer.<Footnote>The reshape is one
classifier, not a schema patch: `isAnyAddress` became `addressScope`, still the
SINGLE judge both platforms reach through their own decoder, so the two cannot
come to disagree about `::ffff:0.0.0.0` — the property PRT1 paid for twice. The
fold widens rather than ORs (`any` > `interface` > `loopback`), which keeps it
order-independent, which is what keeps a 5-second scanner from republishing a
"change" forever. Cost, stated: padi's surface goes 4.2 → 4.3 and a straddling
padi is drained by the existing convergence machinery before either parser meets
the other's frame — the same rule 4.1 and 4.2 already rest on, so the reshape
needs no compatibility arm and deliberately has none. Verified against the real
OS, not just fixtures: the live suite binds a real routable interface address and
asserts it classifies as `interface`.</Footnote>

The structural lens's original case stands too, and is worth recording as
*separate*: `scope` is still an OBSERVATION, not a verdict. Whether a port answers
for a given viewer needs the HOST as well, which no field of `PortInfo` ever
carried — so the judgment stays `portReach(scope, onKoluHost)` in kolu's own
vocabulary, where both ends of the wire read the one copy.

### …and then production froze, and `scope` turned out to be half the fact

The first deploy of PRT2 **froze the entire kolu server on the first forward
click** — UI dead, HTTP dead, `SIGTERM` ignored until systemd sent `SIGKILL` —
and the forward it did open served nothing. Three defects, and the two that
matter are the same mistake in different clothes.

**The freeze was a cycle between two reasonable halves.** The forward cell is a
poll on a *fused* cadence (`everyMsOr(interval, onChange)`): the interval runs
the auto-cancel pass, and the change edge makes an act publish at once instead of
waiting out a tick. Separately, the auto-cancel pass ended by announcing its
result. Each half is right on its own; together, the pass announced on the very
edge that triggers the pass — read → reap → announce → tick → read — and the
event loop never yielded again. It was invisible until the first click because
with zero `auto` forwards the pass returned *before* announcing. The fix is not a
guard on the announcement but the removal of the shape: the reconciliation
**reports by returning**, the poll publishes what it returns, and "reap and
announce" is no longer spellable.<Footnote>The general lesson is worth more than
the fix: neither module was wrong in isolation, so no unit test of either could
have caught it. What catches it is a test of the JOIN — the regression test
reproduces the fusion in miniature and asserts the read count stays BOUNDED,
which is a property of the wiring rather than of any module in it.</Footnote>

**And `scope` was half a fact.** `127.0.0.1` and `::1` are both `loopback` and
are *not the same address*; the classifier folded them together, and both
mechanisms then dialled v4. A dev server on `[::1]:5173` — what vite and several
Node versions bind by default — got a tunnel that came up perfectly and served
nothing, because there was no listener at the address the door opened onto. So
`PortInfo` now carries `family` beside `scope`, and it is a **separate field
rather than a fourth scope value** because the two answer different questions:
`scope` decides *whether* a door is needed, `family` decides *what it dials*, and
only the first is a reachability judgment with an ordering.

The two are one lesson, stated once because it has now cost two defects in one
PR: **a fact the OS handed us was collapsed below what the consumer needed, and
the collapse was invisible until something dialled the answer.** `wildcard` lost
the interface case; `scope` lost the family. Both looked like tidy reductions and
both were reductions past the point of use.<Footnote>Which is why the dial family
is now read SERVER-side off kolu's own scan rather than accepted from the client:
a client's copy of the port facts can be a scan or two stale, and a stale family
opens a door onto an address with nothing behind it — the same failure by a
different route. The one place kolu cannot observe it (a manual forward to a port
no terminal serves) assumes v4 at a single named constant, with the failure loud
at the point of use rather than silent.</Footnote>

**A second question of the same shape was RAISED AND SETTLED IN PRT1**, not deferred: whether a terminal that has never been successfully scanned is distinguishable on the wire from one that serves nothing. It was first argued as unreachable and the peer review refuted that with three surviving routes — a first-pass `lsof` timeout on darwin, a transient `/proc/net/tcp` read failure on linux, and (widened by PRT1&rsquo;s own fix) any unexpected `/proc` errno — none of which needs the terminal&rsquo;s own shell to be unreadable. So `ports` is a discriminated `known` / `unknown` two-way, the same honest shape `ProcessRss` already uses, and holding a last-good sample now covers only what it can actually cover.<Footnote>PRT1 also left a
second, smaller judgment on the table: kaval's one host-global `activity` edge now
has three independent `resubscribeStream` consumers (the finish fold, the live
dots, the port-scan nudge). They are not three copies of one shape — the live-dots
one is per-SUBSCRIBER by design, the other two are daemon-lifetime — so the shared
fan-out waits for a consumer that actually matches, rather than forcing the
per-subscriber case into a receptacle it does not want.</Footnote>

The kolu server embeds `@kolu/port-forward`; forward state becomes a cell on
kolu's existing surface; chip click → lazy create; tunnel badges; Forwarded
Ports group; manual forward + ⌘K command; auto-cancel policy. Two UX details
adopted from VS Code's Ports view: when an auto-forwarded listener dies and
later returns, **re-forwarding prefers the local port it had before** (links
and bookmarks keep working across a dev-server restart), and every
forwarded-port row carries a **copy-address** affordance beside open and
cancel. **Done when**,
verified with the `remote-host-testing` harness against a real remote box
*and* a viewer on a different machine than the kolu server: clicking a remote
terminal's chip creates the forward **through the embedded library** (a
running vazhi is neither required nor consulted), the opened
`http://<kolu-host>:<localPort>` returns the remote server's body, cancelling
the row severs it, and stopping the remote server auto-cancels the `auto`
forward within two scan ticks. Plus the kolu-level twin of PRT0's SIGKILL
criterion, which matters MORE here than in vazhi because the server restarts on
every deploy: **kill the kolu server and every forward it created must refuse
connections at once** — the old shared-master design would have orphaned them
on each release while the restarted Inspector showed an empty list. Evidence
video of the click-to-page flow.

**When the viewer IS the host.** A machine in kolu's fleet can be the machine you
are reading kolu from — the plan's own footnote called this "roundabout but
correct, and not worth a special case in v1", and in practice it was baffling:
every chip on *zest*'s terminals, viewed from zest, offered to open a door on
*pureintent* so that zest's browser could reach a port on zest. So kolu now
recognises it, from the one fact that can settle it: the **peer address of the
viewer's own connection**, which only the server can see, compared against the
addresses the host resolves to.

Two things make an inexact comparison acceptable here, and neither is incidental.
First, **the failure direction is safe**: a match opens the port directly on the
viewer's own loopback, and every way of failing to recognise the viewer — a NAT,
a proxy, an ssh alias DNS cannot resolve — leaves the forward exactly as it was,
which works. Second, **a `direct` port is never rewritten to `localhost`**: it
already answers on a name that means the same thing from every machine, and
`localhost` is the one hostname that does not — trading the first for the second
would undo the rule this whole feature is built on.

It rides a ROOT rpc rather than a surface member, and that is structural rather
than convenient: the answer differs per viewer, and a surface cell is broadcast,
so it has no shape that can carry a different answer to each connected
browser.<Footnote>The reliable version of this needs a fact kolu does not have —
the host's own interface addresses, which padi could report but does not — so
what ships resolves the ssh destination instead. That is genuinely weaker for
alias-named hosts, where it simply never fires. Recorded as a limit rather than
hidden, because the alternative was to add a padi surface field inside an
incident fix.</Footnote>

**The first cut of it never fired once, and the reason is worth keeping.** It
compared the connection's TCP peer — and kolu's real deployment is reached
through `tailscale serve`, which terminates TLS and dials the backend from the
host's OWN tailnet address. So the only established connection to kolu had peer
`100.122.32.106`: *pureintent itself*. The viewer's address never appeared as a
TCP peer at all; it was in an `X-Forwarded-For` header nothing read. The
comparison had been right the whole time and the observation feeding it belonged
to the proxy.

So the address is now taken from the forwarded header **when, and only when, the
direct peer is a trusted local hop** — loopback, or one of this host's own
addresses, which is exactly what a local reverse proxy looks like. Three
properties make that safe to state as a rule rather than a setting: a header
arriving on an untrusted connection is ignored **entirely** (anyone who can reach
kolu directly can invent one, and honouring it would let a stranger be handed a
`localhost` link for any host's ports); the **last** entry wins rather than the
first, because each proxy *appends* the address it received from while the
leftmost entry is whatever the client typed; and there is no trusted-proxy list
to configure, because the trust condition is a fact about the connection rather
than a knob.<Footnote>A deployment shape that hides the viewer more thoroughly —
a proxy on a different machine, or one that strips the header — lands on the same
no-match side as before, which keeps the forward that works. The mechanism is
allowed to not fire; it is not allowed to be wrong.</Footnote>

**What the automated suite actually covers, and what it deliberately does not.**
The e2e scenarios drive the **relay** case end to end — a real loopback listener
in a real PTY, a real click, and the listener's own body arriving in the opened
tab through a port it never bound — plus the cancel twin, which proves the door
is *shut* by dialling the recorded URL from node rather than by watching a row
disappear. The **`ssh -L` case is not simulated**: it needs a second machine, and
a loopback ssh hop standing in for one would exercise a different code path from
the one it claimed to cover, so it stays with the `remote-host-testing` harness
above. Stated rather than left implicit, because "the port forwarding suite is
green" would otherwise read as covering both mechanisms.

## What this track sent upstream

PRT2's production incident was the best evidence for what belongs in the
`@kolu/surface` frameworks rather than in this feature. Four items were
dispatched; **three shipped, one was withdrawn on verified grounds** — and the
withdrawal is recorded here rather than left looking pending, because a roadmap
that claims work it did not do is worse than one that is short.

1. **A loop guard in the reactor, built on PROVENANCE.** The freeze was the
   reactor executing a legal wiring forever, and the class stayed expressible
   after the consumer-side fix — `processMemory` and `daemonInventory` sit on
   identical wiring. Each poll read now runs inside an `AsyncLocalStorage`
   context keyed to its own source, so a change edge that fires *under that
   context* was caused by the read it is about to re-trigger. Three consecutive
   self-caused ticks crash naming the cell.<Footnote>The first cut asked about
   TIMING and value-equality instead, and adversarial verification refuted it in
   both directions: a plain `everyMs(10)` cell whose read takes 30 ms and returns
   a constant crashed in ~400 ms (every coalesced trailing read looked
   "immediate"), while the proposed lap-timing fix would have MISSED the real
   freeze, since a self-loop's lap is just its read duration. Timing is a proxy
   for causation and every variant of it fails one direction or the other. The
   repo's own doctrine already said so — cut feedback loops with provenance, not
   value-dedup (the controlled-component echo rule).</Footnote> Its companion
   `assertCellConverges` ships beside it as the authoring-time twin, and PRT2's
   own convergence test uses it.
2. **Viewer identity graduated** to `@kolu/surface/viewerIdentity`. "Which
   machine is the viewer actually at" is a transport fact any surface-served app
   behind a reverse proxy needs, and kolu got it wrong twice in one day. The
   judgment (trusted-peer gating, which forwarded hop may be believed) is the
   package's; the OS-touching half — DNS, interface enumeration — stays with the
   consumer.
3. **The doctrine, written down** where surface rules live: a per-viewer answer
   is a root RPC and never a broadcast cell; a poll read may reconcile, but
   publishes only by returning. Both cite this incident.

**Withdrawn: `Observed<T>`.** The item's own premise — "the same discriminated
shape hand-rolled three times" — turned out to be factually wrong, and checking
it was the whole value of the exercise. `ProcessRss` is a deliberate THREE-way
whose `error` arm is load-bearing on the wire (producers emit it, two client
consumers render distinct UI from it), so it was never a candidate. Between the
remaining two the honest duplication is ~5–7 lines of map-accumulate skeleton:
the one real merge rule (`preferredFamily`) is already shared, the compare logic
overlaps not at all, and `HostPorts` is a *projection from* `TerminalPorts`
rather than a parallel fold of the same thing. The repo also already has an
in-process generic for this (`Known<T>`, payload key `value`) that a wire
unification would collide with. There is nothing worth extracting; it may be
revisited only if osfacts' kolu-side adoption ever creates real duplicated fold
logic.
