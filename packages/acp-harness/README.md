# @kolu/acp-harness — one conversation, on the client that runs the protocol

[`@kolu/acp`](../acp) is the Agent Client Protocol's words and pure projections over them; nothing in it waits, spawns, or knows a subprocess exists. [`@kolu/acp-client`](../acp-client) is where one does: it spawns the adapter, holds the connection, and says what the agent said as one closed union of events.

`@kolu/acp-harness` is the half above that: it opens or resumes ONE conversation on a client, and turns those events into the rows a person reads. Everything hard about talking to an agent over a pipe — a child that dies mid-turn, a frame from a conversation you already left, a question that blocks a turn until a person answers it — is the client's; what is hidden HERE is everything hard about a CONVERSATION: a conversation the agent cannot come back to, a replay, an attachment that must not silently fail to travel, a background task that outlives the turn that armed it. **It names no product.** Two chat UIs run this one copy — kolu's [Conductor](https://kolu.dev/conductor), held by [`kolu-server`](../server) through [`kolu-conductor`](../conductor), and [olai](https://github.com/juspay/olai)'s chat panel — so every fact either of them knows that the protocol does not arrives as an option or as the row content a verb is handed. `src/noProductImports.test.ts` holds that red: no file under `src/` may import a `kolu-*` package or `@kolu/terminal-vocab`.

## How the conversation is split

| file | what it holds |
|---|---|
| [`@kolu/acp-client`](../acp-client) | the protocol: the subprocess and its stderr, every request and notification, the handshake, which session the agent is in (and which it has left), the questions on the wire, the sign-in attempt, and the reading of every frame. Two products run it — kolu's Conductor and [olai](https://github.com/juspay/olai)'s chat plugin — so it names no row, no fleet ref and no terminal |
| `src/conversation.ts` | the conversation: opening and resuming sessions and what the transcript does about it, the turns and the steering latch, the questions drawn as rows, attachments as content blocks, the state a caller reads, and every row written. The one place an Effect is run — the client's verbs are Effects and this door is promises |
| `src/harness.ts` | the door: the names this package has always published, re-exported from `conversation.ts`, so the split is an arrangement rather than a change to what it hands out |

## The door

One entry, deliberately. A second subpath would be a second way to reach a subprocess, and there is exactly one subprocess — and that is still true now that the door hands out more than `startHarness`: the conversation layer below it (`Transcript`, `Turns`, `holding`, and the `says`/`plus` rules over a change) is exported so that the two products that each hold ONE conversation are served by one class rather than by a copy in each. Both the class and `startHarness` are generic over the product's row union: they own the fields `@kolu/acp/wire` declares as row fields, and what a product adds rides in an `extra` object they copy and never read.

```ts
const harness = await startHarness<Row>({
  leg, adapter,                 // how it reads its wire, what to spawn
  cwd, configDir, mcpServers,   // where it works, the store its signature is read from, what it hands over
  probes,                       // ... and what it DISCOVERS per open, for a product whose hands are found rather than listed
  teaching, taught,             // the standing prompt the CALLER wrote, and whether the session being resumed has had it
  compacts, onCompaction,       // optional: when the agent will compact, and every compaction it reports
  log, opens,                   // { kind: "resume", id } | { kind: "fresh" } | { kind: "adopt", memory }
  resumedSeq, resumedEndsWithDivider, model,
  readCall,                     // (frame, held) => { extra?, untilNamed? } — the product's half of a tool row
  retitle,                      // when a named row may be renamed; omitted is never
  whenNewSession,               // "divide" | "clear"
  numbering,                    // "continues" | "restarts"
  whenLoadRefused,              // "fresh"  | "report"
  whenReplayed,                 // "drop"   | "keep"
  onChange,                     // { kind: "state" } | { kind: "rows", … } | { kind: "turn", … }
});
```

`opens` is the policy that needs a live agent: `{kind:"adopt", memory}` opens the conversation this directory was last in, else the agent's most recent STORED one, else a fresh one — and which conversations an engine has stored is something only the process on the other end of the pipe knows, so a product that worked it out itself would spawn a second adapter to ask. `numbering` is the transcript's: `"continues"` runs the numbers on for the life of the process and starts after `resumedSeq` (a product that writes its rows to a store), `"restarts"` starts a wiped conversation again at zero (a product whose browser reads a row's `seq` as the count of the rows older than it).

**A turn says how it ended, once, as a value.** The third `onChange` arm is `{kind: "turn", row, outcome, why, silent}`: `"ended"`, `"cancelled"` (somebody stopped it), `"refused"` (the agent's own sentence in `why`) or `"unanswered"` (nothing came back), with `silent` saying whether the agent said anything at all while it ran. Rows and state both move during a turn and neither answers "what became of the message I sent"; a panel that read the English of a notice row to find out would be pattern-matching sentences this package writes.

**The three policies are where the two products differ, and each arm is implemented here.** `whenNewSession` says what a new conversation does to the transcript: `"divide"` keeps the history and mints a `divider` row between the two (kolu, which persists its rows), `"clear"` wipes them (olai, whose panel is the only copy). `whenLoadRefused` says what a conversation the agent has forgotten does: `"fresh"` opens a new one and says so, `"report"` lets the refusal stand and opens nothing. `whenReplayed` says what `session/load`'s re-emitted frames do: `"drop"` counts them and throws them away (a product that already holds those rows, in a richer form), `"keep"` folds them in (a product with no record of its own). What the same replay says about the session AS IT STANDS — its commands, its usage — is kept either way.

`readCall` is the other half of the same idea: the conversation hands over everything the client said about a tool call (EVERY MCP server and tool it positively named — one builtin can dispatch several — the raw input, the structured answer, what the agent called it and whose row it is, the panes it is running in, and what the product last read the same call as) and writes what comes back onto the row's product half. The reading has two halves: `extra` is taken on every frame that says it, `untilNamed` only while the row has no name of its own (an engine's raw spelling of a call, which the friendly title arriving a frame later must not drag back). What a card SAYS is the product's, and kolu's reading lives in [`kolu-conductor`](../conductor)'s `kolu.ts`.

`mcpServers` is an array of two arms, discriminated by `kind`. A `{kind:"stdio"}` entry is a program on this machine (`name`, `command`, `args`, `env`); a `{kind:"http"}` entry is a server already running (`name`, `url`, `headers` — where a bearer token rides). What a product hands over is the product's: kolu's one `http` entry is its fleet face, and [`kolu-conductor`](../conductor) says what that buys. On the wire the arms differ by ONE key, and it is not `kind`: ACP's stdio arm is the one with **no `type` key at all**, and the pinned adapter silently DROPS an entry carrying `type: "stdio"` — so the in-tree discriminant is named `kind` precisely so it can never be confused with the wire's `type`.

`startHarness` does spawn + `initialize` + (`session/load` when `opens` names a conversation, else `session/new`) + the leg's permission mode + the remembered `model`, all before it resolves — one `try` over the whole sequence, so a refusal or a deadline **stops the child** rather than leaving an adapter (and a `claude` under it) running for every retry. It never resolves into a half-open conversation, with **two** exceptions, both of which keep the child. An `auth` refusal resolves with `phase: "offline"` and `state.signIn = {cause: {kind: "agent", why}, methods, attempt: null}`, because the process that refused is the process a sign-in has to run against. And a `session/load` refused for any OTHER reason opens a fresh conversation instead: `-32002 Resource not found: <id>` is a fact about a string the CALLER wrote down — its store moved, its history was pruned, a different CLI answered — not evidence that the agent is broken, and the agent demonstrably is not, because it just refused. Read alike, that killed the adapter and the caller spawned another to ask the same dead id again. Every refusal is PUBLISHED through `onChange` before it is thrown, so the panel says why instead of looking idle.

**A refused open is not the only way an agent asks for a signature, and on the pair kolu ships it is not even the usual one.** Measured against `claude-agent-acp` 0.81.2 over agent-distro's `claude` 2.1.319 with an empty `$HOME`: the handshake advertises both paste-a-code methods, the agent pushes `_auth/status_update {kind:"none"}`, **`session/new` SUCCEEDS**, and `-32000` does not arrive until the turn. So `state.signIn` is published on all three — the agent saying nobody is signed in, a refused open, and a refused turn — and withdrawn when the agent names an account or a sign-in exits 0. A PERSON can ask for it too, signed in or not (`askSignIn`): an account at its usage limit, the wrong account and a stale login are all signed in and the agent offers nothing for them, so that row's cause is `{kind: "person", said}` and `signInCancel` closes it again. An offer that waited for the refused open alone was no offer at all here: the panel drew a composer over an agent that could not answer, and the sign-in button reported that the agent had offered nothing.

Two error classes are the whole of what a caller may branch on: `HarnessUnavailable` (no child, no session) and `HarnessRefused` (`{why, signIn, missing}` — a refusal, the agent's or this end's; whether signing in could fix it, `signed-out` off ACP's `-32000` and `account` when the leg's `accountRefusal` reads the agent's error `data` as the account being unable to run it, else `no`; and whether what was asked for is simply NOT THERE, ACP's `-32002` for a `session/load` of an id the store has no record of, which is the one refusal whose way out is a different gesture). A refused turn carries the sign-in reason onto its user row (`signIn`), which is what puts the sign-in door beside it. Anything else is a defect and propagates unwrapped, because a conductor that broke in a way nobody declared should crash loudly rather than arrive as a polite sentence in a chat.

The verbs are `prompt(said, steer)` · `sendAgain(rowId, body, files)` · `hostTurn(row, text)` · `cancel` · `answer` · `signIn` · `askSignIn` · `signInInput` · `signInCancel` · `setOption` · `newSession` · `loadSession(id)` · `clearSession` · `sessions()` · `stop`, plus `state()`, `rows()` and `alive()` — the last for a caller deciding whether to replace a harness, since an `auth`-refused one is offline AND alive. A person's message is one object (`{text, body, extra, files}`): `text` is what the ROW records, `body` is what the agent is sent under it — the product's to compose, because the chips an agent cannot see are the product's — `extra` is the product's half of the row, and `files` are the attachments to read. `sendAgain` re-sends the row already on screen and is refused for any row that is not waiting to be sent; `loadSession` moves to another stored conversation in the SAME process under the same policies as the bring-up; `sessions()` lists what the running agent has stored, so a picker spawns no second adapter. `state()` answers the conversation and nothing a caller already knows: phase, session, title, model, usage, settings, commands, servers, watching, open asks, sign-in, the advertised sign-in `methods`, identity, refusal, `steers`, `queues`, `busySince` and `taught`. What a product keeps BESIDE a conversation — which install it is, what the agent is called, the directory it works in, whatever its host is watching — is the caller's, and a harness that echoed it back would be overwriting the caller's answer with a copy of it.

## The rules it keeps

Each of these is a bug that happened once. They are what the package is. The
rules about the PROTOCOL — the prompt frame, the permission mode, the roster,
the stale-frame fence, the close of a conversation being left, the prologue, an
auto-approval, an MCP answer, the model row, what a sign-in runs — moved with
the code that keeps them, and are in [`@kolu/acp-client`](../acp-client)'s
README.

- **A message sent mid-turn is marked `queued`, and nothing is held here.** The
  queue is the AGENT'S: the client sends the prompt immediately and it waits
  there, and this end only marks the row until the agent picks it up — which is
  also why `cancel` has nothing to throw away.
- **A resumed conversation's HISTORY is the product's call; its NEWS is kept either way.** `session/load` re-emits the whole transcript before it answers. Under `whenReplayed: "drop"` those frames are counted and thrown away, because the caller's own persisted rows are the richer record (they carry readings no agent's transcript holds); under `"keep"` they are folded in, in chunks, which is how a panel with no record of its own comes back to its conversation. Only the transcript-bearing kinds are affected: an `available_commands_update`, `config_option_update` or `usage_update` on that same stream is the session as it stands NOW, and dropping it left a resumed conversation with no `/` completion and no context meter for the rest of its life. `resumedSeq` is the highest `seq` the caller holds, and every id and `seq` minted here starts after it.
- **The standing prompt rides the first message of a session — and the CALLER remembers that it has.** `taught` comes in and `state().taught` goes back out, because a harness is replaced for reasons that have nothing to do with the conversation (an upgrade, a crash, a signature) and one that assumed nothing put the standing prompt back into the middle of a chat on every restart. A new session clears it: an agent with no memory of the conversation is owed the words again.
- **A caller that says when the agent compacts (`compacts`) gets the standing prompt again around a compaction.** It rides the message the agent will compact before it reads, the first message of a loaded session whose usage is not known yet, and, after a completed compaction it did not ride, the next message, which clears `taught` until then. Each is once: a reading under the limit, a reported compaction or a new session re-arms it. `onCompaction` hears every live report, with whether the rules are already in the new context (`sent`) or go with the `next` message; a replay's reports are history and are not passed on.
- **A divider means the agent's memory was reset, and nothing else.** Two things mint one: `newSession()`, and a resume that could not be — a `session/load` the agent refused for the id, where the conversation that opens instead is a different one and the break says so, under one line naming the agent's own sentence for why. A bring-up, a resume that worked, and the replacement that comes up over a dead adapter mint none. The transcript KEEPS its history across the break — a `clear` would be a lie to a caller whose copy holds rows this process never minted — and the mark is withdrawn again if the new conversation would not open, because an open that failed reset nothing and a retry behind it is how four `— NEW SESSION —` lines come to sit on top of one another. A second break with nothing said between is not minted at all — including the break the CALLER is already holding, which a fresh transcript cannot see and `resumedEndsWithDivider` tells it about: without it, a `newSession` after a respawn minted one beside the caller's every time.
- **An attachment is a content block or a refusal, never a silent drop.** An `image/*` needs the agent's advertised `promptCapabilities.image`, a text-like file (`text/*`, JSON, XML, JavaScript) embeds its text as a `resource` and needs `embeddedContext`, and everything else is a `resource_link` naming the absolute path the caller wrote. 10 MiB an attachment and 20 MiB a message, refused with a sentence naming the limit — and refused BEFORE the row is minted, so a person's message is still theirs to send. **The bytes are read off `path`**, which is the only copy there is: base64 cannot ride the `prompt` frame, because an oversized frame closes the socket the words came in on. That is also why a RESTORED row can be sent again — it has a path like any other.
- **Nothing is published after `stop()`.** A turn still on the wire ends a moment later; its rows would be rows the caller persists for a conversation it has already let go. The one frame a shutdown owes a reader is sent by hand.
- **A frame refines, never retracts.** The product's reading of a tool call is accumulated across frames: `readCall` is handed what the same call was last read as, because the adapter puts the call's input on the arming frame and its answer on the settling one, and a card built from either alone is missing the half the other had. The readings are cleared with the conversation — a call id is only ever looked up inside the session that minted it.
- **A message may be STEERED into the turn that is running.** `prompt(…, steer)` takes the leg's `Steering` — the method, its `_meta`, its own deadline, and what its answer means — and sends the words INTO the running turn: `injected` leaves the row unqueued and starts no turn here, *nothing to steer* sends them as an ordinary prompt instead, and a steer aimed at a turn somebody CANCELLED under it is refused rather than silently un-cancelling their press. A message carrying ATTACHMENTS is never steered, whoever asked: the steer carries one text block, so steering it would deliver the words and drop the files — it goes the ordinary way, words and files together. `state.steers` is both halves in one bit: the agent advertised steering at the handshake, AND this conversation has never held a message behind a running turn (the `queuedHere` latch, around a defect of the pinned adapter measured in [`@kolu/acp-claude`](../acp-claude)'s `adapter/patches/README.md`). A new session gets it back.
- **A product can start a turn of its own.** `hostTurn(row, text)` mints the row the CALLER hands over and runs a turn exactly like a prompt — the standing prompt rides it if it is the first message, it waits behind whatever is running and says so, it can be cancelled, refused or go unanswered. Whose words they are is the row's kind and nothing else: every delivery mark is the same machinery a person's message uses, and the class is told that THIS row takes them. `state.busySince` is when the turns in flight began, so every reader counts "working · 2m" from one instant.
- **Re-entering the conversation after a sign-in is the CALLER'S.** A signature reaches an adapter only through a fresh `initialize`, so this harness opens NOTHING when a sign-in succeeds: the caller restarts it with the conversation it wants back on `opens`. This end used to open one itself, out of the conversation it booted with, which put a person back in the conversation they had left.
- **A turn the agent REFUSES is a turn that ended**, not an agent that has gone: the conversation stays ready and the next message goes to the same agent.

## It is vendored, so the door is append-only

[olai](https://github.com/juspay/olai) copies this directory out of a
content-addressed kolu pin and compiles it with its own `tsc`. Its panel does
not come through this door yet, so `src/sharedVocabulary.json` records the door
it WILL use — everything `index.ts` hands out, with the options it will pass,
the state it will draw and the verbs it will call — and
`src/sharedVocabulary.test.ts` holds it: adding is free, and removing or
renaming a recorded name fails here rather than in the other repository's
build. The ledger's own header says which rows are read out of olai's source
and which are a promise made ahead of it.

## Tests

Against **really spawned** fixture agents (in [`@kolu/acp-client`](../acp-client)'s `src/fixtures/`, reached through its `./testlib`), not mocks — plain `.ts` files run as `process.execPath <file>`, since node strips types natively. A mock would prove only that the reader can read what the test wrote; a spawned agent proves the pipe, the codec, the ordering and the lifecycle. `subprocess-agent.ts` goes one further and holds a REAL child process per session, the way the pinned adapter holds a `claude`, so "a replaced conversation leaves one process, not two" is a count of processes rather than of bookkeeping. The lane is **`test:daemon`**, not `test:unit`: every case forks a detached process group, so it runs serially with the other daemon-forking packages, and one `afterEach` stops every harness a case started. The one pure file, `src/kolu.test.ts`, rides the same lane (a package declares one): each kolu tool read off the shapes it really takes and answers, and every reading — whatever strings sit in its arguments — encoded under the contract's row schema.

A fixture is only ever as honest as the measurement it was copied from, so the two signed-out agents are copies of two different measurements: `signed-out-agent.ts` refuses the OPEN with `-32000` (the protocol's own way of asking, and what every fixture here used to assume), and `signed-out-open-agent.ts` is the pinned pair's real sequence — methods at the handshake, `{kind:"none"}` pushed, the session OPENED, the TURN refused — with `--no-methods` and `--no-status` for the dead end and for an agent that says nothing about itself. The claim only the two binaries can keep is kept where they are: `packages/server/src/conductor/signedOut.live.test.ts` drives the real adapter and the real `claude` against a scratch `$HOME`, offers the sign-in, runs it as far as the URL, and cancels — a test may never complete a login or touch anybody's credential.

## What it deliberately does not do

The adopt-or-create boot and the model memory the client offers (the caller owns persistence and hands `opens`, `resumedSeq`, `taught` and `model`, so this harness is TOLD which conversation to open and answers the client's memory out of those options), and the agent's own panes for a `terminal/*` call. Neither is a gap this package hides; each is a decision recorded where it was made.
