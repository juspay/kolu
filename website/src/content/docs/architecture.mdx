kolu splits the terminal problem across four layers. Close the browser tab,
restart the web server, or redeploy the whole thing: your shells, and the agents
running in them, keep going. This page shows the layers, the contract they talk
over, and the packages behind them.

## The stack

Four layers, each with one job. The top two are faces, which come and go. The
bottom two are daemons: [padi](/padi) holds the workspace record, and
[kaval](/kaval) owns the live shells. The arrows are transports: a websocket to
the browser, a unix socket between the daemons, ssh out to each other host's
padi. Kill any layer and everything below it keeps running.

kolu-server binds one padi per host. That set is its **host map**, which is why
kolu-server also holds [the Conductor](/conductor), one agent conversation for
the whole fleet.

| Layer | Its one job | Killing it does not lose |
| --- | --- | --- |
| [`PWA client`](/install-pwa) | The view in your browser, one surface consumer per pane. | Nothing. Reload the tab or switch devices and it re-subscribes. It holds no state. |
| `kolu-server` | The web shell: HTTP, the app, websockets. It binds one padi per host and holds [the Conductor](/conductor)'s conversation. | Terminal metadata, the remote hosts you added, or the conversation. Each is stored, and the conversation is resumed by its id. |
| [`padi`](/padi) | The per-host workspace daemon: session, awareness, restore. | Terminal state. Records live in its folder on disk, the shells survive in kaval, and it re-seeds in seconds. |
| [`kaval`](/kaval) | The shell survivor: it owns the PTYs and their live screens. | The live shells and their scrollback. They live in kaval's memory, under everything you can restart. |

## A deploy adopts what is running

Upgrading kolu does not kill your daemons. A new build adopts the compatible
ones, and their live shells, instead of reaping and restarting them. Restore is
the path for a daemon that is dead, never for one that is still running. The
agents in your terminals survive the upgrade, because they never stopped.

<Aside type="tip" title="padi drains, kaval waits">
  A newer client meeting an older padi asks it to _drain_: save its session and
  exit, while the PTYs stay alive in kaval. An older client meeting a newer padi
  is refused. Draining kaval would kill the live shells, so an older kaval stays
  up and asks you to restart it.
</Aside>

## Compared to tmux and zellij

tmux and zellij fold the PTYs, the layout, and the session into one server
process. kolu splits them: kaval owns the PTYs, padi owns the workspace. The
layer you restart or redeploy is not the layer holding your shells.

No multiplexer keeps a live process across a machine reboot: a PTY cannot
outlive the kernel. All three re-create rather than resume. kolu remembers more
about how: the layout, the working directory, the agent that was running, and
where to pick it up.

## One contract — `@kolu/surface`

<LinkCard title="Announcing @kolu/surface" href="/blog/surface-framework" description="read the story behind the one contract every layer talks over" />

<LinkCard title="@kolu/surface — the docs" href="/surface" description="the framework's own four-quadrant docs: declare a surface, serve it, daemonize it, and mirror it across an ssh fleet" />

Every layer talks over the same thing: a _typed reactive surface_. You declare
what a daemon exposes, a handful of primitives plus the verbs that change them,
and get a client that stays in sync. Four primitives cover almost everything:

<CardGrid>
  <Card title="Cell<T>">
    One value: a snapshot, then live deltas. The session, the version.
  </Card>
  <Card title="Collection<K,T>">
    Many keyed rows, each independently observable. The terminals registry.
  </Card>
  <Card title="Stream<I,T>">
    A live view computed over outside state (files, git). Snapshot plus deltas,
    never stored. A file preview.
  </Card>
  <Card title="Event<I,T>">
    A point in time: no snapshot, no current value. A terminal exited.
  </Card>
</CardGrid>

Beside them sit _procedures_: the verbs you call and await, such as create a
terminal, kill one, or restore a session. That is the whole contract, and it is
served over any transport: in process with no wire at all, over a local unix
socket, over a browser websocket, or over ssh. The ssh transport is how
`kaval-tui --host`, drishti, and kolu's remote-host canvas reach a daemon on
another machine. Swap the transport and the client code does not change.

The [@kolu/surface docs](/surface) teach this end to end: [your first
surface](/surface/your-first-surface), [make it a
daemon](/surface/make-it-a-daemon) (the pattern kaval and padi are built on),
and [across the hosts](/surface/across-the-hosts) (the ssh mirror drishti runs).
The framework is not kolu-shaped: [drishti](https://github.com/srid/drishti) is
a separate app built on the same `@kolu/surface`.

## How a daemon is identified

A daemon is its data folder. padi's identity is its _state-root_, a durable
directory on the host that holds its session, its memory, and its activity feed.
The socket it listens on is named by a digest of that folder and lives in a
scratch directory that is wiped on every boot.

<div class="doc-term">
  <span class="note">// identity: durable, the daemon itself</span>
  <span class="cmd">$KOLU_PADI_STATE_DIR or --state-root</span>
  <span class="note">// production wrappers supply $HOME/.local/state/padi</span>
  <span class="note">// address: config, wiped on boot</span>
  <span class="cmd">$XDG_RUNTIME_DIR/padi-&lt;digest&gt;/sock</span>
  <span class="note"> where &lt;digest&gt; = hash(state-root path)</span>
</div>

- A stale lock cannot make a dead daemon look alive. Its socket lives in the
  boot-wiped directory, gone the moment the machine restarts.
- A dev or test kolu gets its own state-root, so its own padi and its own kaval.
  It cannot touch your production terminals.
- Binding never silently defaults to production's folder: a bare launch dies with
  one line. Production wrappers supply `$HOME/.local/state/padi`, and a client
  never invents the path over the wire.

## Talking over the wire

Everything the browser does flows over a **single WebSocket** (`/rpc/ws`) via
[Effect RPC](https://effect.website/), framed as newline-delimited JSON. The
contract lives in one package both sides share, so calls are type-checked when
kolu is built and their payloads decoded by [Effect
Schema](https://effect.website/docs/schema/introduction/) as they arrive. Two
patterns cover all of it:

<div class="doc-scroll">

| Pattern | Semantics | Used for |
| --- | --- | --- |
| **Request / response** | a one-shot call you await | create a terminal, kill one, restart a daemon, add a host |
| **Subscription** | the server pushes values over the socket as a stream | the terminal list, per-terminal metadata, server state |

</div>

A subscription becomes a fine-grained SolidJS signal on the client, so one row
changing repaints only that row. The shell CLIs are the exception to the
websocket: [`kaval-tui`](/kaval) and [`padi-tui`](/padi) reach their daemon over
its local unix socket, with the same ndjson framing.

### The Conductor's tool endpoint

[The Conductor](/conductor)'s agent needs kolu's own tools, and it gets them
over MCP on a dedicated loopback listener of kolu-server's: `127.0.0.1`, an
ephemeral port, no TLS, one endpoint over streamable HTTP. It is deliberately
not a route on the app listener, which is TLS-able, bound wherever you asked,
and gated for browsers by origin.

Its gate is a **bearer token**, minted fresh for each kolu-server process,
required on every request and compared in constant time. Loopback on its own is
not a gate, because every other process on the box can reach loopback too.
Before opening a conversation against the endpoint, kolu-server makes a real
request to it. A conversation that cannot reach its own tools is refused with a
sentence naming the URL.

<Aside type="caution" title="The RPC surface is unauthenticated, so origin is gated">
  Loopback binding does not defend the socket: an attacker's page runs in your
  own browser. A <strong>same-origin gate</strong> runs before RPC dispatch. It
  rejects a cross-site <code>Origin</code> at the websocket upgrade and 403s a
  cross-site HTTP call. Allowlist a proxy with
  <code>KOLU_ALLOWED_ORIGINS</code>, as the
  <a href="/deployment#allow-a-reverse-proxy-origin">deployment guide</a> shows.
</Aside>

## Three loops of data flow

Three loops drive the system. Terminal input and output is the hot path: your
keystrokes and the screen. The metadata loop is side-channel enrichment: the
git, PR, agent state and output activity that light up the dock. Both run over
the browser's one websocket. The conductor loop is the third, and it touches no
browser at all.

### Terminal input and output

A keystroke goes over `sendInput` to the PTY that [kaval](/kaval) owns.
kolu-server proxies the browser's socket to [padi](/padi), which drives kaval.
Output flows back as an **attach stream**: a screen-state snapshot, then live
deltas. kaval parses the VT sequences itself, so a client joining late gets
about 4 KB of screen state instead of a replayed buffer.

Each connection carries every terminal's stream at once. When one attach stream
stops being read, only that stream waits, and it picks up where it left off. A
reader that falls far enough behind is re-attached with a fresh snapshot rather
than fed the backlog.

A resize is handled the same way: kaval holds the program's redraw back for a
moment, then either delivers it or drops the viewers onto the settled screen.
Both arrive as the attach stream's `overflow` control frame.

A connection's keep-alive ping ends a hop that has carried nothing for a full
minute. Where a watchdog guards a hop it decides first. The browser's counts
any arriving data as progress, the one to a local padi checks that padi's
process is still running, and a remote hop is probed over ssh. There is no
watchdog between padi and kaval.

### Metadata

Every per-terminal sensor lives in padi. A working-directory change (OSC 7)
wakes the git sensor (branch, remote), which wakes the PR sensor (open PR and
CI checks). Agent detection tails each agent's session store. padi folds those
observations into each terminal's record and serves it on one collection the
client reads directly. See [Agent detection](/agent-detection) for the agent
half.

Live output activity comes from a layer down. [kaval](/kaval) sees every PTY
byte and every resize, so it emits a host-global meaningful-output edge, with
resizes excluded, which padi folds into a short live-dot window.

### The conductor loop

kolu-server spawns one ACP adapter (`claude`) and talks [the
protocol](https://agentclientprotocol.com) to it over stdio. The agent calls
kolu's own [MCP tools](/mcp) back over the loopback endpoint, and kolu-server
answers them out of its host map, so `lifecycle_create` on `prod` lands a
terminal in that host's padi. A terminal is named `host/id` on that wire.

kolu-server also starts turns itself. It watches the same host records the dock
is drawn from, and when a watched terminal stops, asks something or leaves, it
mints a wake and runs a turn as your own prompt does. News arriving during a
turn is held and delivered when the turn ends. See [the
Conductor](/conductor).

kolu-server delivers the agents themselves to each host, reading a
content-addressed build off agent-distro's published index and having the host
pull it from the cache. See [Agents](/agents) for what lands and when.

The Nix composition follows the same boundaries. The root flake contains only
the runnable kolu packages, their checks, and the development shells needed to
work on them. The website, the Surface examples, the Solid Browser example and
the Odu CI coordinator each have an independent subflake, so none of them enters
`nix run .`'s evaluation graph. Remote provisioning uses a separate exact-source
flake that exposes only the packages Kolu's agent manifest names.

A dial lands the daemon plus the client CLIs a terminal there must be able to
run (`kaval-tui`, `padi-tui`, `kolu`). So an agent working on a remote machine
can drive its sibling terminals and reach the [MCP server](/mcp) with nothing
installed there. Tool and daemon arrive together, as one build.

## Other machines

The same surface contract runs over ssh. It is how `kolu --host`, and the
[`kaval-tui`](/kaval) and [`padi-tui`](/padi) previews beside it, drive a daemon
on another machine with nothing pre-installed there. Pointing kolu's browser at
a padi on a remote host is a first-class feature: see [Add another
machine](/remote-hosts). That is separate from [From another
device](/remote-access), which serves today's browser UI over private HTTPS.
