`kolu mcp` connects your coding agent (Claude Code, Codex, or any
[MCP](https://modelcontextprotocol.io) host) to your running kolu. The agent
opens a terminal, types a task into it, waits for the reply, reads the screen,
and sees which terminals need you.

<Aside type="caution" title="alpha">
  `kolu mcp` is an early preview. The tool set and wiring may change; the
  driving pattern (create, prompt, wait, read) is stable.
</Aside>

It runs as a small process your agent starts over stdio. With no padi reachable
at startup it exits non-zero before the MCP handshake, so a consumer can test
whether kolu is usable on a host by reading that exit code.
[`kolu surface`](/terminal-ui) projects the same tool table to argv.

## Install the skill and server together

With `kolu` on PATH and a running kolu daemon, install the plugin in Claude Code:

```text
/plugin marketplace add juspay/kolu
/plugin install kolu@kolu
```

Restart Claude Code, then use `/kolu:kolu` for the terminal-driving skill and
`/mcp` to check the server connection.

For Oh My Pi, pass the repository root as the plugin directory:

```sh
omp -e .
```

Use `/skill:kolu` to load the skill. The plugin also registers `kolu mcp`. Keep
your host's environment forwarding configured for `PADI_SOCKET`. Nix consumers
can use `${inputs.kolu}` from a `github:juspay/kolu` input: the repository root
is the plugin, archived with the skill, its reference file and the MCP
configuration.

## Connect it to your agent

<Steps>

1. Put the `kolu` binary on your PATH. The home-manager module does it, and so
   does a kolu terminal (see [Inside a kolu
   terminal](#inside-a-kolu-terminal)). Then register the server:

   ```sh
   # Claude Code
   claude mcp add kolu -- kolu mcp
   ```

   No kolu install? Run it straight from the flake instead:

   ```sh
   claude mcp add kolu -- nix --refresh run github:juspay/kolu -- mcp
   ```

2. Prefer a config file? Add an `.mcp.json` entry, which any MCP host that reads
   that file picks up:

   ```json
   {
     "mcpServers": {
       "kolu": { "command": "kolu", "args": ["mcp"] }
     }
   }
   ```

3. Drive a kolu on another machine by adding `--host`. It reaches the remote
   over ssh, with nothing installed there first.

   ```sh
   claude mcp add kolu-prod -- kolu mcp --host nix@prod
   ```

   `kolu mcp` takes the same endpoint flags every verb does, so `--socket <path>`
   and `--state-root <dir>` name a specific local daemon.

</Steps>

Without a flag, `kolu mcp` picks your everyday kolu over a development or test
one. If it cannot tell, it says what it looked for.

## Inside a kolu terminal

An agent running in a kolu terminal needs no step above, on a remote host as on
your own machine. The terminal is spawned with kolu's own CLIs (`kolu`,
`kaval-tui`, `padi-tui`) on its `PATH`, and with `$PADI_SOCKET` naming the
daemon that owns it. A plain `.mcp.json` with `"command": "kolu"` connects.

Those tools match the daemon's own build. After an upgrade, a terminal you
already have runs the new `kolu` the next time it is used. A terminal opened by
a kolu older than this mechanism has to be reopened once.

In bash and zsh, kolu re-applies its `PATH` entries after your dotfiles run, so
an absolute `PATH=` line in `~/.bashrc` or `~/.zshrc` cannot remove the tools.
In fish and other shells they are only put in the spawn environment, so an
absolute `set -x PATH …` in `config.fish` drops them. Prepend rather than assign
there.

## Drive a terminal

Driving another agent is a loop:

<Steps>

1. Create a terminal (optionally as a split, or in a fresh worktree) and keep
   the `id`.
2. Send the prompt text into it.
3. Wait for the output to settle, then send `Enter` as its own step. Combining
   text and the submit key in one call is a deliberate error, because a
   same-breath `Enter` can race the paste.
4. Wait for the turn to end, then read the screen.
5. Send the next prompt, or kill the terminal.

</Steps>

## How the Conductor's tools differ

[The Conductor](/conductor), the one chat that drives every terminal on every
host, uses this same tool table. `kolu mcp`, this page, serves one host over
stdio and names a terminal by its bare id. The Conductor's copy covers every
host, served inside kolu-server (the process your browser talks to) on a
loopback HTTP listener.

<div class="doc-scroll">

| | `kolu mcp`, one host | the Conductor's, every host |
| --- | --- | --- |
| naming a terminal | `3f29…` | `local/3f29…`, `remote:nix@prod/9a1b…`: the host, then the id, read apart at the last `/` |
| `lifecycle_create` | opens one here | takes the host to open on, answers a fleet reference, and is refused without a `work` and a `role` |
| the repo tools — `git_getStatus` · `git_getDiff` · `fs_listAll` · `fs_readFile` | a repo path | a repo path and the host it is on |
| the waits and the watch | `wait_outputSettled` · `wait_agentState` · `watch_open` · `watch_next` · `watch_close`, all as below | `wait_outputSettled`, hard-capped at a few seconds, plus the work tools below. The rest are not served |
| live views | `terminals` · `urgency` · `daemonStatus` · `status` · `identity` | `terminals` · `urgency` · `hosts` · `works` |

</div>

A turn of the Conductor's stuck in a wait is a person stuck behind it. It opens
a piece of work, says what it has set going, ends its turn, and kolu-server
starts the next one. The capped `wait_outputSettled` survives because typing a
command and submitting it needs the pause between.

`hosts` is the live roster: which machines kolu knows, what each is called, and
whether it is warming, connected or failed. A call naming a host that is not
connected is refused by name, never with an empty list.

`works` is the Conductor reading the pieces of work kolu stores: their members,
where each stands, and any question open with you. The view subscribes, so an
answer given from the card arrives without a call. One terminal's record is
read at `surface://collections/terminals/<host>/<id>`.

## What your agent can do

The name in the first column of each table below is what your agent calls. Every
answer is structured data, alongside text for every tool but `screen_image`,
whose answer is the image.

A refusal carries data when the tool has a machine-readable reason.
`lifecycle_sendInput` labels its four refusals `text-and-key`, `key-refused`,
`text-refused` or `no-input`. `lifecycle_create` labels its directory refusals
(`cwd-and-worktree`, `worktree-needs-repo`, `repo-without-worktree`,
`blank-field`) and the partial-failure report `stopped-partway`. A bad
`placement` is refused by the schema, before any terminal is created.

### Create and drive terminals

| Tool | What it does |
| --- | --- |
| `lifecycle_create` | Open a new terminal and return its `id`. `placement` is required: `{"kind":"toplevel"}` for a tile of its own, or `{"kind":"child-of","parentId":"…"}` for a split inside that terminal. |
| `lifecycle_sendInput` | Type into a terminal: text, or one named key or chord (`Enter`, `Escape`, `C-c`, arrows…), never both in one call. |
| `lifecycle_kill` | Close one terminal by `id`. |
| `agent_say` | Say something to the agent in a terminal, idle or mid-turn. kolu presses that agent's own submit keys, in the order and number it wants. |

`lifecycle_create` also takes a working directory (`cwd`) or a fresh git
worktree (`repo` + `worktree`, cut at `<repo>/.worktrees/<name>`), a canvas
label (`intent`), and a first command (`run`). It does what
`kolu create --toplevel --repo … --worktree … -- <cmd>` does, and the terminal
picks up your [new-terminal theme setting](/theming). A create that fails midway
names the survivors as data.

`agent_say` knows which agent is in the terminal (see [agent
detection](/agent-detection)). It refuses by name for a terminal with no agent,
an agent kolu has no recipe for, an agent that cannot be told anything mid-turn,
and an agent whose screen is still being drawn.

Its answer says whether the words took: for an idle agent, whether it began
working within a few seconds, and if not, that the keys were sent and the screen
is what to read. For an agent already working, how the words were delivered
(steered, or queued behind the turn), which is not observable from outside. The
CLI serves it too: `kolu surface agent_say <id> --text '…'`.

### Wait for the right moment

| Tool | What it does |
| --- | --- |
| `wait_outputSettled` | Block until a terminal's output goes quiet — the turn ended, or it is waiting for input. |
| `wait_agentState` | Block until the terminal's agent reaches a state you name (`working`, `awaiting`, `waiting`) — a precise done-signal, not a guess from silence. |

Both take two extras that turn a three-call routine into one:

- `settledMs` also requires the output to have been quiet that long. Bytes still
  arriving keep the wait open. This tells a finished agent from one whose main
  loop ended while a background helper runs on.
- `screenTail: N` hands back the last N screen lines on the signal itself. A
  later read can catch a screen that has moved on.

`wait_agentState` with `until: ["awaiting","waiting"]`, `settledMs: 15000` and
`screenTail: 40` answers "is this worker's turn really over, and what did it
say?", as [`kolu debrief`](/agent-fleets) does from a shell.

### Watch many terminals at once

The two waits each watch one terminal, while the call is open. A subscription
watches many, between your agent's calls:

| Tool | What it does |
| --- | --- |
| `watch_open` | Start watching — the whole fleet by default, or a named few. You choose the subscription's name. |
| `watch_next` | Block until a watched terminal needs you, then hand over everything since your last call. |
| `watch_close` | Stop watching and discard the queue. |

Anything that happens while your agent is not asking is kept for it, in kolu's
background service, so reopening with the same name picks up where you left off.
Each event says which terminal and why: it is asking for input, it finished its
turn, or it is gone. Leaving `ids` off is the better default: a subscription
scoped to the lanes you remembered goes blind to the one you did not.

#### Report a terminal until you deal with it

A settle event fires once, so an agent that finishes and then waits is reported
then and never again. Optional parameters on `watch_open` replace that with a
level you cannot miss:

| Parameter | What it does |
| --- | --- |
| `states` | which agent states to report — any of `working`, `awaiting`, `waiting`. Defaults to `awaiting` + `waiting`, the two that need somebody |
| `heldForMs` | report a terminal only once it has *held* that state this long. An agent handed more work inside the window is never reported |
| `nagMs` | re-report it every this many milliseconds while it keeps holding. A string spells the same interval, `"30m"`, and a count after the slash caps it: `"30m/3"` is three reminders, then quiet until the state changes |
| `ignoreSelf` | mute the terminal this MCP server runs inside. Refused if the transport cannot identify the caller, or if this server's padi does not know that terminal |
| `ignoreIds` | mute these terminals. Fail-open: a stale id costs nothing, and every new terminal is still watched. An `ids` list that is entirely muted is refused rather than hanging silent |

```json
{ "name": "campaign", "states": ["awaiting", "waiting"],
  "heldForMs": 60000, "nagMs": 300000, "ignoreSelf": true }
```

Such a subscription reports three kinds of event. A snapshot is a terminal
already in that state when you opened, handed over first. A transition is one
that entered the state and held it. A nag is one still holding, an interval
later: it carries `nag.index`, which reminder this is (the first re-report is
1), and `nag.left`, how many follow (`0` on the last, absent when uncapped).

Reopening after a restart leads with a fresh snapshot, and inherits the
episode's spent nag budget. Re-specifying the filter throws away the queued
events and the nag accounting both. Restarting kolu's background service clears
the queue, and says so.

kolu asks each agent for its own state rather than watching its output, so
`heldForMs` times the state, not the screen. The same knobs are [`kolu watch`'s
flags](/terminal-ui).

These parameters report states, so they do not report `gone` when a terminal
disappears. To hear about that, keep a second subscription without them. A batch
is handed over until your agent confirms it, and a queue holds the most recent
512 events; overflow it and the next batch carries a count of what was dropped.

### The Conductor's pieces of work

The Conductor's tools replace the subscription with the **pieces of work**
kolu-server stores: it is woken rather than waiting.

| Tool | What it does |
| --- | --- |
| `work_open` | Open a work: its title, repo and branch, with the setup questions it must ask. The unanswered ones reach you as one form. It answers at once; your answers arrive later as a wake. Refused when a question is missing. |
| `work_ask` | Ask you about a work, under a two-or-three-word header, with options, a box of your own, and the `file` to read. It answers at once; kolu wakes the Conductor with your answer. |
| `work_adopt` | Add a terminal the Conductor did not create, by its `host/id`, with its role in that work. Answers the state it was found in, a baseline rather than news. Refused for a bad reference or a finished work. |
| `work_leave` | Take a terminal out of its work. One that closes leaves by itself, and one the Conductor creates joins without asking. |
| `work_note` | Put a line of plain text on a work's timeline. |

A member terminal starts a new Conductor turn when its agent comes up, stops,
asks, goes or sleeps, and so does an answer of yours. No timer wakes it. [The
Conductor](/conductor) has the rest.

### Read the screen and the code

| Tool | What it does |
| --- | --- |
| `screen_text` | Read a terminal's rendered screen as text; ask for just the last N lines. |
| `screen_image` | See the same screen as a themed PNG, with the colours, box drawing and highlights text throws away. Ask for the last N rows (up to 200), or omit that for the visible screen. |
| `screen_history` | Read the older scrollback above the current screen. |
| `git_getStatus` · `git_getDiff` | The git status and diff for a terminal's repo. |
| `fs_listAll` · `fs_readFile` | List and read files in a terminal's project. |

Your agent's host has to show images for `screen_image`, and CJK and emoji
render as empty boxes.

A terminal you put to [sleep](/sessions) has no live screen. A read or a wait
aimed at one answers "Terminal … is asleep — wake it before reading its screen",
with the id and whether it is `sleeping` or `parked`. An agent either asks you
to wake it or tells you how many are asleep.

### Live views

| Live view | What it shows |
| --- | --- |
| `terminals` | The live roster of your terminals — what is open, what each is running, and each agent's state. |
| `urgency` | Which terminals need attention now — the ones waiting on a human or an answer. |
| `daemonStatus` · `status` · `identity` | Whether kolu's background service is live, up to date, and has not restarted underneath the agent. |

An agent subscribed to `urgency` hears the moment a terminal starts waiting.

## When kolu's background service restarts

An upgrade restarts kolu's background service, and the restart keeps your
terminals running. Your agent does not need to reconnect: the next tool call
opens a new connection, and the terminals it was driving keep their ids.

A local connection is told when the service goes away; with `--host`, `kolu mcp`
finds out by making one call that fails. That call says the connection dropped,
that `kolu mcp` is still running, and that retrying re-opens it. Nothing is
queued or re-sent behind your back.

<Aside type="caution" title="A call that died mid-flight has an unknown outcome">
  "The connection dropped" does not tell you whether the service had already done
  the thing. For a mutating tool (`lifecycle_create`, `lifecycle_kill`,
  `lifecycle_sendInput`), read the `terminals` roster before you repeat it. Reads
  and the `wait_*` tools are safe to retry.
</Aside>

## What an agent cannot touch

`kolu mcp` exposes a reviewed allowlist. Reads and terminal control are in:
creating, driving, killing, and observing terminals. Out: administering the
background service, changing session policy, or rearranging your canvas.
Widening the list is a reviewed change, never a runtime toggle. An agent's
terminals obey your [new-terminal theme policy](/theming), which only your
browser can read or change.
