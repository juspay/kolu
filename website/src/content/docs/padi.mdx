`padi` is the per-host daemon that remembers the memory under kolu — what a Kolu
workspace _is_: terminals, sessions, restore state, repo context, the code tree,
git status, diffs, and agent awareness. It sits above [`kaval`](/kaval), which
owns the live PTYs. The split is simple: kaval keeps shells alive; padi keeps the
workspace legible. The whole layer stack is in [Architecture](/architecture);
padi is a [@kolu/surface daemon](/surface/the-daemon-spine), with the
drain-capable [live recycle](/surface/recycle-and-upgrade) that keeps a client
connected across an upgrade.

## Where it sits

The browser talks to `kolu-server`, the server binds `padi`, and padi supervises
its own `kaval`. Restart the web shell and padi still has the workspace. Restart
padi and kaval still has the PTYs. The layers recover on different clocks because
they own different state.

## What padi knows

kaval only knows terminals. padi is where terminal observations become a
workspace: repo-aware, agent-aware, resumable, and readable from more than one
face.

## The thin shell face — `padi-tui`

`padi-tui` reads the same workspace surface kolu uses. Where `kaval-tui` shows
what's running in each PTY, padi-tui shows what each terminal is in: repo, PR,
checks, foreground command, live byte activity, and agent state. That is the
state behind the [multi-agent dock](/power-features).

```sh
padi-tui status
padi-tui watch
padi-tui wait a3f10000 --until awaiting,waiting
padi-tui create -- claude
```

```text
ID        REPO·BRANCH         PR        AGENT             FOREGROUND        IDLE
a3f10000  kolu·feat/dial-ssh  #1412 ✓   claude · working  node              2s
b7c20000  kolu·master         —         codex · waiting   codex             1m
c9d40000  kolu·fix/fold       #1408 ✗   —                 nvim              5m
```

**Usually no flag.** padi keys its socket by a digest of its state-root, so
inside a kolu terminal `$PADI_SOCKET` makes `padi-tui` flag-less — an agent
driving its siblings never guesses a path. Elsewhere it autodiscovers the running
padi; `--socket <path>` or `--state-root <dir>` point it at a different local
daemon, and `--host <ssh>` reaches a padi on **another machine** — the twin of
[`kaval-tui --host`](/kaval#reach-a-remote-kaval--over-ssh): it provisions the
daemon with Nix, runs `padi --stdio` over ssh, and runs every verb unchanged
against the remote (`padi-tui status --host nix@prod`). Read verbs are safe and
`create` lands a real terminal on the host (which survives the link); a tui is a
dial, so it never drains or converges the remote padi. `--host` is mutually
exclusive with `--socket` / `--state-root`. Pointing kolu's **browser** at a
remote padi is a separate path that already ships — see [Remote
Hosts](/remote-hosts) for adding a machine to the canvas.

`wait <id> --until awaiting,waiting` blocks until a terminal's agent finishes its
turn — a done-signal read from real padi state, not guessed from terminal
silence. For a robust driver, wait in two phases: `--until working` for pickup,
then `--until awaiting,waiting` for turn-end, so a stale previous-turn state
cannot satisfy the wait early. `--timeout <ms>` fails loud (exit 2), a terminal
that exits first exits 3, and `--json` prints `{ id, agent }`. The deeper design
notes live in the [padi atlas note](https://kolu.dev/atlas/padi.html).

| Command | What it does |
| --- | --- |
| `padi-tui status` · `--json` | Print a one-shot workspace snapshot: terminals, repos, agent state, foreground process, and recency. |
| `padi-tui watch` · `--json` | Follow the workspace live, including state changes and activity indicators. |
| `padi-tui wait <id> --until awaiting,waiting` · `--timeout <ms>` · `--json` | Block until an agent turn ends using padi's real agent-state fold, not a guess from terminal silence. |
| `padi-tui create -- claude` · `--parent <id>` · `--worktree <branch>` · `--repo <path>` · `--json` | Create a kolu terminal from the shell: a new tile, a split tile (`--parent`) that opens and selects just like a browser-made split, or a worktree'd agent — all appearing live on the canvas. |

## The agent face — `kolu mcp`

`kolu mcp` is the third face of this same surface. Where the browser is the human
face and [`padi-tui`](#the-thin-shell-face--padi-tui) is the shell face, `kolu mcp`
serves padi to a **coding agent** over [MCP](https://modelcontextprotocol.io) — so
an agent can list the terminals, spawn one, type into it, wait for a turn to end,
and read the screen, all as structured tool calls instead of scraped text. It is a
pure padi client over stdio, with no web server behind it, exposing a
**default-deny** slice of the surface (an unlisted procedure is simply
unreachable). The framework underneath is [`@kolu/surface-mcp`](/surface/expose-to-agents);
[Architecture](/architecture) places the `kolu-mcp` package in the stack.

### How to wire it

<Steps>

1. Put `kolu` on your PATH. The home-manager `services.kolu` module installs the
   binary through its `cliPackage` option — **on by default**, pinned to the same
   build as the running daemon — so `kolu mcp` resolves from any shell. Without
   home-manager, run it straight from the flake (no install):

   ```sh
   # kolu on PATH (home-manager cliPackage)
   claude mcp add kolu -- kolu mcp
   # or, no install — run from the flake
   claude mcp add kolu -- nix --refresh run github:juspay/kolu -- mcp
   ```

2. Or register it as an `.mcp.json` entry — the same stdio server, spelled for any
   MCP host that reads that file:

   ```json
   {
     "mcpServers": {
       "kolu": { "command": "kolu", "args": ["mcp"] }
     }
   }
   ```

3. To drive a padi on **another machine**, add `--host` — the same ssh path as
   [`padi-tui --host`](#the-thin-shell-face--padi-tui), pointed over the wire:

   ```sh
   claude mcp add kolu-prod -- kolu mcp --host nix@prod
   ```

</Steps>

The driving loop itself — spawn a terminal, send a prompt, **wait** for the turn
to end, read the reply, prompt again — is packaged in the `/kolu` agent skill,
MCP-first with the `padi-tui` / `kaval-tui` CLIs as the fallback when no MCP is
connected. Input follows the same discipline as the shell faces: send the text and
the submit key (`Enter`) as **separate** calls, never one, so a same-breath Enter
can't race the paste.

### Tools and resources

The face exposes a reviewed slice of padi's surface. **Resources** are
subscribable live projections; **tools** are one-shot calls (read-only or
mutating). The wire name is what the agent sees.

| Wire name | Kind | What it does |
| --- | --- | --- |
| `terminals` | resource | The live roster — one record per terminal: id, title, command, agent kind + state. |
| `urgency` | resource | The awaiting set — which terminals need a human or agent **now**. |
| `daemonStatus` · `status` · `identity` | resource | Daemon health: kaval liveness, build-currency, and padi's own boot time + build commit — so an agent can **see** "the daemon restarted under me" rather than infer it. |
| `screen_text` | read tool | A terminal's rendered screen as text; `tail` returns just the last N lines. |
| `screen_history` | read tool | Older scrollback above the current screen. |
| `git_getStatus` · `git_getDiff` | read tool | Git status and diff for a terminal's repo. |
| `fs_listAll` · `fs_readFile` | read tool | List and read files in a terminal's workspace. |
| `lifecycle_create` | mutating tool | Spawn a terminal (command, cwd, `parentId` split) and return the `id` to drive. |
| `lifecycle_sendInput` | mutating tool | Write to a terminal — text **or** one named key/chord (`Enter`, `Escape`, `C-c`, arrows…), never both in one call. |
| `lifecycle_kill` | mutating tool | End one terminal by id. |
| `wait_outputSettled` | wait tool | Block until a terminal's output goes quiet — the turn ended / it's awaiting input. |
| `wait_agentState` | wait tool | Block until a terminal's agent reaches a state (`working`, `awaiting`, `waiting`) — the real padi fold, not guessed from silence. |

Everything else on the surface is denied by default: raw byte-stream attach,
`lifecycle.killAll` and other daemon-admin verbs, and worktree provisioning
(`padi-tui create --worktree` stays the path for that). Widening the slice is a
reviewed one-line change, never a runtime knob.

## Why it is not inside kolu-server

The web server is a face: HTTP, assets, websocket transport. The workspace is a
daemon: durable folder, terminal registry, session restore, agent awareness.
Keeping those apart means a deploy can replace the web shell without making the
workspace disappear.
