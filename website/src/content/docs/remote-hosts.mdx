kolu runs terminals on other machines over ssh and puts them on your canvas as ordinary tiles. The canvas shows one host at a time, and a row of host tabs switches between them live. Each host keeps its own arrangement.

To reach the kolu app itself from another device, see [From another device](/remote-access).

## What a host needs

<CardGrid>
  <Card title="Passwordless ssh">
    You can `ssh` to the host without typing a password, through an `~/.ssh/config` alias or a `user@host`. kolu dials non-interactively, so a host that asks for one [says so](#when-a-host-is-down).
  </Card>
  <Card title="Nix on the remote">
    The host has [Nix installed](https://nixos.asia/en/install), and `nix` runs from a non-interactive ssh session, not only a login shell. On a Mac, make your user trusted by its nix-daemon (`trusted-users`).
  </Card>
  <Card title="A Nix-wrapped kolu">
    Launch kolu through its Nix wrapper, which bakes in the [padi](/padi) build it deploys. kolu asks the host for its CPU and OS, so a macOS kolu can bind a Linux box.
  </Card>
</CardGrid>

## Add a host

<Steps>

1. Click **+ add** on the host row. It needs nothing set up first.
2. Type the target: an `~/.ssh/config` alias such as `zest`, or a destination such as `srid@zest`.
3. Press <kbd>Enter</kbd>. The host joins the row as a chip and the canvas switches to it.

</Steps>

A host you add is remembered: it returns after a kolu restart and reconnects on its own. The only way a host leaves is your own **remove**; one that has gone away comes back as a failed chip with the reason.

Your local machine is the first chip and cannot be removed. Typing `localhost`, `127.0.0.1` or `::1` selects it. `user@localhost` is a real remote: the loopback as another user is a different session.

### Pre-seed hosts at launch

Use this when you want a host present without clicking anything: a scripted launch, a shared dev box, a fresh profile. Set `KOLU_PADI_HOST` to a comma-separated list of ssh targets:

```sh
KOLU_PADI_HOST=localhost,you@box kolu
```

Your local host is first in the pool either way.

## First connect

The first time you switch to a host that has never run padi, kolu sets it up over ssh: one Nix operation finds the build the host needs, copies it over and installs it there. A first setup can take minutes.

| How kolu runs | Where padi comes from |
| --- | --- |
| the home-manager module | the build is already installed alongside kolu, so the copy starts at once and the host never compiles |
| `nix run` or `nix profile install` | the [binary cache](/deployment#first-run-compiling-enable-the-binary-cache) first, and a build when the cache does not have it |

A Linux host usually needs no extra setup: its Nix accepts padi from any user when it is Nix 2.17 to 2.34, or when it and kolu's own machine both run Nix 2.35 or newer. Otherwise, and always on a Mac, the host's nix-daemon must trust your login: add your user to `trusted-users` in its Nix configuration.

What lands is padi plus `kaval-tui`, `padi-tui` and `kolu` itself. They are on `$PATH` in every terminal kolu opens there, with `$PADI_SOCKET` set, so an agent can drive its sibling terminals and use the [MCP server](/mcp) at once.

[AI coding agents](/agents) and your profiles are delivered separately when a host first connects, and kept current. See [Agents](/agents) for what a host needs and what a failed delivery says.

### While it connects

The canvas narrates a cold connect: the phase, a live tail of Nix's output, a large transfer's bytes, and a timer that climbs while the log is quiet. **Copy** copies everything the session kept.

If nothing arrives for long enough, kolu stops narrating and shows a card:

| What stalled | What the card offers |
| --- | --- |
| a remote still probing or provisioning | the phase, the last line printed, and how long nothing new arrived. **Retry connection** re-dials from the server, which a browser reload cannot do, and **Switch to local** |
| something that never reached this tab: the host list, your saved session, a host's agent status | what did not arrive, with **Reload**, and **Switch to local** on a remote |
| this browser's own link to kolu | **Disconnected from server · Reconnecting…**, and no claim about any machine |

A local machine whose own agent fails to start has its own ["kaval didn't start" card](/kaval).

The kolu server log keeps every line the tail shows, including Nix's error and a failed build's last lines. To read that build's whole log, run the `nix log` command the error names, on the host.

## Host tabs and the connection pip

Each host is a tab: local shows a Home icon and this machine's hostname, a remote its ssh target. Every tab carries a pip for the whole chain, kolu to that host's padi to its kaval.

| Pip | Meaning |
| --- | --- |
| green | kolu reaches the host and its terminal daemon is serving |
| amber, pulsing | connecting or provisioning |
| amber, "kaval down" | kolu reaches the host, but its terminal daemon is not serving. [padi restarts it for you](/padi#when-kaval-stops-answering); the tooltip carries the daemon's verdict |
| red, label struck through | failed. Open diagnostics for the error, and retry |

A host that answers kolu's watchdog in time keeps its connection however slow it is. One that is powered off or off the network is noticed in about 25 to 30 seconds, and kolu reconnects when it is back.

Click the pip for diagnostics: connection state, terminal and awaiting counts, that machine's agents, padi and kaval detail, and remove-with-confirm.

## Switch hosts

| What you do | What happens |
| --- | --- |
| click a tab | the canvas switches to that host, live |
| <kbd>Cmd</kbd>/<kbd>Super</kbd> + <kbd>K</kbd>, then a host name | hosts are root results in the [switcher](/switcher) |
| <kbd>Mod</kbd> + <kbd>Shift</kbd> + <kbd>H</kbd> (**Mod** is <kbd>Cmd</kbd> on a Mac, <kbd>Ctrl</kbd> elsewhere), or the search icon in the host bar | the scoped host list, with the machine you came from highlighted, so the chord then <kbd>Enter</kbd> hops between two machines |

Each host owns its canvas: its terminals, splits and focused tile come back as you left them, and its work keeps running while you are away. If the active host leaves the pool, kolu switches you to local.

A tab also carries that host's attention counts, violet for needs-you and amber for unread. Clicking the violet count jumps to the agent that is waiting, and an [installed PWA](/install-pwa) badges the awaiting count across hosts. See [Notifications](/notifications) for what each signal means.

### Put the tabs in your own order

Drag a host tab along the strip to move it. The tab lands where you dropped it and everything else keeps its relative order, including machines folded into the **⋯ +N** overflow. A drag neither switches host nor opens diagnostics.

The order is saved on the server, so every browser, device and other list of machines shows it. A machine you add joins at the end, and your own machine is pinned first.

## One Conductor, every host

[The Conductor](/conductor) is one conversation, on the machine running kolu-server, and its tools reach every host in your pool. Its tab comes first in the tab row.

## When a host is down

When a host's [padi](/padi) cannot bind, its canvas is replaced by a card naming the cause, with **Reconnect** (a real re-dial, once you have cleared the cause) and **Switch to local**.

When the attempt printed anything, the card shows its last lines under the error, in the words of the tool that hit it. So does the diagnostics popover.

| Card | What happened |
| --- | --- |
| **Another kolu owns this host** | another kolu supervisor already holds this host's padi |
| **This host runs an older kolu** | the padi there speaks an older contract and refused to bind |
| **This host runs a kolu from before the protocol change** | kolu cannot ask that padi which protocol version it speaks. Update that machine's kolu, or stop the padi there |
| **This host needs passwordless ssh** | the host asked for a password. Set up key-based access (`ssh-copy-id`) |
| **This host isn't trusted yet** | ssh does not recognize the host's identity key. Run `ssh <host>` once to accept it, or to clear a changed-key warning |
| **This host has no Nix that kolu can run** | the shell could not run `nix-instantiate`: Nix is missing, or off a non-interactive session's PATH |
| **Connecting to this host kept stalling** | a step went quiet too many times, a stalled download included. The detail names the step |
| **Kolu couldn't set up this host** | bringing padi up there kept failing. The detail is the error |
| **This kolu run is missing its agent source** | kolu was not launched through its Nix wrapper, so it has nothing to deploy |
| **Kolu couldn't prepare padi for this host** | the host's Nix did not report its CPU and OS (often a startup file writes to stdout), or the baked source could not resolve padi |
| **This host's padi never settled** | a contract upgrade's drain never provably finished |

A separate card covers the host's [kaval](/kaval). When its kaval speaks an incompatible wire contract, the canvas names both versions and offers **Update & restart kaval** behind a confirm.

## Port forwarding

A dev server on a remote host listens on that machine's loopback, which never leaves the machine it is on: `http://127.0.0.1:5173` in your browser means your own machine. Click the port and kolu forwards it (opens a **door**, a port on the machine running kolu that reaches the server), then opens the tab.

The [Inspector's **Ports** section](/right-panel#ports-the-terminal-is-serving) lists what each terminal is serving, read from the host's socket table.

### What a click opens

kolu reads the port's bind address and picks the mechanism. Nothing to configure.

| Where the server listens | What kolu does | What opens |
| --- | --- | --- |
| a remote host, on loopback | `ssh -L` over a connection of its own | `http://<the kolu host>:<port>` |
| kolu's own machine, on loopback | a plain TCP relay | `http://<the kolu host>:<port>` |
| kolu's own machine, all interfaces | nothing: it already answers | `http://<the kolu host>:<port>` |
| a remote host, one specific interface | nothing it can do | the row says "not reachable" |

Both mechanisms reach the far side's loopback, so a port bound to one named interface of a remote machine is out of reach, and kolu says so.

You get the same port number back whenever it is free, so a saved link survives a restart. When it is taken, the row shows the one you got.

### Open and close doors

A forwarded port is one row wherever it appears, with a teal `⇄ :<port>` pill naming where it answers, a copy button, and a `⨯` that closes the door. The rows are in the Inspector's Ports list, the host tab's dropdown and the connection pip, and each links to the terminal serving it.

<Steps>

1. **Open one by clicking it.** Any port row that needs a door offers **forward & open**. Doors open only for ports you click, and close when the scanner sees the listener die.

2. **Or forward a port kolu never saw.** <kbd>Cmd</kbd>/<kbd>Super</kbd> + <kbd>K</kbd> → **Forward a port…**, then `host:port`, or just a port for the host you are looking at. Use it for a port kolu's scan cannot see.

3. **Close it when you are done.** Click `⨯` on the row. A forward you asked for by hand stays until you cancel it or its host leaves.

</Steps>

A door onto a server no terminal holds, such as one you opened by hand, sits under **elsewhere on this host** in the Ports list, and stays visible while that group is folded.

Every door dies with the kolu server, guaranteed by the kernel rather than by a timer, so a deploy or a crash leaves none open.

### A printed `localhost` URL

Agents print `http://localhost:5173/` and its relatives (`127.*`, `[::1]`, `0.0.0.0`) constantly. In your browser that hostname is your own machine, not the host running the server. Click a loopback URL and a card appears at the cursor: it names what on the host listens on that port and offers **forward & open** and copy, carrying the printed path through the door. When nothing listens there, it says so.

<kbd>Cmd</kbd>/<kbd>Ctrl</kbd>-click opens the raw URL with no card. The card is live: leave it open while a server starts and it upgrades when the listener is real.

<Aside type="caution" title="A forwarded port is unauthenticated">
The door kolu opens is plain TCP on every interface of the machine running kolu, the same exposure as starting the dev server on `0.0.0.0` yourself. Anyone who can reach that machine can reach the forwarded service. Keep it to a network you trust.
</Aside>

## Known limitations

A kolu remote terminal is an ssh session, not the machine's GUI login session, so tools that lean on that session behave differently.

| Symptom | Why | Remedy |
| --- | --- | --- |
| on macOS, `gh` reports **`The token in default is invalid`** | `gh` keeps its token in the login Keychain, unlocked only for the GUI session | a `$SSH_CONNECTION`-guarded `GH_TOKEN` (a scoped [fine-grained PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token)), or [`security unlock-keychain`](https://ss64.com/mac/security.html), or [`gh auth login --insecure-storage`](https://cli.github.com/manual/gh_auth_login) |
| `git push` or clone fails `Permission denied (publickey)` | the session forwards no agent: your keys live in the local session, and kolu passes no `-A` | put `ForwardAgent yes` for the host in `~/.ssh/config` and reconnect (see [Forwarded ssh-agent](#forwarded-ssh-agent)) |
| `pbcopy`, `pbpaste`, `launchctl` and desktop notifications do nothing | these are GUI-session services | run them from the box's own terminal; for `launchctl` name the domain: `launchctl print gui/$(id -u)` |
| a command is "not found", locale warnings, missing `$PATH` | ssh starts a leaner login shell | put `PATH` and locale in the rc both shells read (`~/.zshrc`); check with `echo $PATH` and `locale` |

This table grows by incident. If you hit a case that is not here, add a row.

## Forwarded ssh-agent

kolu dials ssh itself and passes no `-A`, so your `~/.ssh/config` stays the authority. Set forwarding there and reconnect:

```sh
# ~/.ssh/config
Host box
  ForwardAgent yes
```

kolu then hands your forwarded agent to every terminal it opens on that host, so `git push` and a further `ssh` hop work there. Each reconnect re-points the link it arrives on, so terminals opened under an earlier connection heal. `ssh-add -l` lists the keys a terminal can reach; an empty answer means no agent was forwarded.
