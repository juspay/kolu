Kolu can bring the AI coding agents along — **Claude Code, Codex, OpenCode, Pi
and Oh My Pi** — kept up to date, with nothing for you to install. Kolu asks
which set you want ([First run](#first-run)); pick one, open a new terminal and
type `claude`: it runs, and so do the others. Each one starts with kolu's own plugin loaded, so it can drive your
other kolu terminals out of the box. Agents you installed yourself keep working:
kolu's come first, yours stay as the fallback.

You choose between the sets kolu ships — today **vanilla** (the stock agents)
and **juspay** (Juspay's). Settings says what each one is, in a sentence, the
moment you look at it ([Pick a set](#pick-a-set)).

Until you choose, nothing changes: kolu adds no agents to your terminals until
you pick a set, on a fresh install and on one that predates this. The agents come from
[agent-distro](https://github.com/juspay/agent-distro), a distribution of coding
agents that kolu pins and ships; agent-distro calls each set a **profile**.

## First run

Until agents are on, kolu asks in three places:

- the **welcome card**, whenever no terminals are open — the question leads it:
  **Choose your coding agents**;
- the palette's **Tutorial** command, which shows the same welcome at any time;
- **Settings → Agents**, at any time, which says when nothing is chosen yet.

It is the same choice everywhere — **Off**, or one of the sets. Until agents are
on, the welcome card keeps the choice at the top; pick **Off** and it stays
there, with no agents added. If you upgraded and your session brings your terminals back, you will not see the
welcome card: your terminals have no agents until you choose in Settings or the
Tutorial.

Until you pick anything, the choice already has the keyboard: press **Enter** to take
**vanilla**, the stock agents; **←** and **→** move to **Off** and **juspay**, and
the line under the choice says what each one means as you move. Once you pick a
set, the question folds away into the welcome's done line — "Agents: vanilla ✓".
On the machine running kolu that is at once, because the agents ship inside
kolu; it stays only while that machine is still downloading them, or if that
download failed.

Pick **Off** and the question stays, with **Off** pressed. It no longer takes
the keyboard when the welcome card appears, so an **Enter** out of habit
changes nothing. When you tab into it, the keyboard lands on **vanilla**, so
**Enter** there turns agents on.

Nothing forces the question. **⌘⏎** still opens a terminal from anywhere; it just
gets no agents, and the question stays until agents are on.

## Pick a set

To change it later, open **Settings** (the gear in the top bar). One row, **Agents**, sets it:
**Off**, or one of the sets the pinned agent-distro ships. Picking a set turns
agents on with it; **Off** turns them off. Either way kolu tells you what changed
for new terminals.

The hint under the row says where things stand: with Off, what kolu can bring
and what Off means (and, before your first choice, that nothing is chosen yet); with a set chosen, what that set is and which agents (with
their versions) it puts on your terminals. Hover a choice for agent-distro's own
description of it.

With a set on, under the hint is one status line per machine, each named the way
its host tab names it (the machine running kolu by its hostname) — the machine
running kolu first, then every other host that is not ready yet, is updating,
whose last look for newer agents failed, or whose update history kolu could not
read — each with a bar that fills while that machine downloads, turns to the
warning colour if the download failed, and stays empty until the machine has
answered. Under a ready line, a quieter one says when that machine last looked
for newer agents ("updated 3h ago", "checked 2h ago, up to date", "last update
failed 1h ago"), or that it is updating now; hover it for the reason a look was
skipped or failed, and who gave it — agent-distro, or kolu itself when
agent-distro gave none. When every machine is ready with nothing to report, the
lines fold into one, **all hosts**, with how many there are. Below them sit
**Check now** and the **History** ([Kept up to date](#kept-up-to-date)).

The setting is one for all of kolu — not per host, not per terminal.

## A profile of your own

Besides the sets kolu ships, **Custom** takes a profile of your own: an
`agent-distro.nix` in any git repository, named by a flake reference
(`github:you/your-profile`) or by a path to its directory
(`~/src/my-profile`). Pick **Custom**, type the reference and press **Enter**
(or **Use**). Anything without a `/` or a `:` is refused right there, since it
would read as the name of a built-in set.

kolu does not read the reference itself. New terminals get the stock
(**vanilla**) agents with the reference as `AI_PROFILE`, and agent-distro
resolves it when you launch an agent. It is a **fallback**: agent-distro picks
the profile in this order —

1. one you name on the command line (`agent-distro <reference>`),
2. the `agent-distro.nix` of the repository you are in (looked up from the
   folder you are in to the repository's root),
3. `AI_PROFILE` — the setting's reference,
4. the built-in set.

So inside a repository that carries its own `agent-distro.nix`, that one wins,
whatever the setting says. Each tile's pill tells you which one is in effect
there ([below](#new-terminals-only-and-each-one-says-which)).

## New terminals only, and each one says which

A change applies to the **next new terminal**. A terminal that is already open
keeps exactly the agents it started with: kolu puts the exact build of that set
on its PATH, so a later switch (or a newer build arriving) never changes a
running agent under you — until you **Restart** it (below).

Every tile shows which it got: a small pill in the tile's title bar with the
profile and a short hash of the build. Two tiles with different pills started
with different agents; **no pill** means agents were off when that terminal
started.

The profile on the pill is the one **in effect** in that terminal: right after
the terminal starts, kolu asks agent-distro once, in the terminal's folder and
with its environment, and shows its answer — a repository's own profile, the
setting's reference, or the built-in set. Hover the pill to see where it came
from. Until agent-distro answers (or if it cannot), the pill shows the
setting's choice. It is asked once per terminal: `cd` into another repository
and the pill keeps naming the profile from where the terminal started, though
an agent you launch there follows agent-distro's own order.

In a terminal with agents, a bar under the tile's title bar points at the next
step — a button for each agent of its set to launch, then a skill to try at its
first prompt — and the buttons type it for you ([A tip under the title bar](/tiles#a-tip-under-the-title-bar)).

## Restarting a terminal onto the current agents

When a terminal's agents are no longer what a new terminal there would get — you
picked another set or another reference, turned agents off, or a newer build of
the same set arrived —
its pill dims and becomes a **Restart** button. Hover it to see what the terminal
has and what new terminals get. While that machine is still downloading the set,
or its download failed, new terminals there get no agents — so the pill says so
and offers no Restart yet: restarting then would leave the terminal with none.

Restart gives the terminal a fresh shell in place — the same tile, folder, splits
and theme — with the current agents. With agents still on, the agent's
conversation resumes on the new agents, and any other program in the terminal
ends. With agents now off it comes back as a plain shell, and the agent ends too.
If an agent is working or waiting for you, the first click only asks; a second
click within a few seconds confirms. The old shell is stopped the way sleep stops
it — killed outright — so it does not write its history file, and anything you
started with `nohup` keeps running.

## Where they sit on the PATH

With agents on, a new terminal's PATH reads, from the front:

1. kolu's own tools (`kolu`, `kaval-tui`, `padi-tui`),
2. the chosen set's agents,
3. your own PATH — including anything your shell's dotfiles add.

So the bundled `claude` wins over one you installed yourself. That is on purpose.
kolu re-applies this order after your `.bashrc` / `.zshrc` run, so neither a
dotfile that sets `PATH` outright nor one that puts its own directory first
(`export PATH=$HOME/.local/bin:$PATH`, as Claude Code's own installer writes)
undoes it (bash and zsh; other shells get the order at spawn only — see
[Shell integration](/shell-integration)).

To run your own `claude` in a kolu terminal, turn Agents off, or call it by its
full path.

The chosen set also brings a command, **`agent-distro`**: type it to see the
set this terminal has (agent-distro calls it a profile), its agents,
their versions and whether each is signed in, or to launch one. It comes from the same build the tile's pill names, so what
it lists is exactly what this terminal has — on the machine running kolu and on
every host alike. It knows only this terminal's
set: to switch sets, use [Settings](#pick-a-set).

## On other machines

Agents work the same on every host you [add](/remote-hosts), but nothing is
copied over ssh — a [profile of your own](#a-profile-of-your-own) included: a
flake reference is fetched by each host, and a **path** names a folder on that
host, so it works only where that folder exists. The first time a host is used with agents on, that host
**downloads them itself**, from agent-distro's binary cache into its own Nix
store, and kolu tells you when they have landed. Terminals opened on that host
before then have no agents (and no pill).

Every host tab with agents on carries agent-distro's mark right after the host
name, and the mark's look says where that host stands:

| The mark | Means |
| --- | --- |
| plain, in the tab's text colour | ready for new terminals |
| a thin ring around it, filling up | downloading — hover for the progress |
| plain, with the ring filling | ready, and a newer set is downloading; the current one keeps serving ([Kept up to date](#kept-up-to-date)) |
| warning colour with a small dot | the download failed — hover for why ([below](#when-a-download-fails)) |
| dimmed, with a spinning arc | checking: the host is connected but has not said yet |
| no mark at all | agents are off |

Clicking the mark opens Settings, without switching tabs.

The machine running kolu itself needs no first download: every set ships inside
kolu, so switching there is instant and works offline. It still keeps itself
up to date like any other host (below); the set kolu shipped with is what it
falls back to when it has never been online.

<Aside type="note" title="Disk">
  A host keeps its downloaded bundle in its own Nix store (and the machine
  running kolu also carries the bundles kolu ships). If you also install
  agent-distro on a host through its Home Manager module, both share the same
  downloaded bundle for the same set. Only the newest set is protected from
  Nix's garbage collection: after an update, the one before it can be removed,
  even while a terminal opened before the update still has it on its PATH.
</Aside>

## Kept up to date

agent-distro publishes a newer tested set of agents up to four times a day. At
those times — 02:00, 08:00, 14:00 and 20:00 UTC, agent-distro's own schedule —
every machine with agents on looks for a newer build of the set you chose, and
downloads it if there is one. Only the chosen set is kept current; switching
sets downloads the new one as before. A machine that was asleep through one of
those times looks once within minutes of waking. And whenever a newer kolu
reaches a machine with agents on, or that machine reboots, it looks once right
away, so a newer kolu brings the newer agents with it. A look that fails — the
machine was offline, say — tries again up to twice, five minutes after the
failed look ended, as agent-distro's own schedule does; that includes a look
at start that was due anyway, while one taken only because kolu is newer, or because the machine restarted, waits
for the next of those times.

Nothing is ever compiled. A newer set is downloaded only once agent-distro's
cache holds all of it; until then the machine skips it and looks again at the
next time.

While a newer set downloads, the one you have keeps working: new terminals get
it until the new one has fully arrived. The host's mark keeps its plain colour
and the ring fills around it; its line in Settings says "updating" with the
progress. Then:

- a toast says what changed, in agent-distro's own words ("Claude Code 2.1.286
  → 2.1.291"), and on which machine;
- new terminals there start with the new set — `agent-distro` included, since
  it comes in the same build;
- a terminal already open keeps its own, and its pill offers **Restart**
  ([above](#restarting-a-terminal-onto-the-current-agents)).

A look that finds nothing newer, or skips (the newer set is not fully in the
cache yet, or the machine's Nix cannot use the cache), says nothing; the host's
line says it was skipped, and its hover and the History give agent-distro's
reason. A skip is not a problem, so once every machine is ready it folds into
the **all hosts** line like a look that found nothing, and shows only in the
History. A look that fails says nothing either — the agents you have keep
working — and the host keeps its own status line saying so, even when every
other machine is ready (and it is in the History, when agent-distro wrote it
down: a run that crashed did not, so its line's hover gives kolu's words for
it).

A terminal keeps the set it started with until you restart it — or until a Nix
garbage collection on that machine removes that set, which an update leaves
unprotected. **Restart** gets the current set.

In **Settings → Agents**:

- **Check now** looks for newer agents on every machine at once, whatever the
  time. It is greyed out while there is no machine it could ask — every
  connected one is already looking, or not ready yet — and reads "Checking…"
  while one of them is looking.
- **History** lists each machine's last five events — updated, skipped or failed —
  one line each, with the time and agent-distro's own words (hover a line for
  all of them). A machine whose update history kolu could not read gets a line
  saying so. The list scrolls once it is long, so Settings stays on screen
  however many machines you have.

## When a download fails

The host needs Nix with flakes, reachable on padi's PATH, and its Nix must be
allowed to use agent-distro's cache (`https://cache.nixos.asia/oss`). If it is
not, the first download is skipped — the host never compiles agents — and the
host's mark turns to the warning colour. (A later update that cannot download
is different: the agents the host already has keep working, and it shows on the
host's status line and in the History — see [Kept up to date](#kept-up-to-date).) Its hover, the toast and the host's line in
Settings all say the same thing: the cause, the setup fix when the cause is a
missing `nix`, and how to retry. Until it is fixed, new terminals on that host
get no agents. Fix it, then switch Agents off and back on in Settings: that is
the retry, and it downloads again. Nothing retries on its own.

## Turning it off

Settings → **Agents** → **Off**. From the next new terminal on, on every host,
kolu adds no agents and no plugin variable; your own tools are what run.
Terminals already open keep what they have, and keep their pill, until you close
them (or restart them, which brings them back as a plain shell). While agents
are off, the welcome card keeps the choice at the top of every empty canvas.

## What doesn't change

[Agent detection](/agent-detection) works the same either way: kolu watches the
agent running in a terminal, whichever `claude` it is.
