Kolu can bring the AI coding agents along — **Claude Code, Codex, OpenCode, Pi
and Oh My Pi** — kept up to date, with nothing for you to install. Kolu asks
whether you want them ([First run](#first-run)); switch them on, open a new
terminal and type `claude`: it runs, and so do the others. Each one starts with
kolu's own plugin loaded, so it can drive your other kolu terminals out of the
box. Agents you installed yourself keep working: kolu's come first, yours stay
as the fallback.

Switched on, new terminals get **Vanilla**, the stock set kolu ships — the card
marked **Default**. **Juspay**'s profile is one click away on its own card
(`github:juspay/skills`, shown under the name), and **Custom…** takes a profile
of your own ([A profile of your own](#a-profile-of-your-own)). You pick a set by
name; a flake reference belongs in one place only, inside Custom….

Until you choose, nothing changes: kolu adds no agents to your terminals until
you switch them on, on a fresh install and on one that predates this. The agents
come from [agent-distro](https://github.com/juspay/agent-distro), a distribution
of coding agents that kolu pins and ships; agent-distro calls each set a
**profile**.

## First run

Until agents are on, kolu asks in three places:

- the **welcome card**, whenever no terminals are open — the question leads it:
  **Choose your coding agents**;
- the palette's **Tutorial** command, which shows the same welcome at any time;
- **Settings → Agents**, at any time.

The welcome card and the Tutorial ask with the cards themselves — the sets kolu
names, **Vanilla** picked for you — and two buttons: **Turn on ⏎**, and **Not
now — plain terminals, ask again later**. Until you choose, the picked card
already has the keyboard: press **Enter** and agents are on with Vanilla. Move
to another card first (←/→/↑/↓, or click) and Turn on takes that one; nothing is
written until you press it, so a card here is a choice, not a switch. A profile
of your own stays a Settings matter.

The question then folds away into the welcome's done line — "Agents: Vanilla ✓",
a name, never a flake reference — once agent-distro says the profile resolves on
this machine; if it does not, agent-distro's words stand there instead of the
check ([A profile of your own](#a-profile-of-your-own)). On the machine running
kolu that is at once, because the agents ship inside kolu; it stays only while
kolu is still delivering them to that machine, or if that delivery failed.

**Not now** chooses nothing: no preference is written, no agents are added, and
the question only goes for this session — the next time the welcome card appears
it asks again.

Until agents are on, the welcome card keeps the question at the top: switch them
off again in Settings and it comes back. Once you have chosen, it no longer takes
the keyboard when the welcome card appears, so an **Enter** out of habit changes
nothing. If you upgraded and your session brings your terminals back, you will
not see the welcome card: your terminals have no agents until you switch them on
in Settings or the Tutorial.

Nothing forces the question. **⌘⏎** still opens a terminal from anywhere; it just
gets no agents, and the question stays until agents are on.

## Pick a set

To change it later, open **Settings** (the gear in the top bar). One row,
**Agents**, holds all of it: a switch, on or off, and while it is on, the
**profile cards**. Either way kolu tells you what changed for new terminals.

The cards name the sets; nobody types a reference to pick one:

- **Vanilla**, marked **Default** — the stock agents kolu ships, and where a
  kolu nobody has asked yet starts;
- **Juspay** — `github:juspay/skills`, shown under the name: Juspay skills plus
  Kolu, through Juspay's LiteLLM gateway;
- **Custom…** — a flake reference or a path to your own `agent-distro.nix`
  ([A profile of your own](#a-profile-of-your-own)).

Click a card, or move with ←/→/↑/↓ and press **Enter**: that is the setting, at
once, for new terminals on every machine.

Under the cards sit the agents that set brings, one **chip** each with the
version this machine has, and the note that a repository with its own
`agent-distro.nix` overrides the choice. While agents are off the chips name the
stock set without versions — nothing is installed yet — and the hint above them
is one sentence: "Off. New terminals use only the agents you installed yourself.
Turn on and they start with these, kept up to date:".

Below them is one **fleet line** for every machine at once — "Ready on
naiveintent and 2 more · buildbox delivering · devbox failed", a coloured dot
per state. Each machine's name is a link that opens that machine's **host
details**, where everything true of that machine lives: the build it serves, its
state and last update, its own events and its own actions
([On other machines](#on-other-machines)). Settings keeps no per-machine state of
its own.

The row ends with **Docs →** and **Provided by agent-distro ↗**.

The setting is one for all of kolu — not per host, not per terminal.

## A profile of your own

Besides the sets kolu names, **Custom…** takes a profile of your own: an
`agent-distro.nix` in any git repository, named by a flake reference
(`github:you/your-profile`) or by a path to its directory
(`~/src/my-profile`). Use an absolute path or one starting with `~/`: every
terminal gets the profile whatever folder it opens in, so a relative path would
mean a different folder in each.

Picking Custom… reveals the field that used to be this control: a text input,
with a menu of the profiles you set before, most recent first ("used before") —
the sets kolu ships are cards, so the menu never repeats them. Type one and
press **Enter**, or pick a row: that is the setting. Escape, or leaving the
field, puts the stored profile back, so a half-typed reference is never written.
kolu writes whatever you type; whether it resolves is agent-distro's to say,
under the field.

Under the field, the machine running kolu says whether the profile resolves. It
asks agent-distro once, the same way a terminal's agents would, and shows
agent-distro's name and description for it ("juspay · Juspay skills + Kolu"). If
it does not resolve, the line is agent-distro's own words, in red, such as
"agent-distro: AI_PROFILE=github:nobody/nothing: cannot fetch
github:nobody/nothing: … HTTP error 404". The setting stands even then: new
terminals still get that profile, and their agents will not start until it
resolves — except in a repository with its own `agent-distro.nix`. Fix the field
and it asks again.

kolu does not read the profile itself. New terminals get the stock
(**vanilla**) agents with the profile as `AI_PROFILE`, and agent-distro
resolves it when you launch an agent. It is a **fallback**: agent-distro picks
the profile in this order —

1. one you name on the command line (`agent-distro <reference>`),
2. the `agent-distro.nix` of the repository you are in (looked up from the
   folder you are in to the repository's root),
3. `AI_PROFILE` — the setting's profile,
4. the built-in set.

So inside a repository that carries its own `agent-distro.nix`, that one wins,
whatever the setting says. Each tile's pill tells you which one is in effect
there ([below](#new-terminals-only-and-each-one-says-which)).

Opening a terminal in a repository runs that repository's `agent-distro.nix`
through agent-distro, before you type anything, to tell the pill which profile
is in effect. A repository's profile brings its own plugins and MCP servers, so
only open terminals in repositories you trust, as with a `.envrc`.

## New terminals only, and each one says which

A change applies to the **next new terminal**. A terminal that is already open
keeps exactly the agents it started with: kolu puts the exact build of that set
on its PATH, so a later switch (or a newer build arriving) never changes a
running agent under you — until you **Restart** it (below).

Every tile shows which it got: a small pill in the tile's title bar with the
profile and a short hash of the build. Two tiles with different pills started
with different agents; **no pill** means agents were off when that terminal
started.

The profile on the pill is the one **in effect** in that terminal: right after
the terminal starts, kolu asks agent-distro once, in the terminal's folder and
with its environment, and shows its answer — a repository's own profile, the
setting's profile, or the built-in set. Hover the pill to see where it came
from. Until agent-distro answers (or if it cannot), the pill shows the
setting's choice. It is asked once per terminal: `cd` into another repository
and the pill keeps naming the profile from where the terminal started, though
an agent you launch there follows agent-distro's own order.

In a terminal with agents, a bar under the tile's title bar points at the next
step — a button for each agent of its set to launch, then a skill to try at its
first prompt — and the buttons type it for you ([A tip under the title bar](/tiles#a-tip-under-the-title-bar)).

## Restarting a terminal onto the current agents

When a terminal's agents are no longer what a new terminal there would get — you
named another profile, turned agents off, or a newer build of
the same set arrived —
its pill dims and becomes a **Restart** button. Hover it to see what the terminal
has and what new terminals get. While kolu is still delivering the set to that
machine, or the delivery failed, new terminals there get no agents — so the pill says so
and offers no Restart yet: restarting then would leave the terminal with none.

Restart gives the terminal a fresh shell in place — the same tile, folder, splits
and theme — with the current agents. With agents still on, the agent's
conversation resumes on the new agents, and any other program in the terminal
ends. With agents now off it comes back as a plain shell, and the agent ends too.
If an agent is working or waiting for you, the first click only asks; a second
click within a few seconds confirms. The old shell is stopped the way sleep stops
it — killed outright — so it does not write its history file, and anything you
started with `nohup` keeps running.

## Where they sit on the PATH

With agents on, a new terminal's PATH reads, from the front:

1. kolu's own tools (`kolu`, `kaval-tui`, `padi-tui`),
2. the chosen set's agents,
3. your own PATH — including anything your shell's dotfiles add.

So the bundled `claude` wins over one you installed yourself. That is on purpose.
kolu re-applies this order after your `.bashrc` / `.zshrc` run, so neither a
dotfile that sets `PATH` outright nor one that puts its own directory first
(`export PATH=$HOME/.local/bin:$PATH`, as Claude Code's own installer writes)
undoes it (bash and zsh; other shells get the order at spawn only — see
[Shell integration](/shell-integration)).

To run your own `claude` in a kolu terminal, turn Agents off, or call it by its
full path.

The chosen set also brings a command, **`agent-distro`**: type it to see the
set this terminal has (agent-distro calls it a profile), its agents,
their versions and whether each is signed in, or to launch one. It comes from the same build the tile's pill names, so what
it lists is exactly what this terminal has — on the machine running kolu and on
every host alike. It knows only this terminal's
set: to switch sets, use [Settings](#pick-a-set).

## On other machines

Agents work the same on every host you [add](/remote-hosts). The machine
running kolu **delivers** them: it takes the set from agent-distro's binary
cache into its own Nix store, copies it to the host over the same ssh login
kolu already uses, and pins it there so Nix's garbage collection leaves it
alone. The host itself downloads nothing — it needs no flakes, no access to
GitHub and no cache settings of its own for its agents — and nothing is ever
compiled, on either side. The host's tab shows the delivery until it lands
(below). Terminals
opened on that host before then have no agents (and no pill).

A [profile of your own](#a-profile-of-your-own) is different: it travels as
words, never as files. A flake reference is fetched by each host when an agent
starts there, and a **path** names a folder on that host, so it works only where
that folder exists.

Every host tab with agents on carries agent-distro's mark right after the host
name, and the mark's look says where that host stands:

| The mark | Means |
| --- | --- |
| plain, in the tab's text colour | ready for new terminals |
| a turning arc around it | kolu is delivering the agents to it |
| plain, with a turning arc around it | ready, and kolu is delivering a newer set; the current one keeps serving ([Kept up to date](#kept-up-to-date)) |
| warning colour with a small dot | the delivery failed — hover for why ([below](#when-a-delivery-fails)) |
| dimmed, with a turning arc | checking: the host is connected but has not said yet |
| no mark at all | agents are off, or kolu has not delivered that host any agents |

The arc only turns — it never fills: a delivery's copies report no byte counts
to fill it with.

Clicking the mark opens that machine's **host details** — the popover behind its
tab's connection pip — without switching tabs. Its **agents** section is
everything true of that machine: the profile new terminals there get and the
short hash of the build serving it, its state with its last delivery ("ready ·
updated 3h ago"), that machine's recent update events, and one action — **check
for newer agents ↻**, which is also how you try a failed machine again ([When a
delivery fails](#when-a-delivery-fails)). The machine names on Settings' fleet
line open the same place.

The machine running kolu itself needs no first delivery: every set ships inside
kolu, so switching there is instant and works offline. kolu still keeps it up to
date like any other host (below); the set kolu shipped with is what it uses
until the first newer one lands.

<Aside type="note" title="Disk">
  A host keeps its delivered set in its own Nix store (and the machine running
  kolu also carries the sets kolu ships, plus a copy of each set it passed on).
  If you also install agent-distro on a host through its Home Manager module,
  both share the same set and the same update log. Only the newest set is
  protected from Nix's garbage collection: after an update, the one before it
  can be removed, even while a terminal opened before the update still has it on
  its PATH.
</Aside>

## Kept up to date

agent-distro publishes a newer tested set of agents up to four times a day. At
those times — 02:00, 08:00, 14:00 and 20:00 UTC, agent-distro's own schedule —
kolu looks for a newer build of the set you chose and delivers it to every
connected machine that does not have it yet. Only the chosen set is kept
current; switching sets delivers the new one as before. A machine also gets a
delivery whenever it connects — kolu starts, a host comes back after sleep or a
dropped link, a newer kolu reaches it — so a machine that was away at those times
catches up as soon as it is back. A run that fails — the cache did not answer,
a host dropped off mid-copy, or no machine was connected to take it — is tried
again up to twice, five minutes after the failed run ended, as agent-distro's
own schedule does.

Nothing is ever compiled. If agent-distro's cache does not hold the newer set
yet, the delivery fails instead and is tried again as above.

While a newer set is delivered, the one you have keeps working: new terminals get
it until the new one has fully arrived. The host's mark keeps its plain colour
with the arc turning around it; Settings' fleet line keeps that machine among
the ones still working, and its host details say "ready · delivering newer
agents…". Then:

- a toast says what changed, in agent-distro's own format ("Claude Code
  2.1.286 → 2.1.291"), and on which machine;
- new terminals there start with the new set — `agent-distro` included, since
  it comes in the same build;
- a terminal already open keeps its own, and its pill offers **Restart**
  ([above](#restarting-a-terminal-onto-the-current-agents)).

A look that finds nothing newer says nothing: it shows in that machine's host
details, as its state's last run ("checked 2h ago, up to date"). A later
delivery that fails says nothing either — the agents you have keep working — and
it too stands in that machine's host details, in the warning colour, with the
cause.

A terminal keeps the set it started with until you restart it — or until a Nix
garbage collection on that machine removes that set, which an update leaves
unprotected. **Restart** gets the current set.

Two places let you look right now:

- the palette's **Check for newer coding agents** ("every machine") looks for
  every connected machine at once, whatever the time;
- a machine's host details offer **check for newer agents ↻** for that machine
  alone, greyed out while it could not take one — it is not connected, or a
  delivery to it is already running.

Each machine's **last five events** are in its host details too, one line each
with the time and the log's own words (hover a line for all of them). They come
from agent-distro's update log on that machine, which kolu writes in
agent-distro's own format. A machine whose update log kolu could not read says
so there instead.

## When a delivery fails

The usual cause is a host's Nix **refusing** the set kolu copied there. Nix
accepts copied software only from someone it trusts: either the login kolu
connects as is one of its `trusted-users`, or the software is signed with a key
it trusts. If neither is true, it refuses, and kolu cannot change that from
outside — so the host gets no agents (it never compiles them either), and its
mark turns to the warning colour; its host details say "refused by its Nix".

The machine running kolu can refuse too: it takes each set from the cache into
its own Nix store before passing it on, so its Nix must trust the user kolu runs
as or the cache's key. When it does not, every host's delivery fails the same
way and says "refused by kolu's own Nix" — the fix below then goes on the
machine running kolu, with your user in place of the login.

The fix is one line on that machine, either half is enough. On NixOS, trust the
login kolu connects as:

```nix
nix.settings.trusted-users = [ "root" "@wheel" "<login>" ];
```

or trust agent-distro's cache and its key:

```nix
nix.settings = {
  extra-substituters = [ "https://cache.nixos.asia/oss" ];
  extra-trusted-public-keys = [ "oss:KO872wNJkCDgmGN3xy9dT89WAhvv13EiKncTtHDItVU=" ];
};
```

Elsewhere, put the same settings in `/etc/nix/nix.conf` (`trusted-users = …`,
or `extra-substituters = …` and `extra-trusted-public-keys = …`) and restart the
Nix daemon. This is the same cache [kolu itself comes
from](/deployment#first-run-compiling-enable-the-binary-cache).

Other failures — agent-distro's cache did not answer or does not hold the set
yet, the copy broke off — carry kolu's words for the cause, with Nix's own line
after it. kolu tries those again on its own (see [Kept up to
date](#kept-up-to-date)).

A refusal is not retried on a loop, because only that machine's settings change
it — not even when the machine reconnects: kolu remembers the refusal and says
it again rather than copying the set over once more. Once you have fixed the
settings, kolu tries again at the next scheduled time — or right away: open
that machine's host details
(click the mark, or the machine's name on Settings' fleet line) and press **check
for newer agents ↻**. Its **agents** section carries the cause in full — Nix's
own words — that "New terminals on &lt;host&gt; get no coding agents until this is
fixed", the fix, and a link back to this section.

A later delivery that fails on a machine that already has agents is different:
the agents it has keep working, and the failure shows only in that machine's
host details ([Kept up to date](#kept-up-to-date)).

## Turning it off

Settings → **Agents**, switch it off. From the next new terminal on, on every host,
kolu adds no agents and no plugin variable; your own tools are what run.
Terminals already open keep what they have, and keep their pill, until you close
them (or restart them, which brings them back as a plain shell). While agents
are off, the welcome card keeps the question at the top of every empty canvas.
Your pick stays on its card for when you switch them back on.

## What doesn't change

[Agent detection](/agent-detection) works the same either way: kolu watches the
agent running in a terminal, whichever `claude` it is.
