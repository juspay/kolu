kolu runs on phones and tablets, not as a cut-down view but as the same
workspace re-shaped for a thumb. Two things decide the layout, and they're
independent: the viewport **size** (a phone gets the drawer layout) and the input
**modality** (a touch device gets roomier, ≥24px hit targets). A desktop browser
made narrow is *not* the same as a real phone — kolu keys the layout off the
**pointer**, so a coarse-pointer screen never masquerades as a desktop.

## On a phone

- **One tile at a time**, fullscreen, with **swipe** navigation between
  terminals instead of a spatial canvas.
- A two-row **soft-key bar** sends the keys touch keyboards lack — Esc, Tab, the
  arrows, Ctrl-C, `/`, Enter — with two sticky modifiers you tap to arm. The keys
  reach whichever terminal (or split) actually has focus.
- A **bottom-drawer** inspector replaces the desktop right panel; pull the
  chrome down from the top for app controls.
- **Only the tile you're looking at is live.** The other terminals on the host
  keep running, but the phone neither streams their output nor tells them how
  big its screen is — so opening kolu on a phone no longer reshapes every
  terminal on the machine behind it, and the soft keyboard rising only affects
  the terminal you're typing in. Swipe to another tile and it keeps the screen
  you left, replaced the moment the current one arrives; the activity dot is
  what says a tile changed while you were elsewhere.

## On a tablet or an unfolded foldable

A wide **touch** screen — an iPad, an Android tablet, a Galaxy Z Fold unfolded —
gets its own **two-pane** layout: a persistent terminal rail down one side, the
active terminal filling the rest, with the same touch-sized controls as the
phone. It's neither the phone's single tile nor the desktop's mouse-driven
canvas; a real mouse still gets the canvas.

Folding or unfolding the screen keeps the same terminal view. Switching between
touch and desktop layouts also retains the terminal instead of attaching it again.
The desktop canvas and split panel have separate layout owners from the touch
drawer: their gestures and sizing are rebuilt at that boundary. Phone and compact
share both the terminal view and the drawer.

## Multi-host from a phone

The [multi-host](/remote-hosts) engine works everywhere, and the phone can drive
it. The pull-down chrome sheet carries a **host row**: a chip per machine with
the same vocabulary as desktop — Home + machine hostname for local / ssh target for remotes,
identity colour when active, always-on connection pip (green / amber / red — the
same [whole-chain reading](/remote-hosts) desktop uses, so an amber "kaval down"
reads the same on a phone),
and that machine's attention counts (active · needs you · unread) — a **tap to
switch** (instant, no reload), and
a **+** that opens a full-width add-machine section right in the sheet. The
chrome stays above the canvas in every state, so a still-connecting or
unreachable host can never strand you with no way back to the host row. The row
follows the [arrangement you dragged the desktop host tabs
into](/remote-hosts#put-the-tabs-in-your-own-order) — it is saved on the server,
so the phone shows the same order; the drag gesture itself is desktop-only.

Above those chips, first in the sheet and visibly not one of them, sits
[**`◆ Conductor`**](/conductor) — kolu's one agent chat, which covers every
host rather than belonging to any, with the same one badge its desktop tab
wears: how many pieces of work it has in flight, turning the needs-you violet
while it is asking you something, and a violet dot with no number when it is
asking with nothing in flight. Tapping it gives the
conversation the whole screen under the pull handle, and the handle then reads
**◆ Conductor**. The sheet opens from there exactly as it does from a host,
with the Conductor lit and no host lit; tapping a host chip takes you back to
that machine — and the conversation is kept as you left it, so coming back to
it finds the same open panels, the same place in the transcript and the same
half-typed message.

The conversation on a phone is **one column** — the transcript, the status
line and the composer at one measure, with your own messages at that column's
right edge. A phone is narrower than the width where kolu can stand the work
in progress beside the conversation, so the watched terminals stay the panel
that the status line's **N pieces of work · M terminals** opens, and that
count is **absent when nothing is being watched**: no `watching 0`, and no
control that would open an empty list. The composer is one line that grows as
you type, with **Send** beside it; the steer hint, when a turn can be steered
into, is on the status line rather than a row of its own.
