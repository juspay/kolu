<Aside type="caution" title="Alpha preview">
This ships as a preview and **the surface may change** — flags, the socket
contract, and the shape of the transcript are all still moving. Two things
people reasonably expect are **not built yet**: you cannot answer an agent's
permission request yourself (the proxy auto-answers — see below), and a session
does not survive the agent being restarted. Both land in later phases. The
library the package is built on is also mid-migration
([#1989](https://github.com/juspay/kolu/issues/1989)).
</Aside>

Driving a coding agent by typing into its TUI means watching a screen and
guessing: has the turn ended, was that keystroke swallowed, did the tool finish?
The [Agent Client Protocol](https://agentclientprotocol.com) (ACP) removes the
guessing. A prompt is a request that **returns when the turn ends**, and
everything in between — message text, tool calls, permission requests — arrives
as a typed frame.

**`acp-proxy`** runs a headless agent behind that protocol and re-serves it on a
unix socket, so a program can drive the agent while you watch the very same
session scroll past in a terminal. **`acp-chat`** is the client you talk to it
with.

## Try it

Two terminals. In the first, harness an agent:

```sh
nix run github:juspay/kolu#acp-proxy -- --id demo -- claude-agent-acp
```

It prints the socket it is listening on and then idles. In the second, pass that
path to the client — from any directory:

```sh
nix run github:juspay/kolu#acp-chat -- /run/user/1000/kolu/acp-demo.sock
> why is the e2e suite flaky?
agent ▸ It's a port collision: two workers bind 5173.
```

The first terminal shows the same turn as protocol frames — which is the point
of running it in a kolu tile: the conversation happens over the socket, and the
tile is where you go to watch it happen.

```
▶ session/prompt · "why is the e2e suite flaky?"
◀ agent_message_chunk · It's a port collision: two workers bind 5173.
◀ tool_call · execute — grep -r retry test-results/
◀ session/request_permission · grep … → auto-answered Allow once
◀ tool_call_update · completed
● turn end · stopReason: end_turn
```

<Aside type="note" title="The tile is not an input">
Nothing is typed into the proxy's terminal. All input arrives as ACP calls on
the socket, which is what makes the session drivable by a program and watchable
by a person at the same time. **Several clients can attach at once** and all see
the same turn — so a second `acp-chat` can sit alongside whatever is driving the
agent and watch, including the prompts it did not send.
</Aside>

## Any agent

The adapter is whatever you put after `--`, so no agent is privileged:

```sh
acp-proxy --id a -- claude-agent-acp   # Claude Code, headless
acp-proxy --id b -- codex-acp          # Codex
```

Both adapters ship with the package — no global install — and both use the login
the host already has. Any other stdio ACP agent on your `PATH` works the same
way.

Note the adapter is an **ACP adapter**, not the interactive CLI: it is
`claude-agent-acp`, not `claude`. Point it at the wrong one and the proxy tells
you so after a few seconds rather than hanging.

## What the harness handles

An agent process can die mid-turn, ignore a cancellation, or block waiting for
permission. The proxy absorbs all three so a client sees one durable session:

- **A dead adapter is replaced.** The turn it was running fails loudly; your next
  prompt works. Conversation history does not survive the restart. Replacement is
  paced and capped, so an agent that cannot start at all tells you so instead of
  retrying forever.
- **A cancel always ends the turn.** It is forwarded first; an agent that keeps
  going anyway is replaced after a short grace window rather than left running.
- **Permission requests are auto-answered "allow once"**, and every decision is
  printed in the transcript. This is the current policy, not a setting: there is
  no way to answer one yourself yet, and no way to decline. Run agents here only
  where that is acceptable.
- **The agent is taken down with the proxy**, including the tools and MCP servers
  it spawned — Ctrl+C does not leave an agent running behind you.

## Where this is going

Everything in this section is **future work — none of it is built.** What ships
today is the substrate: a socket, two bins, and a transcript. The destination is
an agent you talk to from a chat thread, and the plan of record is the Atlas
note [Chat threads as terminals, over
ACP](https://kolu.dev/atlas/chat-native-agents-and-kolu.html).

The shape it is heading for:

- **One chat thread ↔ one kolu terminal.** DM a bot; a daemon creates a proxy
  tile on your host, prompts it, and streams the reply back into the thread. The
  tile stays an ordinary terminal you can click into for the full frame log.
- **Permissions you answer from the chat.** A permission request becomes a card
  with a button per option; answering it unblocks the agent. That replaces
  today's auto-answer.
- **Sessions that survive a restart.** The bind is remembered and the
  conversation resumes with its prior context, rather than starting fresh.
- **Any agent, still.** The adapter stays argv, so the chat front end and the
  agent behind it remain independent choices.

None of that changes what is here now, and none of it is promised on a date.
