- <Change title="Your terminals live in kaval, a standalone daemon you can drive from any shell" pr={1301} tags={["terminal", "cli"]}>**kaval** (Tamil *kāval* — watch, guard) is a small, standalone **PTY daemon**: it owns your shells, mirrors their screens, and serves them over a local socket, outliving the clients that come and go. Run it on a box where kolu has never been installed — `nix run github:juspay/kolu#kaval` — and drive it with **kaval-tui**, its terminal client: `kaval-tui list` prints every live terminal (id · pid · idle · command · cwd) and `kaval-tui snapshot <id>` dumps a terminal's scrollback to stdout for piping and grepping, while `kaval-tui attach <id>` takes one over full-screen with raw passthrough — an ssh-style line-start `~.` detaches, the scrollback repaints on attach, and it exits with the inner program's code, your terminal always restored cleanly even on a crash. An unreachable daemon is an honest one-line error, never a hang.</Change>

- <Change title="Spawn a terminal from your shell — and see it appear in kolu live" prs={[1370, 1458]} tags={["terminal", "cli"]}>`kaval-tui create` spawns a new terminal on the daemon — a plain `$SHELL`, or a command you give it (`kaval-tui create -- htop -d 5`) — and prints its short id; `kaval-tui attach <id>` then takes it over. The daemon owns the terminal, so it outlives the `create` command that made it — create it from one shell, attach from another, detach and reattach at will. A terminal you spawn this way shows up as a **tile in kolu instantly**, the moment it's created, and one you end drops from the canvas — the daemon serves every client a live inventory feed, so kolu's terminal list is a continuous projection of the one set of PTYs the daemon owns rather than a list re-synced only at boot.</Change>
- <Change title="Send input to a terminal from your shell — kaval-tui send" pr={1589} tags={["terminal", "cli"]}>`kaval-tui send <id> [text]` writes input straight to a terminal the daemon owns — a prompt to a **Claude Code / Codex / opencode** agent running in it, so one agent can drive another. It sends **exactly the text (and any `--key`s) you pass — no implicit Enter**; submitting is its own explicit `kaval-tui send <id> --key Enter` (a separate write that lands after the text settles, dodging a race against bracketed-paste input). A multiline prompt — or one piped on **stdin** — is sent as a single **bracketed paste** so it lands as one block; `--key` also sends control keys (`Escape` to interrupt, `C-c`, the arrows). It's the write half of driving an agent from a script: `create` a terminal running an agent, `send` it a prompt, `send --key Enter`, then read the reply with `snapshot`.</Change>
- <Change title="Block until a terminal goes quiet — kaval-tui wait" pr={1630} tags={["terminal", "cli"]}>Driving an agent that drives another, the missing piece was a reliable "its turn ended" signal. `kaval-tui wait <id> --until idle:<ms>` blocks on the terminal's **raw output stream** and returns the instant no output has arrived for `<ms>` (the turn ended / it's awaiting you). It's **agent-agnostic and needs no shell hooks** — the same command works for `claude` / `codex` / `grok` / `opencode`. `--until match:'<regex>'` waits for a completion marker instead; `--timeout <ms>` **fails loud** (exit 2) so a wedged agent can't hang the loop, and a terminal that exits first fails loud too (exit 3). `--json` prints one structured result frame per outcome, and it works over `--socket` and `--host` like every other verb.</Change>
- <Change title="End a terminal from your shell — kaval-tui kill" pr={1462} tags={["terminal", "cli"]}>`kaval-tui kill <id>` tears a terminal down from the shell: the daemon kills the PTY, it drops out of `list`, and any client still attached sees the shell exit. `<id>` is the short id or any unique prefix, and a missing id fails loud rather than silently doing nothing. It completes the raw multiplexer's lifecycle — `create` makes a terminal, `kill` ends it — and works against a local daemon, a running kolu, or a remote one over ssh.</Change>
- <Change title="Reach a terminal on another machine — kaval-tui --host" prs={[1373, 1377, 1378]} tags={["terminal", "cli", "performance"]}>`kaval-tui <command> --host nix@prod` drives a `kaval` daemon on a **remote machine** over ssh, with nothing to install there first: it provisions the daemon with Nix, runs it, and dials it — every subcommand works exactly as it does locally. The remote daemon is **durable**, so a terminal survives the connection that made it: `create` a shell on prod, close the laptop, change networks, and `attach` finds it still running, scrollback and all. Reconnecting is fast — kolu asks a warm machine once whether the daemon's already present and goes straight to dialing it rather than re-shipping the same build, and it shares **one** ssh connection across the arch-probe, the check, and the dial instead of paying a fresh handshake for each.</Change>
- <Change title="Read just the visible screen — kaval-tui snapshot --viewport" pr={1610} tags={["terminal", "cli"]}>`kaval-tui snapshot <id>` prints a terminal's **whole scrollback**, so `snapshot | tail -8` hands you the bottom of the buffer (often just blanks), not the live screen. **`--viewport`** now prints just the visible screen — the terminal's last screenful, resolved against the **daemon's own grid** so it's correct no matter how tall your shell is (over `--host` the remote terminal is a different size) — and **`--tail N`** the last N rendered lines. `--viewport` is the right read for "what's on screen now" when one agent drives another; the bare default still dumps the full scrollback for `grep`.</Change>
- <Change title="Dump a terminal's older scrollback — kaval-tui history" pr={1783} tags={["cli", "terminal"]}>**`kaval-tui history <id>`** prints the scrollback **above** the current screen — the older output `snapshot --viewport` can't show — VT-serialized so colours survive, cursor-paged from the newest older lines back. `--lines N` prints just the one page immediately above the screen; omit it for the full history, oldest-first. Read-only, takes no TTY — an agent-orchestration or incident-forensics read.</Change>
- <Change title="Pass a big prompt without shell mangling — kaval-tui send --file" pr={1704} tags={["kaval", "cli", "terminal"]}>Handing a large brief to an agent as `"$(cat brief.md)"` lets the shell **execute** any backticks or `$(...)` in the file before `kaval-tui` sees them. **`kaval-tui send <id> --file <path>`** reads the payload **straight from the file** — byte-exact, no shell in the loop. It's mutually exclusive with positional text and piped stdin, and fixes the **shell** hazard, not the wire bytes (still a bracketed paste).</Change>
- <Change title="Every terminal knows its own daemon — $KAVAL_SOCKET" pr={1657} tags={["terminal", "cli"]}>Driving your sibling terminals from an agent running *inside* a kolu terminal meant first **hunting for the daemon's socket** — scanning `/tmp`, or guessing a path that is simply *unknowable* on macOS. ### Fixed

- <Change title="Switching to a terminal no longer shows garbled text" pr={1824} tags={["terminal", "rendering"]}>On a busy workspace — many terminals, splits, **maximized** mode — switching *to* a tile could paint the **whole terminal in the wrong glyphs** (every character substituted — `background` → `tackground`), clearing only when you selected the text or reloaded. The cause: a tile hidden with `display:none` missed the resize events that keep its GPU glyph atlas fresh, and on show re-fit to the **same** size — a no-op that skipped the atlas rebuild — so every glyph drew from a stale slot. kolu now rebuilds the atlas whenever a tile becomes visible again, regardless of whether its size changed. Most visible on Linux and, recently, macOS under load.</Change>
- <Change title="Terminals no longer silently freeze" pr={1235} tags={["terminal"]}>A WebSocket that died without notice — a laptop sleeping, Wi-Fi roaming, or a network dropping an idle connection — used to leave a terminal frozen until you reloaded the page. A heartbeat now detects the dead connection and reconnects on its own, so live output resumes without a reload.</Change>
- <Change title="Terminal output no longer freezes until you press a key" pr={1273} tags={["terminal"]}>A terminal could silently stop painting new output — an agent seemingly stuck for minutes while its work continued — until any keypress made everything appear at once. The cause: a viewport scroll you never made (a touch artifact, a TUI leaving its alternate screen, a scroll tick delivered late after backgrounding the tab) engaged the scroll-lock with nothing to release it. The lock now engages only for scrolls you actually make; any other scroll snaps back to the bottom and output keeps flowing. Returning to the tab also releases a lock left engaged while you were away.</Change>
- <Change title="Output that arrived while kolu was in the background appears the moment you return — no keypress needed" pr={1381} tags={["terminal"]}>Switch to another window while an agent keeps working — exactly what running a fleet of background subagents looks like — and the terminal could stop painting: new output piled up unseen and only snapped into view when you came back and pressed a key. When a window is occluded the browser stops producing animation frames, and xterm schedules every repaint on one, so a paint queued while you were away never ran until an input event forced a frame. kolu now forces an immediate repaint the instant the window regains focus (with a short watchdog for a stall when focus never changed).</Change>
- <Change title="A terminal flooding output no longer freezes when kolu sheds its slow view" pr={1591} tags={["terminal", "performance"]}>kolu's terminal daemon caps how much un-drawn output it buffers per connected view, and when one falls far behind it **drops** that view rather than growing memory without bound, expecting a re-attach. But the drop looked exactly like the shell exiting, so the terminal **froze** — scrollback stuck, no new output — as if the process had died (it hadn't). The daemon now marks that drop distinctly from a real exit, so the terminal **re-attaches on its own and repaints from a fresh snapshot** the moment it's shed. You lose only the sliver of scrollback the cap discarded; the live screen comes right back.</Change>
- <Change title="Working across many terminals no longer crashes the GPU on AMD Linux" prs={[1416, 1404, 1494]} tags={["terminal", "canvas", "performance"]}>On Linux with an AMD GPU, running kolu across several terminals in Chrome/Chromium could slowly exhaust GPU memory until the graphics driver reset — blanking terminals, and on some setups taking down the whole desktop. The cause: kolu kept the hardware (WebGL) renderer on only the most-recently-used terminals, so switching among more of them destroyed and recreated a GPU context on *every* focus change, and Chrome on AMD doesn't reclaim that memory until garbage collection — so the churn outran cleanup until the GPU faulted. kolu now keeps the renderer on your **whole working set** at once, up to a safe cap below the browser's per-tab context limit, so ordinary switching no longer churns contexts and the leak is gone. It also cured the subtler tells of the same churn — text that subtly resized as you clicked between tiles, and tiles that intermittently rendered corrupted on long sessions. Firefox was never affected.</Change>
- <Change title="Long-running kolu no longer runs its terminal daemon out of memory" pr={1427} tags={["terminal", "performance"]}>Over days of heavy use across many terminals, **kaval** could slowly exhaust memory and crash — taking kolu down for a brief restart every few days. The cause: kaval kept a deep **50,000-line** scrollback mirror of every live terminal, and live terminals accumulate, so a few hundred exhausted its heap. kaval now keeps a leaner **10,000-line** mirror per terminal — still enough to repaint a freshly-opened tab and feed agent detection — roughly **quadrupling** how many terminals it takes before memory is a concern. Your in-browser scrollback and PDF export are untouched at the full 50,000 lines.</Change>
- <Change title="Reconnecting no longer makes kolu's memory briefly spike" pr={1573} tags={["terminal", "performance"]}>When the connection to kolu dropped and came back — a reload, a Wi-Fi roam, a laptop waking — the server re-attached to every open terminal at once, and with many open it could briefly balloon its memory by gigabytes before settling. That burst now reuses a single screen snapshot per terminal instead of rebuilding one per attach, and skips the work entirely for attaches whose tab has already gone. Nothing changes on screen.</Change>
- <Change title="After an unclean kaval crash, your agents come back — resumed, not bare shells" pr={1784} tags={["terminal", "session", "agents"]}>If **kaval** was killed **uncleanly** (a SIGKILL, an OOM, a crash), session restore used to bring the terminal *list* back but every agent returned as a **bare shell** — the conversation gone. - <Change title="The 'N terminals reattached' note no longer repeats on every reconnect" pr={1366} tags={["terminal", "mobile"]}>After a kolu update that keeps your terminals running, kolu shows a brief **N terminals reattached** note — meant to appear once. - <Change title="The 'App updated' prompt no longer loops forever" pr={1324} tags={["pwa"]}>The "App updated — Reload to apply" card could reappear immediately after every click, leaving the client stuck a build behind no matter how many times you clicked. The cause: kolu baked the build version into a JavaScript bundle the browser caches for a year, so a deploy that changed only docs rewrote that file's contents without changing its name — and your browser kept serving the year-cached old copy. kolu now carries the build version in the always-fresh page shell instead of the cached bundle, so a normal Reload always lands the deployed build and the card clears for good.</Change>
- <Change title="kaval-tui send no longer hangs forever on a terminal that isn't reading its input" pr={1704} tags={["kaval", "cli", "terminal"]}>If you `send` to a terminal running a program that has **stopped draining its input** (a plain `cat` whose output has backed up), the write had **no deadline** — it could block for minutes with no way out. Now a `send` whose write can't complete **fails loud in a few seconds**, naming the stalled terminal. The bound is fixed in code so the never-hang guarantee can't be tuned away.</Change>
- <Change title="Closing a terminal no longer logs a spurious 'Terminal not found' error" pr={1633} tags={["terminal"]}>Closing a terminal — especially via **Close and remove worktree** — could spit an `error`-level **`Terminal <id> not found`** line into the server log even when you hadn't typed a thing. - <Change title="No more error spam — or a false auth warning — on repos that aren't on github.com" prs={[1256, 1631]} tags={["terminal", "git"]}>A terminal in a repo hosted **anywhere but github.com** — Codeberg, a self-hosted Forgejo/Gitea, GitLab, even a local repo with no remote — used to spit an `error`-level line into the log on every poll, re-log a "gh: not authenticated" warning every 30 seconds, and flash a scary **"gh: unknown error"** popover on its tile. Nothing was wrong: kolu was asking GitHub's `gh` tool about a repo that isn't on GitHub. kolu now asks `gh` only about **github.com** remotes; everything else simply shows **no PR**, exactly like a branch with none — quiet, no popover, no warning. - <Change title="Switching branches no longer flashes the previous branch's PR" pr={1257} tags={["terminal", "git"]}>When you switched a terminal to a different branch (or left the repo) while its PR was still being looked up, the tile could briefly show the *old* branch's pull request — number, title, CI status — until the new lookup finished. kolu now discards a stale in-flight lookup whose branch no longer matches, so the PR pill only ever reflects the branch you're actually on.</Change>
- <Change title="No more error spam in fresh repos" pr={1246} tags={["code tab", "git"]}>Opening a terminal in a freshly `git init`'d repository (no remote, no commits) no longer logs a repeated "no base branch found" error on every change. - <Change title="No more scary error on upgrade" pr={1239} tags={["code tab", "upgrade"]}>Upgrading from an older build no longer logs an `EVENT_ITERATOR_VALIDATION_FAILED` error at launch. - <Change title="The packaged kolu honours KOLU_STATE_DIR again" pr={1415} tags={["packaging"]}>The Nix-built (production) kolu silently ignored `KOLU_STATE_DIR`, always storing your session, preferences, and activity feed under `~/.config/kolu` — so running a second instance on one machine meant the two clobbered each other's saved state, and the only way to relocate it was to hijack `$HOME` (which also moves your ssh and git config). The packaged wrapper now honours an inherited `KOLU_STATE_DIR`, while still defaulting to `~/.config/kolu` when you don't set one — so a second production instance can keep its own state directory.</Change>
- <Change title="An HTML preview stops jumping to the top while you read it" pr={1755} tags={["code tab", "preview", "remote"]}>Reading a rendered HTML file in the Code tab, scrolled halfway down, the preview would **reload and snap back to the top** at seemingly random moments — even though the file's text never changed. The trigger was another terminal doing **git work in the same repo** (a branch checkout during a PR loop, most often on a remote machine): a checkout re-writes files with the **same bytes but a new modification time**, and the preview keyed its cache-buster on that time. The preview now keys on a **hash of the file's actual bytes**, so a same-content rewrite leaves your scroll position exactly where it was.</Change>
- <Change title="Code tab remembers the file you picked, not the one you clicked in the terminal" pr={1345} tags={["code tab", "preview", "terminal"]}>After you clicked a `path:line` reference in the terminal to preview a file, then manually picked a *different* file in the tree, switching to another terminal and back used to snap the preview back to the terminal-clicked file — quietly discarding your manual pick. - <Change title="Code tab keeps your tree/preview split" pr={1250} tags={["code tab"]}>Resizing the split between the file tree and the preview in the Code tab now sticks. - <Change title="The minimap's zoom controls stay reachable when terminals stack into a tall, narrow column" pr={1405} tags={["canvas"]}>The minimap's strip of zoom / arrange / activity-window controls used to narrow along with the overview when tiles stacked into a tall, narrow column, until the buttons were clipped off the right edge and unclickable. - <Change title="Text selection in a zoomed canvas terminal tracks the pointer" pr={1401} tags={["terminal", "canvas"]}>Dragging to select text in a terminal tile while the canvas was zoomed landed off the mouse — the selection started at an offset that grew the more you zoomed, making text out of an interactive TUI a guessing game. - <Change title="Switching terminals in maximized mode no longer re-renders them" pr={1410} tags={["terminal", "canvas"]}>With a terminal maximized, switching to another — from the dock, <kbd>Cmd/Ctrl+1</kbd>…<kbd>9</kbd>, or cycling — used to make **both** terminals visibly re-render on every switch and round-trip a resize to the shell, because kolu kept the inactive terminals at their small canvas size while the maximized one filled the screen. ### Heads-up

- <Change title="Cross-site pages can no longer drive kolu's terminal RPC" pr={1386} tags={["security", "terminal"]}>kolu's terminal control plane is unauthenticated, so any web page you visited could quietly reach your local kolu and drive it — create terminals, type into them, kill them all — without you knowing. Both its transports (a WebSocket and plain HTTP) were reachable cross-site (a WebSocket upgrade needs no CORS preflight; a cross-site form can POST into an HTTP procedure), and binding to localhost didn't help because the malicious page runs in your own browser. kolu now checks the browser's `Origin` on **every** request, on both transports, and rejects cross-site ones; the kolu UI talking to itself and non-browser clients (a CLI, `curl`) are unaffected. If you front kolu with a reverse proxy or `tailscale serve` whose address differs from what kolu sees, allow it through with the new **`KOLU_ALLOWED_ORIGINS`** env var.</Change>
- <Change title="Pointing kolu at a remote machine now seeds it, not boots into it" pr={1714} tags={["remote", "ssh", "multi-host"]}>Previously `KOLU_PADI_HOST=<host>` made the **whole canvas** that one remote machine. Now it's a **pool seed**: the named machine(s) join a warm pool, but the canvas **boots on your local machine** (the always-present, unremovable default) and you switch to a remote from the host strip. So a single `KOLU_PADI_HOST=<host>` no longer opens *straight into* that machine — it opens local, with the machine one click away. The remote's terminals are durable as ever; only which machine the canvas starts on changed. (A comma-separated list seeds several at once.)</Change>
- <Change title="Two kolus can't fight over one machine's terminals — the second refuses to start" pr={1714} tags={["remote", "ssh", "multi-host"]}>Only **one** kolu-server may supervise a given machine's workspace daemon (**padi**) at a time — two would tug-of-war over the same daemon. So starting a **second** kolu-server pointed at a machine another already supervises now **fails fast at boot** with a clear message naming the conflict and the fix, instead of silently degrading. To run two independent instances on purpose, give the second its own state: **`KOLU_STATE_DIR=<dir>`** (and **`KOLU_PADI_STATE_DIR=<dir>`** for an isolated local padi; **`KOLU_REMOTE_PADI_STATE_DIR=<dir>`** for a remote one). `just dev` and the e2e harness already isolate themselves.</Change>
- <Change title="kaval-tui send: text + --key in one command is now a hard error" pr={1704} tags={["kaval", "cli", "terminal"]}>Sending a prompt AND submitting it in one command — `kaval-tui send <id> "prompt" --key Enter` — used to *look* like it worked but silently drop the Enter: a same-breath Enter races the TUI's bracketed-paste debounce, leaving the prompt staged on the `❯` line while `send` reported success. Combining text with `--key` is now a **hard error** that teaches the fix, because `kaval` **cannot observe** when the TUI settled — but the caller can. Submitting a normal-size prompt is **three honest steps**: `kaval-tui send <id> --file brief.md` (the text) · `kaval-tui wait <id> --until idle:300` (observe the settle) · `kaval-tui send <id> --key Enter` (submit). The removed `--submit` flag prints a migration message pointing at the two-command flow. (A big paste Claude Code folds into a `[Pasted text +N lines]` placeholder still doesn't reliably submit on Enter — for a large brief, write it to a file and send a short prompt telling the agent to read it.)</Change>
- <Change title="GitHub Enterprise repos no longer show a PR pill (for now)" pr={1631} tags={["terminal", "git"]}>To stop kolu mistaking non-GitHub repos for GitHub ones, kolu now treats **only `github.com`** as GitHub — it no longer guesses that an arbitrary remote host might be a GitHub server. The trade-off: a repo on a **GitHub Enterprise** host (your company's own `github.example.com`) no longer shows its PR pill, even when `gh` is authenticated for it. This was a deliberate scope call — recognizing arbitrary Enterprise hosts needs per-host configuration, tracked alongside the broader multi-forge work. Everything on `github.com` is unaffected.</Change>
