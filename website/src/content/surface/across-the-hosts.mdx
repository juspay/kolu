So far fleet-top has watched *your* machine. Now we reach one running on
**another** box, over ssh, and show its `top` in your browser — using the exact
same surface. The trick is a **mirror**: the remote box serves the surface, a
local parent folds its frames into a local copy of the same surface and re-serves
*that*, and the browser only ever talks to the local copy. Swap the box behind it
and the browser never notices.

<Aside type="note" title="The code for this page (part 3)">
  Multi-host builds on the **basics** surface (part 1), not the daemon stratum —
  so we continue from the `top` surface you already know, no daemon required. The
  mirror + map code lives at `packages/surface/example/fleet-top/part-3`; it
  typechecks in CI, so the snippets are the real files. Set up like the earlier
  parts: `cd packages/surface/example/fleet-top/part-3 && pnpm install`.
</Aside>

## The agent — what runs on the far box

The remote side is tiny: it serves the same `top` surface over stdin/stdout. This
is what the parent runs on each target — `ssh <host> fleet-top-agent --stdio` for
a remote box, the realised binary directly for `localhost`. It is ephemeral — a
fresh one per link — which is the right shape for a re-run-fresh reader like `top`.

## The three-hop mirror

On the parent, each host is one binding. First, **dial** it —
`makeSession({ connectOnce: sshConnector(...) })` provisions the agent closure
onto the box and runs it (over ssh for a remote host, directly for `localhost`),
reconnecting on drop.

<Snippet src="packages/surface/example/fleet-top/part-3/src/server/hosts.ts" region="dial" />

Then **pump** the agent's frames *inward*, folding each into a local
`implementSurface` of the same surface. The local copy is what browser
subscribers read; `makeSink` writes the incoming frames through its `ctx`.

<Snippet src="packages/surface/example/fleet-top/part-3/src/server/hosts.ts" region="pump" />

Finally **re-serve**: a `directLink` over the local fragment's flattened router is
the link the browser reaches. Three hops — dial, pump, re-serve — and the surface
that started on another machine now serves from this process.

<Aside type="caution" title="The parent owns the connection state">
  The remote box cannot report whether *your* link to it is healthy — so that
  state is the parent's to own. While the closure is copying or the session is
  reconnecting, the parent projects `warming` (in motion, self-heals); only a
  bounded remote fault — a box that answers-but-refuses, or gives up terminally —
  projects `failed` (needs intervention). One box's trouble becomes exactly one
  honest chip, never a crash — the idea behind
  [The server half](/surface/the-server-half).
</Aside>

<Aside type="caution" title="Prerequisites for running it">
  Multi-host needs two things the earlier parts did not. **(1) The agent as a
  [Nix derivation](https://nixos.org/manual/nix/stable/language/derivations.html).**
  `sshConnector` ships a realised closure to each host, so it needs
  the agent's `.drv` path in `FLEET_TOP_AGENT_DRV` — the server refuses to boot
  without it (no fallback). fleet-top ships the agent as a flake output, so you
  resolve it in one command: `nix eval --raw .#fleet-top-agent.drvPath` (from the
  repo root). **(2) A reachable host.** `localhost` is the easy one: `sshConnector`
  detects it and runs the realised binary **directly, with no ssh and no sshd**; a
  non-local `HOST` is a genuine ssh hop.
</Aside>

## Watch it arrive

<Steps>

1. Point the parent at one host and start it. `HOST` is the target (`localhost`
   here — no ssh needed); `FLEET_TOP_AGENT_DRV` is the agent's flake output,
   resolved in place.

   ```sh
   # resolve the agent .drv (works from anywhere in the repo):
   export FLEET_TOP_AGENT_DRV="$(nix eval --raw "$(git rev-parse --show-toplevel)#fleet-top-agent.drvPath")"

   HOST=localhost pnpm run dev
   ```

   ```text
   fleet-top part 3 serving 1 host(s) on http://localhost:7740
   ```

2. Open **http://localhost:5176**. The header chip shows the host warming while
   the agent closure is realised, then flips to connected — and the same live
   `top` you built in part 1 fills in, this time streaming from the agent the
   parent stood up (on `localhost`, directly; on a remote box, over ssh).

</Steps>

You changed nothing about the surface or the browser code. The box could be a
laptop across the room; the mirror makes it read like local state.
