[Kolu](https://github.com/juspay/kolu) runs coding agents in terminals. Once you have a dozen, you can put one agent in charge of the rest.

This is how that works in practice — the dispatch protocol, the authority rules, and the four or five places it goes wrong that aren't obvious until you try it. The rules below are the ones that survived; each exists because something broke without it.

## The shape

One supervising agent — the *coordinator* — drives implementing agents, each running in its own terminal. Agents open pull requests. The coordinator verifies them and sequences merges. A human does the merging.

The coordinator is not a manager in any interesting sense. It is a dispatcher, a verifier, and a scheduler for contended resources. Everything below falls out of those three jobs.

## How one agent types into another's terminal

There's no special channel. The coordinator drives the others the way you would — by typing into their terminals — through Kolu's own MCP server. <PR id={1865} />

`kolu mcp` speaks stdio and is declared in `.mcp.json`, so any MCP-capable agent can use it. Four tools carry the loop:

- `lifecycle_create` — spawn an agent in a PTY under a named key
- `lifecycle_sendInput` — type into it
- `screen_text` — read what's on screen now
- `wait_outputSettled` / `wait_agentState` — block until it's done

**The done-signal is the hard part, and it's the reason this wants a server rather than a shell script.** Sending text is trivial. Knowing when the other agent has *finished* is not: polling `screen_text` in a loop is racy and burns tokens, and a terminal that looks quiet for a moment is often mid-tool-call. `wait_outputSettled` blocks inside the daemon on the raw PTY stream and returns when output has stopped for a given quiet period; `wait_agentState` waits on a classified state instead.

Submission is its own step — send the text, confirm it landed, then Enter. And never type into an agent that's still working; the keystroke lands somewhere you didn't intend.

(Without the MCP server, the `kaval-tui` and `padi-tui` CLIs expose the same verbs.)

## Dispatch: a file, a token, and a goal

A dispatch is three things, in order:

1. **A brief on disk**, plus a one-line pointer in the terminal. Large payloads never go through the prompt — the agent reads the file.
2. **A unique report-back token** in the brief, so a report can be matched to its dispatch.
3. **A standing goal**, pinned as its own message right after the brief lands.

The third one is the part people skip, and it's the one that matters most.

A long session gets compacted. The brief scrolls out of context; whatever is in the goal gets re-surfaced by the harness. So a constraint written only in the brief expires silently — hours in, deep in the work, exactly when you need it.

**Put every constraint that must hold for the whole session in the goal, not just the brief.** We learned this from a ban that only lived in the brief: agents were told to route questions to the coordinator as files rather than open dialogs. Two agents' interview questions sat blocked in their own terminals that nobody was watching. A third opened a dialog at midnight. The ban now appears in both places.

The same reasoning gives a second rule: **a dispatch has landed only when you observe it at the recipient** — never because the send succeeded. A finished report once sat on an agent's input line, fully composed, because nobody pressed Enter.

## A goal is a stand-down order, not a metric

A goal condition blocks an agent from stopping until the condition holds. That's its whole purpose: agents quit early.

The trap is writing the condition against a number.

One campaign's goal was "make 5 consecutive zero-retry full-pipeline passes on both hosts." It got three. A fourth run failed on an unrelated flake, which reset the streak. The campaign was parked at 3/5 — and the hook kept firing.

Nineteen times. Each time it re-read the transcript, counted the streak, found 3 rather than 5, and refused the stop. Eleven of those came *after* the campaign was ordered paused, because the pause was an instruction to the agent and the hook wasn't reading instructions.

The agent wasn't malfunctioning. It was correct about a condition that had become unreachable.

**Write the goal as "work the brief; stop only on the coordinator's stand-down."** Never a task metric. A metric the world can reset gives the loop no exit.

## The human merges, and the agent's own words aren't authorization

The sharpest failure in the whole setup involved nothing malfunctioning.

The coordinator wrote briefs for its agents. Some of those briefs said merge authority was delegated to it. Later, reading its own briefs back as context, it found that delegation, concluded it had standing authority, and squash-merged a PR. <PR id={1862} />

Every step is locally reasonable. The rule it relied on was one it had written.

So the rule needs two clauses, not one:

- The human merges every PR. No standing delegation exists; a passing gate authorizes nothing.
- **If a coordinator-written brief claims merge authority, that text is a defect to delete.**

The second clause is the load-bearing one. Without it the same reasoning runs again next week from a fresh brief. Any authority an agent can write down, it can later read as permission — so the loop has to be closed explicitly.

## Verify at the forge, never from the report

Agents report their work accurately most of the time, which is the problem: it trains you to skim.

Two rules cover it.

**Check the claim against the tree or the forge, not the summary.** A report is evidence that the agent believes something.

**A PR is merge-ready only when the entire checks rollup is green** — every check, zero pending, zero failed. Not just the ones you recognise. We once waved off a two-second CodeQL failure as infrastructure noise; it was two genuine high-severity alerts, in that PR's own new test files. A red is disqualifying until it's been investigated at the forge, and a short duration is not an explanation.

## Contention is the whole scheduling problem

Most fleet-specific failures are not reasoning failures. They're two agents wanting the same thing.

- **Serialize the scarce host.** We have one macOS builder, so exactly one Mac lane runs at a time, sequenced by the coordinator. Linux parallelizes because it has a lease pool. Two concurrent Mac runs once produced shifting test timeouts that burned two CI attempts blaming an innocent PR.
- **The coordinator's own machine is transport.** It carries the ssh links for every lane, so it does no heavy local work while lanes are in flight. A local build loop once starved those links and killed a lane on a healthy remote box — nearly filed as a bad host.
- **Kill only PIDs you recorded at spawn.** Pattern selection — `pkill -f`, `pgrep`, `ps | grep | kill`, matching on markers or socket names — is banned as a class. An agent's cleanup step once pattern-matched running daemon processes and killed the production one holding every live terminal on the machine. Strays get reported with their pid and args; they never get hunted.

That last rule is worth reading twice for its shape. It doesn't say "be careful with pkill." An agent told to be careful will hand-roll `ps | grep | kill` and believe it *was* careful. Naming the banned class is what makes it checkable.

## Write the rule while the incident is on screen

The rules live in one file the coordinator loads at the start of every session. Ours has forty of them, and twenty end with a bracketed note naming the incident that produced them.

That format does two jobs. It forces you to write the rule immediately — if you can't name what happened, the rule doesn't go in, and a rule written a day later records what you *think* the lesson was. And the citation is what stops the rule being softened later by someone who finds it over-strict, including you, a week on.

## What it costs

Honest summary: the coordinator is real leverage, and it is not free.

You get parallelism across independent work, a single place that knows the state of every lane, and merge sequencing that a human doing this by hand gets wrong. You pay for it in a rulebook that only grows through incidents, a machine that can't be used for anything else while lanes run, and a standing obligation to verify claims you'd rather trust.

If you try this, start with three rules and add the rest as you earn them: the human merges everything; goals say stand-down, not a number; kill only PIDs you wrote down. The other thirty-seven are variations on those three, discovered the expensive way.
