# grok round-1: radical simplifier

**Stance**: RADICAL SIMPLIFIER. Propose the *smallest* defensible API surface. Attack every named concept, interface, class, method, and indirection that can be collapsed, renamed, inlined, or deleted while preserving the documented invariants (fail-fast, no silent fallbacks, illegal states unrepresentable, framework slots speak roles, classes only for `new`, prove-then-extract). Per the mid-round amendment, "kolu and drishti must keep compiling with minimal churn" is interpreted strictly as "no gratuitous churn"; coordinated breaking changes (with paired drishti PR) are acceptable and routine when they unlock real shrinkage. Drishti's current consumption of `HostSession` in registry types is NOT an immovable constraint.

## Question 1: collapse session vocabulary?

**Yes. The current surface is larger than necessary.**

Concrete proposal (smallest that still satisfies "framework slots speak roles"):

Move the frozen control-core preamble (`hello` + the three identity facts) into `@kolu/surface-daemon` as a *universal* thing every daemon serves on its control surface (or as a method on the link). Then:

```ts
// proposed, in surface-nix-host (or surface-daemon if we accept the dep)
export interface RemoteMirrorSession<_C extends AnyContractRouter> {
  pin(): Promise<unknown>;
  currentClient(): Promise<unknown> | null;
  isDestroyed(): boolean;
  onState(cb: (s: HostSessionState) => void): () => void;
  markConnected(): void;
  destroy(): void;
  // NEW — honest, universal, already computed by both arms today
  identity(): { startedAt: number | null; contractVersion: string | null; buildCommit: string | null } | null;
}

// Then in padiBinding.ts, this becomes the entire definition of the padi extension:
export type BoundPadi = RemoteMirrorSession<typeof padiSurface.contract> & {
  drain(): Promise<void>;  // renamed from drainBoundPadi for brevity; same semantics
};
```

What this kills:
- The three duplicated readout methods (`padiStartedAt`, `padiSurfaceVersion`, `padiBuildCommit`) on BoundPadi. Evidence: both PadiBindingSession (padiBinding.ts:410, 479) and RemotePadiSession (remotePadiBinding.ts:670, 910) maintain parallel `boundIdentity` / `bindState` records and expose the same three getters. One `identity()` accessor replaces all six methods + the private state that backs them.
- The name `BoundPadi` as a first-class interface in most places. It becomes a one-line intersection alias (or even disappears if `drain` is pushed onto a capability-typed extension that only drainable sessions satisfy). The primer already says "daemon identity is universal; graduating `hello` finishes a job".
- One of the two places that read the hello facts (remotePadiBinding.ts:449 does `combined.surface.control.core.hello()`; local arm gets them via endpoint status from connectPadi + padiConvergence). After graduation the probe path in padiConvergence.ts:130 and the handshake in remotePadiBinding become the *same* code path.

What it deliberately does NOT do:
- Does not rename `HostSession` (it is the concrete class you `new` / `getHostSession`; the amendment lets us stop *exposing it from the registry* but direct ssh users still see the class).
- Does not touch `drain` vs `recycle` verb split (see Q3).
- The `identity()` addition is a required part of graduating the preamble (not optional); drishti-side agents that use the hosting stack will be updated in the paired PR to serve the control-core hello (or provide the identity) so the role carries it honestly. This is exactly the "finishing a planned job" the primer describes.

Evidence that the control core is already "the universal preamble" waiting to graduate: padi/src/controlCore.ts:29 serves exactly `{stateRoot, surfaceVersion, controlCoreVersion, startedAt, commit, buildId}` via the version-agnostic `hello`; padiConvergence.ts:130 dials only for that; decide.ts + convergenceIdentity.ts already treat contractVersion + buildId as the generic axes.

`BoundPadi` after this is effectively a type alias + one method. That is the smallest defensible surface for "a RemoteMirrorSession that also knows how to drain itself."

## Question 2: server-side pool and client-side dynamic scope — one volatility or two?

They are the *same* volatility expressed twice.

Evidence:
- `buildHostRegistry` (hostFanout.ts:349) exists to hold "N sessions, dispatch by name, with add/remove/reconnect/recheck". Its only hard requirement on the session (verified by reading the body) is `.destroy()` (called in remove + destroyAll) plus the RemoteMirrorSession methods that pumpRemoteSurface and reServeSurface already consume.
- The W4 plan (primer + server/index.ts:263) is exactly "kolu-server must hold several bound padis and pick one per browser tab" — i.e. the registry's job.
- The "client-side dynamic scope (surface-app)" is the *consumer* side of the same fact: the set of live upstream surface-clients changes at runtime, so the client object handed to the browser (or TUI) must be swappable.

Smallest proposal (now deeper because drishti shape is movable):
- Excise `HostSession` (the concrete class) from the *entire* registry / fanout public API surface. The registry becomes role-only. No C generic on the registry itself (the registry never uses the contract; only the entry-builder and downstream pump users do). One receptacle for "runtime set of live surface sessions", consumed by both server pooling and (future) surface-app dynamic scope.
- Do not invent a second abstraction. drishti (and any surface-app dynamic) will import the role (`RemoteMirrorSession`) + the (minimal) pooled shape, update its per-host session tracking, and pass `getHostSession<TheirC>(...)` (which still returns a class satisfying the role) into `buildEntry`. The registry no longer forces or leaks the ssh class or a top-level C.

Concrete proposal (what drishti will consume after the paired change):

```ts
// hostFanout.ts — the registry API surface, post-simplification
export interface PooledSession extends RemoteMirrorSession<any> {
  destroy(): void;
  reconnect?(): void;
  recheck?(): void;
}

export interface HostEntry<H> {
  session: PooledSession;  // NO HostSession, NO C
  handler: H;
}

export interface HostRegistry<H> {
  // ...
  getSession(host: string): PooledSession | undefined;  // was HostSession<C>
  // no C on the whole registry
  ...
}

export function buildHostRegistry<H>(
  opts: {
    initialHosts: readonly string[];
    buildEntry: (host: string) => HostEntry<H>;
    persist?: (hosts: string[]) => Promise<void>;
    log?: (line: string) => void;
  }
): HostRegistry<H>;
```

Inside the impl, `entries: Map<string, HostEntry<H>>`, `getSession` just returns the stored (role + destroy) value. The casts in hostFanout.test.ts (which exist *only* to satisfy the old `HostSession` slot) disappear.

What this kills:
- `HostSession` reference in HostEntry / HostRegistry / getSession / build* (hostFanout.ts:279,324,392 and index.ts exports of those types for this purpose).
- The top-level C generic on the registry (previously forced same contract type for all hosts in one registry; now per-entry via the builder's knowledge of its getHostSession call).
- All the `as ... & HostSession<...>` casts at buildEntry boundaries (hostFanout.test.ts:24, "HostSession is a class, so we mint a structural stub... and cast").
- Future hand-rolled maps in any consumer (including potential surface-app scope).
- The class-in-the-slot smell at its root: framework slot now speaks only the role (plus the three methods the body actually calls; see test comment at hostFanout.test.ts:14 "the registry never reaches past these three methods").

What it does NOT do:
- Does not remove `getHostSession` / `HostSession` class export (direct users — kaval-tui, remotePadiBinding.ts:1078 `getHostSession<PadiDaemonContract>`, arch docs — still use the concrete for its full surface and the pool keying).
- Does not change pump/reServeSurface (they already take the role).
- Does not affect kolu's padi paths (they never call buildHostRegistry).

The two appearances are the same volatility; now the machinery is *one* and role-pure. drishti's update is a mechanical type migration on its registry usage + its own session map (if any); the runtime calls remain identical.

## Question 3: two verbs (drain, recycle) or one supervisor renew()?

Current surface (grounded):

- padi: `drainBoundPadi()` (or `drain()` after Q1) — calls control.core.drain, waits for socket close (padiConvergence.ts:70, drainViaControlCore), PTYs survive in kaval.
- kaval: recycle is done *to* it from outside by its supervisor (padi's ptyHost).
- The L3 kit already unifies *decision* (`decide` + `converge` return `drain-and-replace` with axis), but enactment is split.
- Policy declares capability: `DrainableProbe` vs `PlainProbe` (converge.ts:49, policy.ts:20). A non-drainable cannot spell a drain arm (Pin 1).

Radical smallest proposal:

Keep the *verb names* for now (they encode the user-visible promise: "do my programs survive?"), but unify the *supervisor entry point* to a single method on the session role:

```ts
// on a future SupervisedSession (or on RemoteMirrorSession once we have a second bound daemon)
renew(opts?: { strategy?: "drain" | "recycle" }): Promise<void>;
// or, even smaller and more honest:
renew(): Promise<void>;  // the daemon declares its preservation strategy in its hello/preamble
```

The daemon (via its probe or a new `preservationStrategy` field in the graduated identity) tells the supervisor "I am state-external → drain me" vs "state-internal → snapshot-kill-restore".

What this kills:
- The user-facing split ("restart" button has to know which daemon it is talking to).
- Two separate code paths in callers (padiBinding.ts:530 vs whatever does recycle for kaval).

What it deliberately does NOT do:
- Does not erase the *semantic* difference. The outcome (PTYs live or die) remains visible and is still declared by the daemon, not hidden in a boolean on the call.
- Does not move enactment into the shared kit until a second bound daemon exists (prove-then-extract). The kit already owns `decide`/`converge`; the enactment branching can stay in the two arms for now.

This is smaller than maintaining two distinct top-level verbs forever.

## Question 4: fleet verbs — optional methods or declared capabilities?

Current code (hostFanout.ts:439):
```ts
recheckAll() {
  for (const entry of entries.values()) entry.session.recheck();  // no ?.
}
```
And `HostEntry` is typed to `HostSession` which always has them.

The registry is *only* used for fleet (drishti/pulam-web). kolu's padi path never goes through `buildHostRegistry` (server/index.ts uses the session directly).

Smallest defensible (post-amendment):

Keep them optional on the `PooledSession` (the role + destroy + fleet optionals) . Call sites inside the registry already tolerate absence if we guard (and will after the type change):

```ts
reconnect(host) { entries.get(host)?.session.reconnect?.(); }
recheckAll() { for (...) entry.session.recheck?.(); }
```

Declared capabilities (a `Reconnectable` brand or a second interface) adds a type-level union that only two call sites (the two fleet methods) would ever exercise. That is not a win in API surface size.

What the optional form kills:
- A compile-time obligation on every RemoteMirrorSession implementor that will never be a fleet member.
- The need for a `noopReconnect` shim.
- Any declared-capability interface (that would be extra surface with only two call sites in the registry).

What it does NOT do:
- It leaves a mild "silent no-op" at runtime for a caller that does `session.reconnect?.()` without checking. If we want to make "reconnectable" unrepresentable to call on the wrong thing, we would need the declared-capability form — but that enlarges the surface for zero observed consumers today. Radical position: leave it optional until a third fleet verb or a non-fleet consumer appears. (Amendment does not change the cost/benefit here; drishti fleet code will simply see the optionals on the PooledSession it gets from getSession.)

## Question 5: anything else that should shrink?

Yes — several small but real duplications and over-abstractions visible in the cited files.

1. **Duplicate identity state machines.** `PadiBindingSession.boundIdentity` (padiBinding.ts:380) and `RemotePadiSession.bindState` (remotePadiBinding.ts:310, with four discriminated cases) both exist only to answer the same three facts + "am I healthy?". After graduating `identity()` + `drain()`, both classes shrink to wiring + the one extra method.

2. **HostSessionState vs EndpointStatus projection.** padiBinding.ts:269 has `projectEndpointStatus` that collapses the local supervisor states onto the ssh-shaped `HostSessionState`. RemotePadiSession does a similar overlay in `derivedState`. Once the session role carries `identity()`, the projection can be one shared helper instead of two.

3. **The control core is padi-only in name only.** packages/padi/src/controlCore.ts is 70 lines of pure "serve these four procedures + one cell." Moving `buildControlCoreDeps` (and the surface definition) to `@kolu/surface-daemon` lets every daemon (including future drishti agents) serve the identical preamble without copying. This is exactly "graduate the frozen control core."

4. **No need for a new `PoolableSession` (or even `PooledSession`) name, and now we can drop `HostSession` from fanout entirely.** With the amendment, change the slot (and `getSession` return, `HostEntry`, the build fn generic) to the inline role shape or a tiny `PooledSession` that is *never* satisfied by naming `HostSession`. The registry types in index.ts and hostFanout.ts will no longer mention `HostSession` at all. drishti migrates its imports/types for the registry; it no longer has `HostSession` in its fanout consumption. The named type (if any) is internal to the receptacle. This is the root excision of the class from the "many sessions" concept.

5. **reServeSurface and pumpRemoteSurface already do the right thing.** They take `RemoteMirrorSession` (reServeSurface.ts:95, hostFanout.ts:122). No further collapse needed there; the smell was only the registry's slot.

## Net effect on API surface size (counting public names that callers must know)

Before (effective):
- RemoteMirrorSession, HostSession (class + pool fns + leaked into registry types), BoundPadi, HostEntry<C>, HostRegistry<C,H>, buildHostRegistry<C,H>, pumpRemoteSurface, reServeSurface, + the whole L3 kit names.

After (proposed collapses, using the amendment):
- RemoteMirrorSession (now with `identity()`), HostSession (only as the ssh `getHostSession`/`new` target + its own pool fns; *removed from registry/HostEntry/HostRegistry/getSession*), (BoundPadi as 1-line alias or gone), PooledSession (or inline role; only the receptacle), buildHostRegistry<H> (one fewer generic), the L3 kit (unchanged).

Net: HostSession + C-generic + HostEntry<C> + old getSession type + the casts they forced are deleted from the fanout API. At least three first-class names, one generic parameter, and six methods (the padi* readouts) disappear or become mechanical. The registry is now a pure role receptacle ("framework slots speak roles").

kolu is unaffected (uses role paths already). drishti consumption shape changes (it will receive `PooledSession` / role from `getSession`, supply role-satisfying sessions from its `buildEntry` using `getHostSession<ItsC>`, drop `HostSession` type imports for the registry); this is a coordinated paired-PR change, not "churn to avoid". The runtime and the three methods the registry body actually calls are identical (grounded: hostFanout.test.ts comment + impl body only call destroy/reconnect/recheck + role methods). No fallbacks, no override knobs, no silent degradation.

All claims above are directly traceable to the line numbers and identifiers in the files the topic told me to read.
