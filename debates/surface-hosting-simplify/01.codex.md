# Round 1: codex, radical simplifier

My smallest defensible answer is: do not add `PoolableSession`. It is the wrong
cut. The registry does not need a mirror session. The mirror pump does. Split
those roles and let kolu and drishti move together.

The amendment matters. If drishti can change, we should not preserve today's
`HostSession<C>`-shaped registry API just to keep its current imports happy. Make
the shared API say exactly what each site uses.

## 1. Collapse the session vocabulary

Current evidence:

- `RemoteMirrorSession<_C>` is already not really contract-typed. In
  `packages/surface-nix-host/src/hostSession.ts:224-231`, `pin()` and
  `currentClient()` return `unknown`; `_C` is documentary. The long comment at
  `hostSession.ts:206-223` says this directly: the role keeps the client opaque
  because consumers forward structurally.
- `reServeSurface` accepts the role, not `HostSession`, at
  `packages/surface-nix-host/src/reServeSurface.ts:91-97`.
- `pumpRemoteSurface` also accepts the role at
  `packages/surface-nix-host/src/hostFanout.ts:121-128`.
- `buildHostRegistry` is the outlier: `HostEntry.session` is `HostSession<C>` at
  `hostFanout.ts:276-279`, and `getSession()` returns `HostSession<C>` at
  `hostFanout.ts:323-324`.

The role should be renamed and de-genericized. "Remote" is false for
`PadiBindingSession`, and `<C>` is dead weight at the role boundary.

Concrete API:

```ts
export interface MirrorSession<Client extends SurfaceClientLike = SurfaceClientLike> {
  pin(): Promise<Client>;
  currentClient(): Promise<Client> | null;
  isDestroyed(): boolean;
  onState(cb: (s: HostSessionState) => void): () => void;
  markConnected(): void;
  destroy(): void;
}
```

Then:

```ts
export function reServeSurface<S extends SurfaceSpec>(opts: {
  source: Surface<S>;
  policy: RelayPolicy;
  session: MirrorSession;
  log?: (line: string) => void;
}): ReServedSurface<S>;

export function pumpRemoteSurface<S extends SurfaceSpec>(opts: {
  source: Surface<S>;
  session: MirrorSession;
  makeSink: (ctx: { seq: number }) => SurfaceSink<S>;
  liveClient?: LiveSpawnHolder<SurfaceClientLike>;
  liveProcedures?: LiveSpawnHolder<ProcedureForwarders<S>>;
  connection?: { set: (info: ConnectionInfo) => void };
  onLinkDown?: () => void;
  log?: (line: string) => void;
}): Promise<void>;
```

This kills:

- `RemoteMirrorSession<C>` as a public name.
- The explicit `<typeof padiSurface.spec, typeof padiSurface.contract>` at
  `packages/server/src/index.ts:269-272`.
- The misleading claim that the framework role is contract-precise.

It deliberately does not kill `HostSession<C>`. The class can stay generic
because direct callers of `getHostSession<PadiDaemonContract>()` still benefit
from typed `pin()` / `currentClient()` returns. Classes are for `new` and direct
use. Framework slots should take roles.

## 2. `PoolableSession` should be smaller than proposed

The proposed `PoolableSession = RemoteMirrorSession + destroy + optional
reconnect/recheck` is still too large.

`RemoteMirrorSession` already includes `destroy()` in `hostSession.ts:224-231`.
More importantly, `buildHostRegistry` does not call `pin`, `currentClient`,
`onState`, or `markConnected` at all. Its core lifecycle calls only
`entry.session.destroy()` on failed add, remove, and shutdown:

- add rollback: `hostFanout.ts:400-405`
- remove: `hostFanout.ts:411-431`
- destroy all: `hostFanout.ts:456-457`

The fleet verbs are separate:

- `reconnect(host)` calls `session.reconnect()` at `hostFanout.ts:435-437`
- `recheckAll()` calls `session.recheck()` at `hostFanout.ts:439-440`

So the registry role should be a managed resource, not a mirror session.

Concrete API:

```ts
export interface DestroyableSession {
  destroy(): void;
}

export interface HostEntry<S extends DestroyableSession, H> {
  session: S;
  handler: H;
}

export interface HostRegistryOptions<S extends DestroyableSession, H> {
  initialHosts: readonly string[];
  buildEntry(host: string): HostEntry<S, H>;
  persist?: (hosts: string[]) => Promise<void>;
  controls?: {
    reconnect(session: S): void;
    recheck(session: S): void;
  };
  log?: (line: string) => void;
}

export type HostRegistry<S extends DestroyableSession, H> = {
  has(host: string): boolean;
  hosts(): string[];
  getHandler(host: string): H | undefined;
  getSession(host: string): S | undefined;
  add(host: string): Promise<void>;
  remove(host: string): Promise<void>;
  registerConnection(host: string, ws: ClosableSocket): void;
  unregisterConnection(host: string, ws: ClosableSocket): void;
  destroyAll(): void;
} & (
  | { reconnect?: never; recheckAll?: never }
  | { reconnect(host: string): void; recheckAll(): void }
);
```

In implementation, overloads should make the returned registry include
`reconnect` / `recheckAll` only when `controls` is supplied. No optional methods
on the session. No silent no-op. The optionality lives at registry construction,
where the caller declares whether this registry has fleet controls.

This kills:

- `HostEntry<C, H>`.
- `HostRegistry<C, H>`.
- The concrete `HostSession<C>` slot.
- The proposed optional `reconnect?()` / `recheck?()` session smell.

It deliberately does not force every managed entry to be a surface session. The
registry owns a map and teardown. The re-serve pump owns mirroring.

## 3. Make daemon identity one value, then `BoundPadi` can become an alias

`BoundPadi` currently mixes three things:

1. the mirror session role, at `packages/server/src/padiBinding.ts:294-301`
2. the padi restart verb, `drainBoundPadi()`, at `padiBinding.ts:302-304`
3. three identity readouts plus convergence, at `padiBinding.ts:305-321`

The code already knows the identity is one lifecycle value. The local arm has a
single `BoundIdentity` record at `padiBinding.ts:333-359`, set as one record on
connect at `padiBinding.ts:407-412`, and cleared as one record on disconnect at
`padiBinding.ts:422-429`. The remote arm has the same idea as `RemotePadiIdentity`
at `remotePadiBinding.ts:176-183` and exposes it through `liveIdentity()` at
`remotePadiBinding.ts:909-930`.

The shared daemon packages already contain most of the universal identity:

- `ConvergenceIdentity` is `{ contractVersion, buildId }` in
  `packages/surface-daemon/src/convergenceIdentity.ts:29-38`.
- `readBakedIdentity(prefix)` is shared by daemon prefix at
  `packages/surface-daemon/src/buildIdentity.ts:26-42`.
- padi's frozen `hello` carries `surfaceVersion`, `startedAt`, `commit`, and
  `buildId` at `packages/padi/src/surface.ts:795-835`.
- kaval's `system.version` carries `contractVersion`, `startedAt`, and optional
  build identity at `packages/kaval/src/ptyHostSurface.ts:215-241`.

So yes: graduate the identity preamble, but do not graduate padi's whole control
core. `clock.now` is padi-specific today, and `drain` only exists for daemons
whose state can survive outside the process.

Concrete shared type:

```ts
export interface DaemonIdentity {
  contractVersion: string;
  buildId: string;
  startedAt: number | null;
  commit: string | null;
}

export type DaemonConvergence =
  | {
      state: "adopted-stale";
      runningBuild: string;
      expectedBuild: string;
      detail: string;
    }
  | { state: "skew-refused"; detail: string }
  | { state: "unconverged"; detail: string }
  | { state: "link-failed"; detail: string };

export interface DaemonMirrorSession<
  Client extends SurfaceClientLike = SurfaceClientLike,
> extends MirrorSession<Client> {
  identity(): DaemonIdentity | null;
  convergence(): DaemonConvergence | null;
}
```

Then:

```ts
export type BoundPadi = DaemonMirrorSession<PadiSurfaceClient> & RenewableDaemon;
```

If `renew()` replaces `drainBoundPadi()` as proposed below, `BoundPadi` is a type
alias, not a new role. Kolu-specific names like `padiStartedAt()`,
`padiSurfaceVersion()`, and `padiBuildCommit()` disappear. Callers read
`identity()?.startedAt`, `identity()?.contractVersion`, and `identity()?.commit`.

This deliberately does not put identity on `HostSession`. `HostSession` is an ssh
transport to an agent binary. `RemotePadiSession` is the thing that knows how to
ask padi's control surface for daemon identity.

## 4. Server pool and browser dynamic scope share vocabulary, not machinery

They both change which live surface client is used at runtime, but the clocks are
different.

Server pool:

- owns many entries at once in a `Map`, `hostFanout.ts:352-353`
- dispatches sockets by host with `getHandler()`, `hostFanout.ts:390-392`
- owns destructive teardown and socket eviction on remove, `hostFanout.ts:411-431`
- may keep idle upstream sessions warm

Browser dynamic scope:

- `connectSurfaces()` returns one socket, clients, status, health, and `dispose`,
  `packages/surface-app/src/solid/connectSurfaces.ts:71-101` and
  `connectSurfaces.ts:143-158`
- `SurfaceAppProvider` currently takes one static `controlPlane`,
  `packages/surface-app/src/solid/index.ts:550-558`
- it subscribes to that one client's `buildInfo` once at
  `solid/index.ts:610-618`

Those are not one implementation. A server registry is a many-entry resource
manager. A browser active scope is a Solid-owned "current connection" accessor
with old-client disposal.

Concrete browser-side breaking change, allowed because drishti moves with us:

```ts
export type SurfaceAppProviderProps<
  T extends { commit: string } = { commit: string },
  P extends ServerProbe = ServerProbe,
> = {
  controlPlane: Accessor<ControlPlane<T>>;
  clientCommit: string;
  buildInfo?: BuildInfoDef<T>;
  onError?: (err: Error) => void;
  children: JSX.Element;
} & ConnectionSource<P>;
```

Static callers pass `controlPlane={() => surfaceApp}`. Dynamic callers pass
`controlPlane={() => active().clients.surfaceApp}`. The provider must key the
`buildInfo` subscription off the accessor so switching the active client tears
down the old subscription and opens the new one.

Shared vocabulary can be "binding" or "active binding"; shared machinery should
not be extracted yet. A generic keyed resource manager would either leak Solid
into the server side or erase the server's socket eviction semantics.

## 5. One public daemon replacement verb: `renew()`

Keep the consequences typed; do not keep two public verbs.

Current evidence:

- padi declares a drainable policy:
  `packages/server/src/padiConvergence.ts:46-50`
- the shared policy type only permits drain arms for `"drainable"` probes:
  `packages/surface-daemon-supervisor/src/convergence/policy.ts:17-55`
- kaval's convergence probe is explicitly `"not-drainable"`:
  `packages/padi/src/ptyHost/connect.ts:126-155`
- `converge()` already treats `recycle` and `drain-and-replace` as two enactments
  of the same intent: make the running daemon match the supervisor's build or
  contract, `packages/surface-daemon-supervisor/src/convergence/converge.ts:12-20`

The user-facing question is not "drain or recycle?" It is "will my running
programs survive?" So make preservation strategy explicit and expose one verb.

Concrete API:

```ts
export type PreservationStrategy =
  | {
      kind: "state-external";
      children: "survive";
      enactment: "graceful-exit";
    }
  | {
      kind: "state-internal";
      children: "die";
      enactment: "snapshot-kill-restore";
    };

export interface RenewableDaemon<
  Strategy extends PreservationStrategy = PreservationStrategy,
> {
  readonly preservation: Strategy;
  renew(): Promise<void>;
}
```

For padi:

```ts
const preservation = {
  kind: "state-external",
  children: "survive",
  enactment: "graceful-exit",
} as const;
```

For kaval:

```ts
const preservation = {
  kind: "state-internal",
  children: "die",
  enactment: "snapshot-kill-restore",
} as const;
```

This kills `drainBoundPadi()` as a public API name. It does not kill padi's
wire-level `control.core.drain`; that remains the private enactment for the
`state-external` strategy. It also does not pretend kaval preserves processes.
The type carries `children: "die"`.

## 6. Smaller internal shrink: one "await graceful exit" helper

The local and remote padi drains have the same shape with different liveness
signals.

- Local `drainViaControlCore()` starts the drain and waits for socket close,
  `packages/server/src/padiConvergence.ts:82-117`.
- Remote `drainAndAwaitClose()` starts the drain and polls `control.core.hello`
  until it stops answering, `packages/server/src/remotePadiBinding.ts:779-825`.

The transport-specific part is "how do I know the daemon stopped?" The rest is
the same fail-fast algorithm.

Private helper, not public API:

```ts
async function awaitGracefulExit(args: {
  startExit(): void;
  isAlive(signal: AbortSignal): Promise<boolean>;
  ceilingMs: number;
  pollMs: number;
}): Promise<{ exited: true } | { exited: false; detail: string }>;
```

This is worth extracting because there are already two implementations. It
deliberately does not merge local endpoint convergence with remote ssh
convergence. The remote arm still needs instance-keyed drain admission
(`remotePadiBinding.ts:738-769`) because ssh has no socket-close signal with the
same meaning as the local endpoint.

## Bottom line

The smallest API surface is:

```ts
interface MirrorSession<Client = SurfaceClientLike> { ... }
interface DestroyableSession { destroy(): void }
interface DaemonMirrorSession<Client = SurfaceClientLike>
  extends MirrorSession<Client> {
  identity(): DaemonIdentity | null;
  convergence(): DaemonConvergence | null;
}
interface RenewableDaemon<Strategy = PreservationStrategy> {
  readonly preservation: Strategy;
  renew(): Promise<void>;
}
type BoundPadi = DaemonMirrorSession<PadiSurfaceClient> & RenewableDaemon;
```

`HostSession` stays the ssh class. `buildHostRegistry` stores destroyable
entries, with declared fleet controls only when the caller supplies them.
`reServeSurface` consumes `MirrorSession`, without a dead contract generic.
`surface-app` dynamic scope should be an accessor to the active control plane,
not a shared registry.
