# Round 2: codex reply

My round-1 cut survives: do not add `PoolableSession`. After reading Claude and Grok, I would sharpen it this way: the registry needs a smaller role than `HostSession`, but that role is not a mirror session. It is just a destroyable entry, with fleet controls layered only where the caller actually has them.

## Grok

### G1. Put daemon identity on `RemoteMirrorSession`; make `BoundPadi` an alias plus `drain`

Steelman: this is the most aggressive way to erase the duplicated padi identity surface. Today `BoundPadi` repeats the same idea several times: it has `pin`/`current`, plus `padiStartedAt()`, `padiSurfaceVersion()`, `padiBuildCommit()`, and `padiConvergence()` (`padiBinding.ts:294-321`). Remote padi then rebuilds the same identity out of pin/current state in `liveIdentity()` and `padiConvergence()` (`remotePadiBinding.ts:909-970`). Grok is right that the consumer should not need three padi-specific getters when the daemon has one identity.

Concede the shrink, rebut the placement. `RemoteMirrorSession<_C>` is not a daemon contract today. It is the role required by `reServeSurface()` and `pumpRemoteSurface()` (`reServeSurface.ts:91-97`, `hostFanout.ts:121-128`): `pin`, `current`, `onState`, and `markConnected`. Those functions work for arbitrary remote surfaces, not just supervised daemons with baked build identity. Putting `identity()` there would make every mirror claim daemon semantics.

The smaller cut is:

```ts
interface MirrorSession<Client = unknown> {
  pin(...): void
  current(...): Client
  onState(...): () => void
  markConnected(): void
  destroy(): void
}

interface DaemonMirrorSession<Client = unknown> extends MirrorSession<Client> {
  identity(): DaemonIdentity | null
  convergence(): DaemonConvergence | null
}
```

Then `BoundPadi` can be a padi-specialized daemon mirror with the padi-specific action that remains. That kills the duplicate identity getters without lying about every mirrored surface.

### G2. Remove `HostSession` from `buildHostRegistry`; one pool or two?

Steelman: Grok found a real smell. There is a module-level pool in `hostSession.ts`:

```ts
const pool = new Map<string, HostSession<AnyContractRouter>>();
```

and `buildHostRegistry()` also has an `entries` map holding `session: HostSession<C>` (`hostFanout.ts:276-279`, `352-353`). Worse, the `getHostSession()` comments say the registry remove path can call `evictHostSession()` (`hostSession.ts:926-939`), but this repo has no production call to `evictHostSession`; grep only finds tests, exports, and docs. It is fair to ask whether we accidentally have two session pools.

Verdict: two maps should remain, but they are not the same pool.

`getHostSession()` is a process-global transport/session dedupe keyed by `(host, binary)` (`hostSession.ts:953`). It intentionally ignores `.drv` and later resolvers for the same key (`hostSession.ts:926-939`). It owns no host list, no persistence transaction, no fanout handler, and no socket sets. It is also not universal: `dialAgentOnce()` intentionally constructs `new HostSession(...)` instead of using the pool for one-shot dials (`dialAgentOnce.ts:165-174`).

`buildHostRegistry()` is an app-level host-set registry. It is keyed by `host`, rejects duplicate configured hosts before side effects (`hostFanout.ts:361-369`), rolls back persisted adds on build failure (`hostFanout.ts:400-405`), tracks sockets per host (`hostFanout.ts:352-353`), and destroys entries when hosts are removed or the registry is torn down (`hostFanout.ts:430`, `456-457`). That is not a transport pool; it is ownership of a declared fleet.

So: one `HostSession` pool, one host registry. The fix is not to collapse them. The fix is to stop making the registry type pretend it owns `HostSession<C>`.

I concede Grok's API cut here, but reject `PooledSession` as the name and shape. `hostFanout.test.ts` already proves the registry only touches `destroy`, `reconnect`, and `recheck`; the fake session is cast to `HostSession` only because the current slot is too concrete (`hostFanout.test.ts:14-17`). The base registry should store `S extends DestroyableSession`, not `HostSession<C>` and not `RemoteMirrorSession<any>`.

### G3. Keep verbs now; maybe converge on `renew()` later

Steelman: `drain` and `recycle` are not identical enactments. Padi has a control-core `drain` method and waits for socket close (`padiConvergence.ts:82-117`). The generic supervisor has richer decisions: spawn, adopt, report, refuse, recycle, and drain (`converge.ts:155-226`). Forcing a public `renew()` now could hide important state locality.

Concede the timing. I still think `renew()` is the eventual public verb, with preservation strategy declared by the daemon. But after Claude's prove-then-extract point, I would not make that the first cut. The immediate shrink is identity and registry roles; `renew()` should wait until at least two bound daemon consumers need the same public operation.

### G4. Optional `reconnect?()` and `recheck?()` on `PooledSession`

Steelman: this is the fewest lines. `buildHostRegistry()` has only two fleet verbs that need those methods (`hostFanout.ts:435-440`), and unknown-host reconnect is already a no-op. Optional methods avoid a second type or builder.

Rebut. Optional methods turn "this registry supports fleet reconnect" into silent absence. That violates the repo rule against fallback knobs, and it weakens tests: a missing `reconnect` would pass by doing nothing instead of failing at construction or compile time.

Use a declared fleet role instead:

```ts
interface DestroyableSession {
  destroy(): void;
}

interface FleetSession extends DestroyableSession {
  reconnect(): void;
  recheck(): void;
}
```

The base registry can work over `DestroyableSession`. A fleet registry can require `FleetSession` and expose `reconnect()`/`recheckAll()`. No optional methods, no silent no-op for a miswired session.

### G5. Shrink duplicate state machines and avoid a new role name

Steelman: Grok is right that duplicate projections are a simplification target. `HostSessionState` and surface-app `EndpointStatus` both describe endpoint connection/liveness, and padi-specific control-core naming is heavier than its actual daemon identity payload.

Concede the identity duplicate, partially concede the projection duplicate, reject "no role name". There is code evidence for extracting identity now: padi and kaval both expose daemon version/build/start identity shapes (`padi/src/surface.ts:795-835`, `kaval/src/ptyHostSurface.ts:234-241`), and `surface-daemon` already has `DaemonBuildIdentity` and `ConvergenceIdentity` (`buildIdentity.ts:26-42`, `convergenceIdentity.ts:29-38`). But `HostSessionState` includes process/transport supervision details, while `EndpointStatus` is a UI-facing connection status. They can share a projection later; they should not be forcibly unified in the first cut.

The role name is what prevents the accidental re-growth of `HostSession<C>` in the registry. I refuse `PoolableSession`, but not roles. The role just has to be the actual role: `DestroyableSession`, `FleetSession`, `DaemonMirrorSession`.

## Claude

### C1. The missing axis is "multiplicity and lifetime of surface clients"

Steelman: Claude names the real cross-cutting concern better than I did. `surface-app` assumes one static `controlPlane` in context (`solid/index.ts:550-558`, `610-618`). The server registry assumes a changing host fleet. The kolu server has a boot-bound padi binding. These are all about how many clients exist, who owns them, and when they may be replaced.

Concede the vocabulary, keep the machinery separate. The browser provider needs a reactive client source. The server registry needs host-set mutation, persistence rollback, and socket cleanup. Those are not the same implementation. Shared vocabulary is useful; shared pool machinery is not proven.

### C2. Identity is universal in substance; drain is declared capability

Steelman: this is exactly the right split. Identity belongs in shared daemon vocabulary because padi and kaval both have it. Drain belongs only to daemons that declare it. Claude's "control-core graduation" keeps the common preamble common without pretending every daemon drains.

Concede. This survives the radical cut. The only correction is that identity should attach to a daemon-mirror role, not the base mirror role.

### C3. Naming hides hierarchy; prefer primer/docstrings before churn

Steelman: renaming everything can create churn without reducing concepts. Claude's hierarchy is correct: mirror role, host-session implementation, domain extension. A primer table would help readers avoid treating `RemoteMirrorSession`, `HostSession`, and `BoundPadi` as peers.

Partial rebut. Documentation is necessary but not sufficient where the type itself is wrong. `RemoteMirrorSession<_C>` has a dead generic: `current()` returns `unknown`, not `_C` (`hostSession.ts:224-231`). `HostEntry<C,H>` stores `HostSession<C>` even though the registry tests say only `destroy`/`reconnect`/`recheck` are used (`hostFanout.test.ts:14-17`). Those are API defects, not just naming defects.

So: add the primer, but also cut the false generic and the false concrete class slot.

### C4. No optionality; fail loud for unsupported fleet verbs

Steelman: this is the strongest answer to Grok's optional methods. If a registry exposes `reconnect`, every session in that registry must reconnect. If it cannot, that is a type error or construction error, not a runtime shrug.

Concede fully. This is one of the doctrine defenses that survives no-`PoolableSession`.

### C5. `drain`/`recycle` intent can unify, but enactment is state-local

Steelman: a user wants "make this daemon converge", not "call this internal padi drain procedure". But the implementation still depends on whether we have a live control plane, whether we can adopt, whether we must spawn, and whether the daemon advertises drainability.

Concede with lower priority. Keep the strategy vocabulary. Do not put it on the first API cut unless the second bound daemon arrives at the same time.

### C6. Claude's four doctrine defenses under no-`PoolableSession`

Per-member forwarding policy survives. The policy lives in the mirror/fanout path: values can be held/rebound, byte streams fail through. `reServeSurface()` and `pumpRemoteSurface()` already depend on the mirror role, not on a pool role. Removing `HostSession` from `HostEntry` does not flatten this policy.

Fail-loud degraded states survive. Padi's remote binding already exposes skew/unconverged/link-failed style states through `padiConvergence()` and `derivedState()` (`remotePadiBinding.ts:936-995`). A `DestroyableSession` registry slot has no reason to collapse those states; it should not even know they exist.

The role/implementation split survives and becomes stricter. The proposed roles are `MirrorSession`, `DaemonMirrorSession`, `DestroyableSession`, and `FleetSession`. `HostSession` remains one implementation. `BoundPadi` remains a domain extension or alias over the daemon mirror. `PoolableSession` is rejected because it mixes mirror, pool, and fleet ideas.

Prove-then-extract survives. We can prove `DestroyableSession` from `buildHostRegistry()` and its tests now. We can prove shared daemon identity from padi, kaval, and `surface-daemon` now. We cannot yet prove one browser/server pool implementation or universal public `renew()` strongly enough to ship them first.

## Revised Priorities

1. Cut `buildHostRegistry()` away from `HostSession<C>`. Store `S extends DestroyableSession`; put `reconnect`/`recheckAll` behind a fleet-specific role or builder requiring `FleetSession`. No `PoolableSession`, no optional methods.

2. Clarify the two maps. Keep the module-level `getHostSession()` pool as the `(host,binary)` shared-session cache. Keep `buildHostRegistry()` as the host-set owner. Audit drishti, then delete or privatize public `evictHostSession()` if it is only stale docs/tests, since destroyed pooled sessions are already treated as absent (`hostSession.ts:955-967`).

3. Rename and shrink the mirror role: `RemoteMirrorSession<_C>` becomes `MirrorSession<Client = unknown>` or loses the dead generic. Do not add daemon identity to the base mirror role.

4. Graduate shared daemon identity/convergence vocabulary. Collapse padi's duplicate identity getters into one daemon identity surface. Make `BoundPadi` a padi-specialized `DaemonMirrorSession` plus the padi action that remains.

5. Make surface-app support a dynamic client source with browser-appropriate machinery. Share the vocabulary of lifetime and replacement with the server registry, not the registry implementation.

6. Defer public `renew()` until the second bound daemon consumer proves the common operation. Keep drain/recycle as internal enactments behind declared daemon capabilities for now.

## Forks I Refuse To Concede

I refuse `PoolableSession`, especially as `RemoteMirrorSession<any> & { reconnect?; recheck? }`.

I refuse optional fleet methods that silently no-op when a registry claims to support fleet reconnect/recheck.

I refuse putting `identity()` on every mirror session. Identity is a daemon role, not a mirror role.

I refuse collapsing `getHostSession()` and `buildHostRegistry()` into one pool. They are different authorities: shared transport cache versus declared fleet ownership.

I refuse a shared browser/server lifetime implementation before the code proves it. Shared words now; shared machinery only after a second consumer forces the same shape.
