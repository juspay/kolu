# Round 1 — claude (doctrine judge): the step-back evaluation

Scope: the hosting side as it stands on master (`51fc8feb7`) plus the queued W4 decisions. Method: /perfection-review (where does each defect class relocate; what would make it inexpressible) and /architecture-first-principles (values-not-places · one authority on its own clock · illegal states unrepresentable · guarantees at the knowing endpoint).

## F1 — the real disease: the framework keeps being "one axis short," and each phase widens it ad hoc

Three episodes of one pattern: `surface-app` assumes ONE static client per app (W4-PR2 must widen it); `buildHostRegistry` types its slot with the concrete class (the PoolableSession widen must fix it); kolu-server assumed ONE boot-time binding (the W4 pool must fix it). The un-named axis under all three: **the multiplicity and lifetime of surface-clients**. Perfection's question is not "fix three corners" but "name the axis once." My honest analysis stops short of "one machinery," though: the server pool holds N upstreams *concurrently warm*; the client scope swaps ONE active downstream; the reactive-teardown problem exists only on the client. Shared **vocabulary** (a keyed, changing set of live clients) — yes. Shared **machinery** — unproven, and forcing it would be receptacle-invention. **Fork for this debate**: is there a smallest shared kernel (a keyed client-set with lifecycle events) both sides genuinely consume, or is vocabulary-only the honest stop?

## F2 — identity is universal in substance; the packaging debt is real and cheap to clear

Every durable daemon stamps started-at · commit · contract version; the L3 kit already holds the generic type (`ConvergenceIdentity`) and reads it for both daemons. Graduating the frozen control core (hello · version · drain* · clock.now) into the shared daemon package as the standard preamble finishes a planned job. Then the concrete shrink: `BoundPadi` ≈ `SupervisedSession<PadiContract>` — a type alias plus padi's two verbs' wiring, not a hand-maintained role. Net concept count drops by one. (*drain graduates as a TYPED CAPABILITY, not a universal — see F4.)

## F3 — naming hides the hierarchy; the code is innocent, the vocabulary guilty

`RemoteMirrorSession` / `HostSession` / `BoundPadi` read as three peers; they are role / one-implementation / domain-extension. This cost a real confusion round this week (recorded in surface-hosting-101). Cheapest fix first: the primer's table becomes canonical, linked from all three docstrings; rename only if confusion recurs. I will concede renames to the simplifiers if they show the docstring fix insufficient — but renames churn history and the primer already exists.

## F4 — optionality lives in types, never in maybe-methods

The codebase's own precedent decides this: `DrainableProbe` vs `PlainProbe` made "drain a kaval" a compile error; the gray-chip fix made "subscribe before the key exists" a defined state. An optional `reconnect?()` that silently doesn't exist is the same defect class those two killed (silently-absent behavior). Whatever shape the pooled-session role takes, fleet verbs are a declared capability or provably-never-called — never a no-op.

## F5 — drain/recycle: the intent is already unified; the enactment fork is a FACT of state-locality, not an API wart

One intent ("the running daemon isn't the build I want; make it so, preserving what can be preserved") — already unified in the kit's decide()/converge(). Two enactments, forced by where the daemon's valuable state lives: external (padi's PTYs live in kaval → drain, children survive, automatic) vs internal (kaval's PTYs are its children → snapshot-kill-restore, programs die, human-gated). A `kill(respawn:true)` flag would bury the one question users care about — do my programs survive? — so the *verbs* must not merge. The open, legitimate unification: a supervisor `renew()` that branches on a daemon-DECLARED `PreservationStrategy` ("state-external" | "state-internal"), with the existing verbs as the two strategy implementations. I lean yes-when-a-third-daemon-appears; doing it now serves a population of two whose enactments share almost no code.

## F6 — what I defend, doctrine-bound (the simplifiers must pay for these in evidence)

1. **The per-member forwarding policy** (values hold-open + rebind; byte streams fail-through). This is guarantees-at-the-knowing-endpoint incarnate; flattening it to one behavior re-opens either silent stale bytes or needlessly broken values.
2. **Fail-loud degraded states** (skew / unconverged / adopted-stale / link-failed as standing, surfaced states). Any simplification that collapses these into "disconnected" trades honesty for tidiness.
3. **The role/implementation split itself.** One role + one ssh implementation is the MINIMUM for "two consumers, different far ends" — collapsing role into class re-creates the exact wall W4 just hit.
4. **Prove-then-extract.** No shared kernel, no SupervisedSession package, no renew() until a real second consumer exists. The graveyard of this repo's rejected shapes (padi-web-client, the bespoke pool) is the evidence this rule works.
